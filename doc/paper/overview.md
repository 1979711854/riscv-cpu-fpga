## 三个最重要的发现

**1. 一个被漏掉的亮点数字 —— 而且已经兑现成了分数**

`report_timing/cpu_top_board.rtr` 显示
`Requested 85.0051 MHz / Estimated 87.0019 MHz / Slack +0.270 ns`（**双发射**；单发射 Estimated 91.3993 MHz / Slack +0.823 ns），
时序余量 **2.3%**，`Design Summary : All Constraints Met`（TNS 0、失败端点 0）。
`Estimated Frequency` 是工具给出的实际可达频率，是评审最能看懂的硬指标之一。

更关键的是**余量已经换成了分数**：27 MHz 时代本设计可达 47.81 MHz、余量 77%，
即能力被平台固定时钟限制住、**用不上**。改用**板载 27 MHz 晶振 + Pango PLL 倍频**、
一路提频（45 → 49.8927 → 62.0309 → **85.0051 MHz**）之后，
**同一份设计的实际得分由 75.25 一路涨到 351.86 CoreMark（iterations/sec）**。
提频各代分开记：45.0005 MHz 时 **125.40**（纯提频 +66.7%，比例恰好等于时钟比 45.0005 ÷ 27）；
49.8927 MHz 时 **140.89**（效率也已升到 2.824）；62.0309 MHz 时 **170.64**；
85.0051 MHz 单发射 **233.85**。执行效率与时钟无关（同一代设计跨时钟逐位不变），
所以提频阶段的提分纯粹来自频率。
在 85 MHz 上又叠加了两次**效率跃升**：顺序双发射（2.751 → **3.186**，+15.8%）与
任务C `EARLY_LD`（3.186 → **4.139**，+29.9%），**时钟一直没动** ——
最新的 **351.86（85 MHz 双发射 + `EARLY_LD`）**就是这么来的。
这个"把余量兑现成分数"的故事比"我们余量很大"有冲击力得多。
（**2026-10-11 板上实测**：`Total ticks 994,386,960` ÷ 85,005,100 = 11.69797 s → 351.86 CoreMark，
日志 `doc/board/uart_20261011_225624.txt`；**I+D Cache 版** 76.5052 MHz / ITER=3668 → 313.63 分，
日志 `doc/board/uart_20261012_155934.txt`。历史：**2026-10-06** `Total ticks 994,988,178` → 11.7050 s →
270.82 CoreMark，日志 `doc/board/uart_20261006_162410.txt`；49.8927 MHz ITER=1663 = 11.8031 s / 140.89。）

> [!] **口径别搞混（旧文档在这里算错过）**：**+66.7% 是"纯提频收益"**
> （效率分子不变，只有频率变）。**不要把它和流水线优化带来的效率提升乘在一起** ——
> 那是**两个互相独立的事件**：
> 效率侧是 2.380 → 2.611 → 2.787 → 2.824 → 2.751（两拍乘法器）→ **3.186**（双发射）（与时钟无关）；
> 频率侧是 27 → 45 → 49.8927 → 62.0309 → **85.0051 MHz**（提频，与流水线无关）。
> 旧文档的"70.50 → 125.42（+77.9%）"两处都错：**70.50 实为 2.611 × 27**，
> 用的是**第二轮优化后、第三轮之前**的效率值，且 **2.787 × 27 = 75.25**，不是 70.50。
>
> [!] **再往下的 45 → 49.8927 MHz 那一步（125.40 → 140.89，+12.36%）也不是纯提频** ——
> 它 = 时钟 +10.87%（49.8927 ÷ 45.0005）**乘上**效率 +1.33%（BHT，358,846 → 354,119 拍）。
> **两笔账要分开报。**

> 数据出处：`doc/resource_efficiency.md` §3/§4 与 2026-09-25 综合的 `cpu_top_board.rtr`
> （上板顶层已改为 `cpu_top_board`，旧的 `cpu_top.rtr` 不再更新）。

## 与项目既有规划的一个分歧

`doc/plan.md` 把"2 路组相联 I/D Cache"列为高阶加分项。但本设计的存储器是
**行为级单周期 BRAM**（`unified_mem`），访存本就 1 拍返回、无缺失惩罚，
加 Cache 收益有限；且 `fence.i` 必须从 NOP 升级为"冲刷 I-Cache"，
否则 `fence_i` 会退化回 FAIL，正确性风险高。

相比之下 **BHT 分支预测（2 位饱和计数器，256 项）** 在资源上依然加得起 ——
当前 LUT 占 **4.94%（7,896/159,800，双发射 + I+D Cache，含视频全 SoC；不开 Cache 时 4.32% = 6,909）**，空间仍极充裕，而分支仍是单项最大的效率损失
（BHT 之后约 **12.8%**，是 load-use 停顿的 2.2 倍），开销真实且可量化。

> [!] **"优先 BHT"已经落地，结论要按结果改写（2026-09-25 更正）**：第三轮优化
> **ID 级静态后向预测 + jal**（`core.v` 的 `id_pred_taken = (branch && imm[31]) || jump`）
> 把分支惩罚从"无条件 2 拍"变成 **1 拍（命中）/ 2 拍（未命中）**，
> 那 14.0% 是**静态预测之后**的残值；**第四轮的 256 项 BHT 又拿掉 4,727 拍（1.32%，
> 捕获率 56%），每迭代 358,846 → 354,119 拍**。残余空间已定位：256 项表偏小、
> 别名冲突（341 个静态分支里 149 个冲突），**扩到 1024/4096 项预计还能回收约 1%**。
> **"Cache 收益有限"的结论不变。**
