## 0. 先说结论：这篇论文的成败取决于三件事

**第一，你手里有一个被严重低估的数字。** 时序报告里写着：

```
Requested Frequency   27.0000 MHz
Estimated Frequency   47.8126 MHz
Slack                 16.122 ns
Design Summary: All Constraints Met.
```

你们在设计上跑到了 **47.8 MHz**，但约束只要求 27 MHz —— **时序余量高达 77%**。
"Estimated Frequency" 是工具给出的实际可达频率，这是评审最能看懂的硬指标之一。
目前 `README.md` 只写了"27MHz 下 Setup +16.122ns"，把最有冲击力的一半（47.8MHz）漏掉了。

> 数据来源：2026-09-21 取指重定向改造后**与新 RTL 同批**的
> `pds/RV32I_1/report_timing/cpu_top.rtr`（14:08 那次综合）。改造前是
> Estimated 46.4209 MHz / Slack +15.495 ns —— **读报告前先确认它与当前 RTL 同批**，
> 旧数据备份在 `report_timing/bak/`。

**第二，你们最可能被扣分的不是性能，是"工程完整性"和"稳定性"。**
`doc/base_task_status.md` §已知限制 第 5 条写得很清楚：`.fdc` 目前仍按**远程平台**约束，
`led`/`key`/`uart_rx` 引脚**整块被注释掉**，未指定 LOC 会让 place & route **失败**。
而 `doc/board/` 目录是**空的**。这意味着：**演示录像、板卡照片这类评审硬证据，目前一无所有。**
论文写得再好，如果拿不出"实物在跑"的证据，应用场景分和工程分都拿不到。

**第三，最大的性能提升点不在 Cache，在分支预测。** 见 §4.2，BHT 方案用不到 50 个 LUT
就能吃掉你们当前超过一半的动态分支开销，性价比远高于 Cache。

## 2. 应重点突出的技术亮点

按"评审可感知度"排序，前三个不要省。

### 亮点 1：统一存储器架构 —— 这是你们最"有故事"的设计决策（强烈建议作为全文核心）

很多队伍会写"我实现了五级流水线 + 前递 + 停顿"，这是**教科书标准答案**，区分度低。
你们有一个真正做过取舍、且**有实测证据**的设计决策：

**问题**：哈佛结构（imem/dmem 两块独立 BRAM）下，`fence_i` 测试 TIMEOUT。
**根因分析**：不是"少实现一条指令"，而是**存储器结构决定的** ——
store 只写 dmem、取指只读 imem，写进代码区的指令永远进不了取指通路，
`fence.i` 实现成 NOP 也没用。
**决策**：合并为一块物理双端口 BRAM（A 口取指 / B 口访存），
软件层看到统一地址空间（modified-Harvard），核内取指/访存通路仍逻辑分离。
**收益**：① `fence_i` 从 TIMEOUT 转 PASS；② BRAM 用量减半（对"资源效率"评分项直接有利）；
③ 为后续 I/D Cache 留出干净的后备存储。
**证据**：整个回归里 **`fence_i` 是唯一变化的一项，其余 40 项逐项一致，CoreMark 周期一字不差**。

这个"问题→根因→决策→收益→无副作用验证"的完整闭环，
**是论文里最能体现工程能力的一段**。建议在摘要里就点出来，第 3/4 章展开。

写法上注意用对比结构，并诚实写出残留限制（见 §4.1）—— 主动写限制反而显得可信。

### 亮点 2：Fmax 46.4MHz / 时序余量 72%

不要把时序报告贴上去就完事。要**解释你们为什么能跑这么快**，这才是加分项：

- **多拍迭代除法器**（`divider.v`，恢复余数法，每拍只做一次"移位 + 32 位比较/减法"）：
  关键路径约等于一个减法器。**如果用单拍组合除法，这条路径会直接拖垮 Fmax** ——
  这是一个明确的设计取舍，值得单独一段展开，并给出"若用组合除法，Fmax 会降到多少"的估算或实测。
- **写通路零寄存器 + 读数据在 MEM→WB 沿寄存**（`mem_bus.v` 头注释中的两条硬约束）：
  说明你们清楚"哪里能插寄存器、哪里不能"，并解释了为什么（冒险单元不知道内存有几拍）。
- **前递路径的优先级设计**（EX/MEM 优先于 MEM/WB，load 结果不从前递取）：
  关键路径在 EX 的 ALU/前递 mux，说明你们做过时序导向的设计。

**建议补一张表**：`约束频率 / 估计频率 / WNS / TNS / 失败端点`，注明"多 seed"，
并说明 hold 也收敛（+0.145ns，失败端点 0）。这体现你们做到了**签核级**的时序验证。

### 亮点 3：验证体系的三层结构与"回归纪律"

这是**软性但高区分度**的亮点。你们有一套多数学生队伍不具备的工程习惯：

- **单元层**：ALU / 除法器 / UART FIFO / 译码器 / GPIO / UART RX 共 6 个测试台
- **集成层**：riscv-tests 全量 50 项 / CoreMark / demo 端到端 7 项
- **回归纪律**：改动 RTL 后，`50/0/0` 与 CoreMark 的**计时区间 382,972 拍**
  （测试台总周期 1,488,333）**必须同时不变**，后者是"没碰坏流水线"最灵敏的探针

**特别值得写进论文的两件事**：

1. **把基线 ELF 入库**（`third_party/riscv-tests-elf/`）并说明理由：
   "上游 riscv-tests 会变，重新 clone 未必复现同一批二进制，基线漂移会让人误判成自己改坏了 CPU"。
   —— 这是**验证可复现性**思维，评审里懂行的人会认。
2. **`ma_data` 的"预期失败"标记**：明确写"这一项必须仍然 FAIL，
   如果它被修好了说明有人动了 load/store 的字节抽取逻辑，属非预期改动"。
   —— 把"已知失败"转化为**回归哨兵**，这个思路非常专业。

### 亮点 4：CoreMark 口径的严谨推导

你们踩过一个坑并把它变成了论文素材：**ITER=1 的测试台总周期不是"每迭代成本"。**
它是仿真测试台的总周期，含约 110 万周期的一次性 UART 打印开销；而 CoreMark 自己的
`Total ticks` 计时在打印之前就停了、不含打印。两者口径混用会把 ITER 估小
（曾据此写成"ITER≈200 约 10s"，实测只有 3.11s，被判 invalid）。

论文里应写：**如何用两次实测解方程得出每迭代成本，并用它反推 ITER**：

```
改造前设计（分支惩罚 3 拍）：
  ITER=200 →  84,018,579 / 200 = 420,093 周期/迭代
  ITER=700 → 294,065,438 / 700 = 420,094 周期/迭代
  仿真（ITER=1）                 420,070 周期/迭代
  → 真机与仿真只差 0.0057% → 仿真模型可信 → 仿真数据可作论文依据
  → CoreMark/MHz = 1,000,000 / 420,094 ≈ 2.38

取指重定向改造后（分支惩罚 2 拍）：
  仿真（ITER=1）                 382,972 周期/迭代
  → CoreMark/MHz = 1,000,000 / 382,972 ≈ 2.611
  → ITER 必须重算：ITER ≥ 10 × 27,000,000 / 382,972 ≈ 705，取 770（10.92 s）
```

**两个独立结论都可以写进论文**：

1. **"0.0057% 的仿真-实测一致性"** 证明了行为级仿真模型的保真度，使后续所有仿真
   数据都有了背书。这一点很多队伍想不到，是很好的差异化内容。
2. **"ITER 必须跟着每迭代周期走"** 是一个真实的工程约束 —— 优化了流水线却没改 ITER，
   CoreMark 直接判 invalid（700 × 382,972 / 27 MHz = **9.93 s < 10 s**）。
   把"提速反而导致被测项失效"这个反直觉的点写出来，比单纯报数字有说服力。

> 仿真的 420,070 与 382,972 都是 2026-09-21 用测试台的 `+PROF` 直接读 CoreMark
> `Total ticks` 得到的，并用 `start_time`/`stop_time` 两次读 `0x7FF4` 的周期号交叉验证。
> 此前文档写的「仿真 ≈ 420,414」无法复现，已更正 —— 修正后一致性论证反而更强。

### 3.2 表述策略：讲"契约"而不只是"连线"

你们代码里有一个非常好的习惯值得提升到论文层面：**显式写出模块间的时序契约**。
例如 `core.v` 里对取指口的注释：

> "契约：同步读、恰好 1 拍延迟、只读、且不做任何仲裁/冲突检测。
> 本模块的 stall/flush 补偿逻辑依赖 A 口每拍都能独立工作，加仲裁会直接破坏取指时序。"

论文里应当用**同样的语言**描述接口。这传达的信息是：
"我们理解模块化设计的本质是契约，而不是连线" —— 这远高于"我画了个框图"的层次。

### 3.3 一个必须讲清楚的点：取指的两拍延迟与 stall 补偿

`spec.md` §3.1 里的稳态不变量写得很漂亮，**务必放进论文**：

```
imem_rd   = mem[pc_r - 4]      // 在途，下一拍进 IF/ID
if_id_pc  = pc_r - 8           // 正在 ID 译码
id_ex_pc  = pc_r - 12          // 正在 EX 执行
```

然后讲清楚那个"承重"的设计：**stall 时是 `imem_addr` 退回 `if_addr_d`，不是 `pc_r` 后退**，
理由是若 `pc_r` 后退，连续两拍 stall 会让同一条指令被取两次，非幂等指令被重复执行
（历史上踩过这个 bug）。

**这段是论文的"深水区"，也是最容易区分"真做过"和"抄模板"的地方。** 一定要写，
而且要写清楚"为什么不能那么做"。

### 4.2 呈现方式的三个进阶建议

**(a) 用"对比"代替"罗列"。**

| 对比维度 | 本设计 | 基线（若可得） |
|---|---|---|
| 流水线级数 | 5 | 单周期（若你们保留了单周期版） |
| 分支惩罚 | **2 拍**（改造前 3 拍） | — |

| CoreMark/MHz | **2.611**（改造前 2.380） | 典型教科书 5 级无优化实现约 1.5~2.0 |

> 若无法给出可信基线，就**不要编**。可以改为"与设计目标对比"（27MHz 约束 vs 47.8MHz 可达）。
> 编造基线数据是学术不端，且很容易被评审问穿。

**(b) 用"瓶颈定位"体现深度。**
不要只说"2.611 CoreMark/MHz"，要说**这 2.611 是怎么被吃掉的、还能怎么提升**。
**这一项已经做完，而且已经闭环了一次**（详见 `doc/ila_analysis.md`；
测试台内置 `+PROF`，可一键复现）：

| 周期构成 | 拍数 | 占 CoreMark 计时区间（382,972 拍） |
|---|---|---|
| 有效执行（提交 288,056 条指令） | 288,056 | **75.2%** |
| 分支冲刷（37,098 次 × **2 拍**） | 74,196 | **19.4%** |
| load-use 停顿 | 20,720 | 5.4% |
| 多拍除法停顿 | 0 | 0% |

CPI = **1.3295**；理论天花板（两类损失全消除）= `10^6 / 288,056` = **3.472 CoreMark/MHz**。

**而且这里有一条完整的"优化闭环"叙事可以直接写：**

| 阶段 | 分支惩罚 | 计时区间 | CPI | CoreMark/MHz |
|---|---|---|---|---|
| 初始设计 | 3 拍 | 420,070 | 1.4583 | 2.380 |
| 取指重定向（已做，已验证） | **2 拍** | **382,972** | **1.3295** | **2.611** |
| 加分支预测（建议） | — | — | — | 待测 |

第一步的收益是**实测的、自洽闭合的**：`420,070 − 382,972 = 37,098`，
恰好等于冲刷次数（每次省 1 拍）；且 CRC 与 riscv-tests 结果不变。
**"我提出了瓶颈 → 我改了设计 → 我量化了收益 → 我验证了正确性"，
这比一开始就报一个 2.6 有说服力得多。**

剩下的瓶颈仍是分支冲刷（单项 19.4%，是 load-use 停顿的 3.6 倍），
优化优先级应排第一；而实测显示区域内**后向分支 90.8% 都跳转**，
静态"后向预测跳转"即可覆盖大部分，BHT 收益明确。

**(c) 每个实验都要写"怎么做的"，不只是"结果是什么"。**
例如 riscv-tests 的判定方式：
"`scripts/elf2mem.py` 把 ELF 拆成 hex，`sim/tb_riscv.v` 监控 core 对 `tohost` 的 store，
判定 PASS / FAIL / TIMEOUT"。**写出了判定机制，结果才可信。**

**要做的**：抓 CoreMark 主循环的一段时间窗波形，
标出①前递生效的拍 ②load-use 停顿拍 ③分支冲刷拍，
统计占比，配时空图分析。这一张图能同时支撑"验证深度""性能分析""工具使用"三个评分面。

### 5.3 【P1，高性价比】加 BHT 分支预测 —— 投入最小、收益最大

**当前状态**：分支惩罚固定 **2 拍**（取指重定向改造后从 3 拍降下来），**无任何预测**
（已确认 RTL 里没有 BTB/predict 相关逻辑，`ex_flush` 是无条件按"预测不跳"处理）。
而 CoreMark 是分支密集的负载 —— 实测分支冲刷仍占掉计时区间的 **19.4%**，
是单项最大的效率损失。

**为什么推荐 BHT 而不是 Cache**：
| 方案 | 资源投入 | 预期收益 | 风险 |
|---|---|---|---|
| **BHT（2 位饱和计数器，256 项）** | **< 50 LUT**（当前仅用 2316 LUT，占 1.45%，空间极充裕） | 吃掉大部分动态分支的 **2 拍**惩罚；把未命中率降到 10% 约可省 **6.7 万拍 ≈ 17.4%** | 低，且**不影响正确性**（预测错照常冲刷） |
| 2 路组相联 I/D Cache | 大量 BRAM/逻辑 | 本项目是**单周期 BRAM 访问**，本来就没缺失惩罚，Cache 收益有限 | 高；且 `fence.i` 必须从 NOP 升级为"冲刷 I-Cache"，否则 `fence_i` 会退化回 FAIL |

**注意 `plan.md` §0 把"2 路组相联 Cache"列为高阶加分项，但对你们当前的设计，
BHT 的性价比明显更高。** 理由：你们的存储器是行为级单周期 BRAM（`unified_mem`），
访存本来就 1 拍返回，没有 Cache 缺失可言，加 Cache 主要收益是"看起来做了高阶功能"；
而分支惩罚是**真实存在且可量化**的开销 —— 实测占掉 CoreMark 计时区间的 19.4%，
且最热的 `matrix_test` 内层循环里，12 条指令中有 2 拍全耗在回跳分支上。
更关键的是：**后向循环分支几乎是必然跳转的** —— 实测区域内后向分支 25,664 条中
**90.8% 都跳转**，用静态规则（"后向分支预测跳转"）都能拿到大部分收益，实现成本极低。

**关键约束**：加 BHT 后必须重跑回归，确认 `50/0/0` 不变、且 CoreMark 周期数**下降**
（注意此时周期数**应该**变化，属于"目的就是改变这一项"的例外，要按 §3 的方式更新基线）。
另外，**预测失败恢复路径必须验证正确** —— 这是唯一的正确性风险点。

**论文收益**：可以写出"优化前 2.380 → 取指重定向 2.611 → BHT 后 X"的**完整优化闭环**，
这比一开始就写一个数字有说服力得多。

### 5.4 【P1】补足"应用场景"的叙事

评分项第 4 条是"应用场景演示 —— CPU 要'有用'"。当前你们的演示是
"读按键 → 写 LED → 串口打印"，**功能上达标，但叙事上偏"实验板验证"而非"应用"**。

**建议**：选一个能自洽的轻量场景，把已有外设用出"应用感"。例如：
- **串口终端类**：把 SoC 做成一个命令解释器（读 UART → 解析 → 执行 → 回显），
  演示"通过串口控制 LED、读取计数器、跑基准测试" —— 硬件不变，叙事立刻升级
- **逻辑分析仪 / 采集卡**：用 GPIO 采样 + UART 上传 —— `plan.md` §0 已经点了这个方向
- **时序测量**：用 TIMER 寄存器做**片上性能测量**，串口回传 —— 这个你们其实已经具备
  （`0x7FF4` 有一个 32 位自由跑计数器）

> 关键不是做多复杂，而是**能讲清楚"这个 CPU 在这个场景里承担了什么角色、为什么需要它"**。

**重要提醒**：`doc/spec.md` 保留了一个**自修改代码的理论窗口**，建议在论文里主动写明：
"若软件改写自己取指窗口内的指令（恰为 store 之后第 3 条），那一拍发出的取指可能已读到旧值…
这是无 I-Cache/取指缓冲的简单核的固有性质，riscv-tests 未覆盖这种极端情况。"
**主动认账比被问出来强得多**，而且它反过来证明了你们对这个架构理解到位。

### 5.5 【P2】完善"稳定性"维度的证据

赛方关注稳定性，而稳定性最有力的证据是**重复性**：

1. **多 seed 时序收敛** —— 你们有 `multiseed_summary.csv`，**已达标**（Pass Rate 100%），
   论文里要明确写"多 seed 下 setup/hold 失败端点均为 0"
2. **长时间运行** —— CoreMark ITER=700 跑 10.89 秒、CRC 校验通过，

   可以做一个**连续收发压力测试**并统计错误率，这是很好的稳定性数据

### 5.6 【P2】代码规范与可复现性（已有优势，要充分展示）

你们这方面做得比多数队伍好，**要写进论文让评审看到**：

### 5.7 【P2】工程实用性的一个补强点（可选）

当前总线是**固定延迟、无握手**的（`mem_bus.v` 头注释明确写了"没有握手"），
且 `spec.md` §4.1 指出："将来若要做多拍内存（外挂 SRAM、慢速外设），
必须给总线加 `ready` 并接进冒险单元，不能靠事后打补丁。"

**如果想在"工程实用性"上再加分**，可以考虑：
- 给总线加一个 `ready` 握手信号（即使当前所有从设备都是 1 拍返回）
- 这样架构上**支持慢速外设**（如 SPI Flash、I2C 传感器），应用场景叙事会宽很多

但注意：**这会动到冒险单元，是承重改动**。如果时间紧张，建议只做 5.1~5.3，
把 `ready` 作为"后续工作"写在论文第 8 章即可 —— 你们 `spec.md` 里已经写好了这段论述，
直接引用就是很好的"架构前瞻性"论据。
