## 0. 先说结论：这篇论文的成败取决于三件事

**第一，你手里有一个被严重低估的数字 —— 而且它已经兑现成了分数。** 时序报告里写着：

```
Requested Frequency   85.0051 MHz     ← 板上系统时钟（板载 27MHz 晶振经 PLL 倍频，STATIC_RATIO0=13.5）
Estimated Frequency   87.0019 MHz     ← 双发射；单发射为 91.3993 MHz
Slack                 +0.270 ns       ← 双发射；单发射 +0.823 ns
Design Summary: All Constraints Met.   (TNS 0 / 失败端点 0)
```

你们的设计在 -6 速度等级下可达 **87.00 MHz（双发射）/ 91.40 MHz（单发射）**，
而板上时钟约束在 **85.0051 MHz** ——
**时序余量 2.3%**。"Estimated Frequency" 是工具给出的实际可达频率，
这是评审最能看懂的硬指标之一。

**但真正有冲击力的不是"余量大"，而是"余量能换分"。** 27 MHz 时代本设计可达 47.81 MHz、
余量 77% —— 听起来漂亮，本质却是**能力被平台固定时钟限制住、白白用不上**，
评审一句"那你为什么不跑快一点"就能问住。改用**板载 27 MHz 晶振 + Pango PLL 倍频**
之后，这个反问不成立了：付掉大部分余量（77% → 2.3%），
**换来实际得分 75.25 → 270.82 CoreMark（iterations/sec，较 27 MHz 本地板 75.25 累计 +260%）**。
拆成几步看（各代板测都在）：
① **27 → 45 MHz（纯提频）**：**同一份设计**（2.787 CoreMark/MHz）、只换时钟，
   75.25 → **125.40**，提升比例恰好等于时钟比 45.0005 ÷ 27 = **+66.7%**；
② **45 → 49.8927 MHz**：125.40 → **140.89**（**+12.36%**），这一步是**两笔账** ——
   时钟 +10.87%（49.8927 ÷ 45.0005）**乘上**效率 +1.33%（256 项 BHT 把每迭代
   358,846 压到 354,119）；③ 继续提到 **62.0309 → 85.0051 MHz**，得分 170.64 → 233.85（单发射）；
④ **85 MHz 上加顺序双发射**：效率 2.751 → **3.186**（+15.8%），得分 **233.85 → 270.82**。
执行效率与时钟无关（同一代设计跨时钟逐位不变），所以提频的提分**纯粹来自频率** ——
**这是一笔算得清、可验证的交易**。
（`270.82` 是 **2026-10-06 板上实测值**：`Total ticks 994,988,178` ÷ 85,005,100 = 11.7050 s；
日志 `doc/board/uart_20261006_162410.txt`；历史 49.89 MHz 版 140.89 = `588,890,651` ÷ 49,892,700 = 11.8031 s。）

## 2. 应重点突出的技术亮点

按"评审可感知度"排序，前三个不要省。

### 亮点 1：统一存储器架构 —— 这是你们最"有故事"的设计决策（强烈建议作为全文核心）

很多队伍会写"我实现了五级流水线 + 前递 + 停顿"，这是**教科书标准答案**，区分度低。
你们有一个真正做过取舍、且**有实测证据**的设计决策：

**问题**：哈佛结构（imem/dmem 两块独立 BRAM）下，`fence_i` 测试 TIMEOUT。
**根因分析**：不是"少实现一条指令"，而是**存储器结构决定的** ——
store 只写 dmem、取指只读 imem，写进代码区的指令永远进不了取指通路，
`fence.i` 实现成 NOP 也没用。
**决策**：合并为一块物理双端口 BRAM（A 口取指 / B 口访存），
软件层看到统一地址空间（modified-Harvard），核内取指/访存通路仍逻辑分离。
**收益**：① `fence_i` 从 TIMEOUT 转 PASS；② BRAM 用量减半（对"资源效率"评分项直接有利）；
③ 为后续 I/D Cache 留出干净的后备存储。
**证据**：整个回归里 **`fence_i` 是唯一变化的一项，其余 40 项逐项一致，CoreMark 周期一字不差**。

这个"问题→根因→决策→收益→无副作用验证"的完整闭环，
**是论文里最能体现工程能力的一段**。建议在摘要里就点出来，第 3/4 章展开。

写法上注意用对比结构，并诚实写出残留限制（见 §4.1）—— 主动写限制反而显得可信。

### 亮点 2：85.0051 MHz 板上时钟 + 顺序双发射 —— 把"用不上的时序余量"兑现成了分数

**这个亮点的叙事已经升级，务必按新口径写。** 旧的写法是
"约束 27 MHz、可达 47.81 MHz、余量 77%"—— 数字漂亮，但本质是
**能力被平台固定时钟限制住、余量白白浪费**。改用**板载 27 MHz 晶振 + Pango PLL 倍频**后，
把系统时钟真的提到了 45 → 49.8927 → 62.0309 → **85.0051 MHz**：

```
Requested Frequency   85.0051 MHz     ← 板上系统时钟（PLL 输出，STATIC_RATIO0=13.5）
Estimated Frequency   87.0019 MHz     ← 双发射（单发射 91.3993 MHz）
Slack                 +0.270 ns       ← 双发射余量 2.3%（单发射 +0.823 ns / 7.5%）
Design Summary: All Constraints Met.   (TNS 0 / 失败端点 0)
```

**收益可算**：执行效率与时钟无关、同一代设计跨时钟逐字不变，
所以实际得分随频率线性提升。各代板测各报一次：
**75.25（27 MHz）→ 125.40（45 MHz），纯提频 +66.7%**（比例恰好等于时钟比 45.0005 ÷ 27）；
**125.40 → 140.89（49.8927 MHz），+12.36%**（= 时钟 +10.87% × 效率 +1.33%，后者是 BHT）；
62.0309 MHz → **170.64**；85.0051 MHz 单发射 → **233.85**。
最新的 **233.85 → 270.82** 是**在 85 MHz 上又加了一层顺序双发射**（效率 2.751 → 3.186，+15.8%，时钟没动）。
（270.82 为 **2026-10-06 板上实测值**：`Total ticks 994,988,178` ÷ 85,005,100 = 11.7050 s；
历史 140.89 = `588,890,651` ÷ 49,892,700 = 11.8031 s。）
"性能"这一项里最有冲击力的表述不是"我有余量"，而是"**我把余量换成了分数**"。

要做到诚实、可追问，这段必须同时写清**代价**与**归因**：

- **代价是面积和 Fmax**：LUT 历代为 2,316（27 MHz）→ 3,030（45 MHz）→ 3,721（49.89 MHz）
  → 6,909（纯双发射那一代，全 SoC 含视频）→ **7,896（当前双发射 + 任务C `EARLY_LD`，I+D Cache 版实测）**；
  资源效率主口径（CoreMark/MHz 每千 LUT）
  1.127 → 0.920 → 0.759 …… → 0.461（纯双发射）→ **0.524（当前）**。
  **双发射明确是"用面积/Fmax 换效率"**：效率 2.751 → 3.186（+15.8%），
  但 Fmax 91.40 → 87.00（−4.8%）、LUT 4,377 → 6,909（+58%）、
  **CoreMark/LUTs 0.0534 → 0.0392（−27%）** —— **赛题三项指标 1 升 2 降**。
  任务C `EARLY_LD` 又进一步把效率提到 **4.139**（周期 −7.79%、**没有再增加面积**，
  面积增加主要来自 I/D Cache）；A1（乘法器 II=1）再提到 **4.304**（LUT +228）。
  报告里**三个口径都要给**，只给得分是选择性呈现。
  LUT 仍只占 4.94%，**资源本身不是瓶颈**。
- **归因要诚实**：估计可达频率 47.81 → 51.52 → 54.07 → 91.40（单发射）→ 87.00（双发射）MHz 的
  **每一步都是多件事的合并效果** —— 27 → 45 MHz 那步是 ① 约束提到 45 MHz、② 同批改了关键路径（`addr_result`）；
  49.89 / 62.03 / 85 MHz 那几步是 ① 提频、② 新增 BHT 表 / 两拍乘法器、③ 顶层改动。
  **都没有做"只改一处"的对照综合**，
  所以**不要声称"某个单一改动带来了多少 MHz"**（详见 §0 的归因说明）。
- **关键路径改了什么**（这一段是第 3 章的现成素材）：访存地址此前复用 `alu_result`，
  于是 PDS 把 **32×32 乘法器**拉进了"未对齐判据 → 异常 → `pc_r` 写使能"这条路径；
  但 load/store 的 `alu_op` **恒为 ADD**，而 mul 指令**从不访存** ——
  这条时序弧是**假的**。新增 `addr_result = alu_a + alu_b` 加法器即可把它切掉。
  "读时序报告 → 找出假路径 → 用加法器替换乘法器"是一个完整的优化闭环，
  比"我优化了关键路径"这种空话强得多。

下面三点回答的是"**为什么能跑这么快**"，仍要写 —— 只贴一张时序报告是不够的：

- **多拍迭代除法器**（`divider.v`，恢复余数法，每拍只做一次"移位 + 32 位比较/减法"）：
  关键路径约等于一个减法器。**如果用单拍组合除法，这条路径会直接拖垮 Fmax** ——
  这是一个明确的设计取舍，值得单独一段展开，并给出"若用组合除法，Fmax 会降到多少"的估算或实测。
- **写通路零寄存器 + 读数据在 MEM→WB 沿寄存**（`mem_bus.v` 头注释中的两条硬约束）：
  说明你们清楚"哪里能插寄存器、哪里不能"，并解释了为什么（冒险单元不知道内存有几拍）。
- **前递路径的优先级设计**（EX/MEM 优先于 MEM/WB，load 结果不从前递取）：
  关键路径在 EX 的 ALU/前递 mux，说明你们做过时序导向的设计。

**建议补一张表**：`约束频率 / 估计频率 / WNS / TNS / 失败端点 / hold slack`，
注明"多 seed"，并说明 hold 也收敛（失败端点 0；具体值以 `cpu_top_board.rtr` 为准）。
这体现你们做到了**签核级**的时序验证。

> 提示口径：**"约束 85.0051 MHz"指的是板上系统时钟（PLL 输出）这一级** ——
> `.fdc` 里那句 27 MHz 仍是**输入晶振**的频率，`Requested Frequency 85.0051 MHz`
> 是 PDS 从 PLL IP 推导出来的（`ipcore/pll/pll.idf`，`STATIC_RATIO0=13.5`）。引用时别把两者搞混。

### 亮点 3：验证体系的三层结构与"回归纪律"

这是**软性但高区分度**的亮点。你们有一套多数学生队伍不具备的工程习惯：

- **单元层**：ALU / 除法器 / UART FIFO / 译码器 / GPIO / UART RX 共 6 个测试台
- **集成层**：riscv-tests 全量 50 项 / CoreMark / demo 端到端 7 项
- **回归纪律**：改动 RTL 后，`49/1/0`（双发射、单发射都是 49/1/0）与 CoreMark 的
  **计时区间 232,345 拍**（当前默认 = 双发射 + `EARLY_LD` + A1；A1 前 241,633；`EARLY_LD=0` 为 252,730；单发射 `-Single` 为 303,140）**必须同时不变**，后者是"没碰坏流水线"最灵敏的探针

**特别值得写进论文的两件事**：

1. **把基线 ELF 入库**（`third_party/riscv-tests-elf/`）并说明理由：
   "上游 riscv-tests 会变，重新 clone 未必复现同一批二进制，基线漂移会让人误判成自己改坏了 CPU"。
   —— 这是**验证可复现性**思维，评审里懂行的人会认。
2. **`ma_data` 的"预期失败"标记**：明确写"这一项必须仍然 FAIL，

   —— 把"已知失败"转化为**回归哨兵**，这个思路非常专业。

### 亮点 4：CoreMark 口径的严谨推导

你们踩过一个坑并把它变成了论文素材：**ITER=1 的测试台总周期不是"每迭代成本"。**
它是仿真测试台的总周期，含约 110 万周期的一次性 UART 打印开销；而 CoreMark 自己的
`Total ticks` 计时在打印之前就停了、不含打印。两者口径混用会把 ITER 估小
（曾据此写成"ITER≈200 约 10s"，实测只有 3.11s，被判 invalid）。

论文里应写：**如何用两次实测解方程得出每迭代成本，并用它反推 ITER**：

```
改造前设计（分支惩罚 3 拍）：
  ITER=200 →  84,018,579 / 200 = 420,093 周期/迭代
  ITER=700 → 294,065,438 / 700 = 420,094 周期/迭代
  仿真（ITER=1）                 420,070 周期/迭代
  → 真机与仿真只差 0.0057% → 仿真模型可信 → 仿真数据可作论文依据
  → CoreMark/MHz = 1,000,000 / 420,094 ≈ 2.38

当前设计（顺序双发射 + 任务C `EARLY_LD` + A1 乘法器 II=1；分支惩罚 1 拍命中 / 2 拍未命中；ID 静态预测 + jal + 256 项 BHT + 两拍乘法器）：
  仿真（ITER=1）                 232,345 周期/迭代（A1 前 241,633；`EARLY_LD=0` 是 252,730；纯双发射 313,886；单发射 312,428）
  → CoreMark/MHz = 1,000,000 / 232,345 ≈ 4.304
  → ITER 必须重算：85.0051 MHz 下 ITER ≥ 10 × 85,005,100 / 232,345 ≈ 3659，取 4280（11.70 s）；A1 前用 4116（11.69797 s）
```

**两个独立结论都可以写进论文**：

1. **"0.0057% 的仿真-实测一致性"** 证明了行为级仿真模型的保真度，使后续所有仿真
   数据都有了背书。这一点很多队伍想不到，是很好的差异化内容。
2. **"ITER 必须跟着"每迭代周期"和"时钟"一起走"** 是一个真实的工程约束 —— 优化了流水线
   却没改 ITER，CoreMark 直接判 invalid。**而且两个方向都会踩这个坑**：
   流水线优化把每迭代周期压小要重算 ITER；**把时钟从 27 提到 45 MHz 同样会让
   ITER=820 失效（820 × 358,846 / 45 MHz = 6.54 s < 10 s）**，这一步已实踩。
   后来 45 → 49.8927 MHz 时 ITER=1500 虽然仍能过线
   （1500 × 354,119 / 49,892,700 = 10.65 s），但余量只剩约 6%，所以提到
   **1663（11.80 s，余量 18%）**。
   把"提速反而导致被测项失效"这个反直觉的点写出来，比单纯报数字有说服力。

> 仿真的 420,070 与 382,972 都是 2026-09-21 用测试台的 `+PROF` 直接读 CoreMark
> `Total ticks` 得到的，并用 `start_time`/`stop_time` 两次读 `0x7FF4` 的周期号交叉验证。
> 此前文档写的「仿真 ≈ 420,414」无法复现，已更正 —— 修正后一致性论证反而更强。

### 3.3 一个必须讲清楚的点：取指的两拍延迟与 stall 补偿

`spec.md` §3.1 里的稳态不变量写得很漂亮，**务必放进论文**：

```
imem_rd   = mem[pc_r - 4]      // 在途，下一拍进 IF/ID
if_id_pc  = pc_r - 8           // 正在 ID 译码
id_ex_pc  = pc_r - 12          // 正在 EX 执行
```

然后讲清楚那个"承重"的设计：**stall 时是 `imem_addr` 退回 `if_addr_d`，不是 `pc_r` 后退**，
理由是若 `pc_r` 后退，连续两拍 stall 会让同一条指令被取两次，非幂等指令被重复执行
（历史上踩过这个 bug）。

**这段是论文的"深水区"，也是最容易区分"真做过"和"抄模板"的地方。** 一定要写，
而且要写清楚"为什么不能那么做"。

| 方案 | 资源投入 | 实际收益 | 风险 |
|---|---|---|---|
| **BHT（2 位饱和计数器，256 项）** | 已计入当前占用（LUT 6,909 占 4.32%、分布式 RAM 含 BHT 表，空间仍极充裕） | **已兑现 4,727 拍 = 1.32%**（捕获率 56%）；扩表预计再 +1% | 低，且**不影响正确性**（预测错照常冲刷；riscv-tests 仍 `49/1/0`） |

**注意 `plan.md` §0 把"2 路组相联 Cache"列为高阶加分项，但对你们当前的设计，
它的性价比低。** 理由：你们的存储器是行为级单周期 BRAM（`unified_mem`），
访存本来就 1 拍返回，没有 Cache 缺失可言，加 Cache 主要收益是"看起来做了高阶功能"；
而分支是**真实存在且可量化**的开销 —— BHT 之前实测占掉 CoreMark 计时区间的 14.0%，
