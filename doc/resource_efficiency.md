## 2. 指标一：执行效率 CoreMark/MHz

### 2.1 赛题公式与等价换算

赛题式 (1)：`Score = CoreMark_Iterations / (Total_Time × Frequency)`

其中 `Frequency` 取 MHz、`Total_Time` 取秒，结果即 CoreMark/MHz。它与「每迭代周期数」是同一个量的两种写法：

```
CoreMark/MHz = 10^6 / 每迭代周期数
```

### 2.2 测量结果

| 口径 | 每迭代周期 | CoreMark/MHz | 来源 |
|---|---|---|---|
| **仿真（当前设计，主口径）** | **358,846** | **2.787** | `+PROF` 直接读 CoreMark `Total ticks`，2026-09-21 |
| 板上实测（改造前设计） | 294,065,438 / 700 = **420,094** | 2.380 | 远程平台 ITER=700 实测 |
| 板上实测（改造前，交叉验证） | 84,018,579 / 200 = **420,093** | 2.380 | 远程平台 ITER=200 实测 |
| 仿真（改造前设计） | **420,070** | 2.381 | `+PROF`，2026-09-21 |

改造前两个板级点独立测得 420,093 / 420,094，互差 1 个周期，口径自洽；
**板上与仿真差 24 周期 / 0.0057%** —— 行为级仿真模型与真实硬件的吻合度极高，
这一点本身就是结论：**后续所有仿真数据可以直接外推到板上**。

> ⚠️ **改造后的板上数值尚未复测。** 上面 2.787 CoreMark/MHz 是**仿真**口径
> （`+PROF` 读的是 CoreMark 自己的 `Total ticks`，与板上口径同源）。
> 按改造前 0.0057% 的板/仿真偏差推算，板上应约为 382,994 周期/迭代，
> 但**这是推算、不是实测** —— 需按 ITER=820 重新烧录后确认。

### 2.3 达到的实际得分

```
Score(27 MHz)   = 2.787 × 27      ≈  70.50 CoreMark（iterations/sec）
Score(47.81 MHz)= 2.787 × 47.8126 ≈ 124.84 CoreMark（若时序按更高频约束重跑）
```

赛题要求「运行时间不低于 10 秒」，当前设计取 **ITER=820**：
`770 × 358,846 / 27 MHz = 10.921 秒`，余量 9.2%。**满足要求。**

> ⚠️ **ITER 必须跟着每迭代周期走，改了流水线就要重算。**
> 改造前 420,094 周期/迭代时 ITER=700 正好 10.891 秒；优化后降到 358,846，
> **ITER=700 只剩 9.93 秒，会被判 invalid**。
> 换算办法：`ITER ≥ 10 × 27,000,000 / 每迭代周期`，取整后再留约 9% 余量。
> 每次动流水线后先跑 `run_coremark.ps1 -Iter 1` 读 `Total ticks`，再定 ITER。

> 注意口径陷阱：CoreMark 打印的 `Total time (secs): 10` 是整数截断，
> `Iterations/Sec: 70` 也是按截断后的 10 算的。

## 3. 指标二：时钟频率 Fmax

来源：`pds/RV32I_1/report_timing/cpu_top.rtr`（PDS 时序分析报告）。

| 项目 | 值 |
|---|---|
| Requested Frequency | 27.0000 MHz（周期 37.037 ns） |
| **Estimated Frequency** | **47.8126 MHz**（周期 20.9150 ns） |
| Setup Slack (Slow corner) | **+16.122 ns** |
| Setup Slack (Fast corner) | +23.677 ns |
| Hold Slack (Slow / Fast) | +0.147 ns / +0.100 ns |
| 结论 | `Design Summary : All Constraints Met.` |
| TNS / 失败端点 | 0.000 / 0 |
| 收敛率 | Pass Rate 100% / Convergence Rate 100% |

**关键表述**：当前 `.fdc` 把时钟约束在 27 MHz（远程平台限制），时序余量高达 **77%**。
工具估计该设计在 -6 速度等级下可达 **47.81 MHz**。

> 这是文档里此前被漏掉的数字。早先 README / spec / test_report 只写了
> 「27MHz 下 Setup +15.495ns」，把最有信息量的一半丢掉了 —— 应改为
> **「约束 27 MHz，可达 47.81 MHz，余量 77%」**。
>
> **顺带一个反直觉的实测**：取指重定向把 `ex_target` 直接接到 BRAM 地址口，
> 关键路径名义上变长（原来终止于 `pc_r` 的 D 端），但实测 Fmax 反而从
> 46.42 MHz 升到 **47.81 MHz**（slack +15.495 → +16.122 ns）。
> 因为同一次改动也删掉了 `ex_flush_d` 及其配套 mux，净效果是简化。
> **这说明关键路径必须重新综合才知道，不能靠推断** —— 改造前我在
> `doc/reports/2026-09-21_branch_opt_verify.md` 里预期它"大概率仍满足、
> 但需重测"，实测结果比预期好。

**Fmax 不是本设计的上限**，而是被平台时钟卡住。若换成本地盘古板并使用板载晶振
（或经 PLL 倍频），有实测提分空间。赛题该项要求「在满足时钟约束的前提下能达到的
最高工作频率」，报告里应同时给出「约束频率」与「估计可达频率」。

## 4. 指标三：资源效率 CoreMark/LUTs

### 4.1 资源占用明细

来源：`pds/RV32I_1/multiseed_summary.csv` · Device Map 段。

| 资源 | 用量 | 总量 | 精确占比 | PDS 显示 | 主要来源 |
|---|---|---|---|---|---|
| LUT | **2,316** | 159,800 | **1.45%** | 2% | 流水线控制、ALU、译码 |
| FF | 1,913 | 319,600 | 0.60% | 1% | 级间寄存器、FIFO |
| DRM（块 RAM） | 16 | 415 | 3.86% | 4% | 统一存储器（32KB 双端口 BRAM） |
| APM（DSP） | 11 | 740 | 1.49% | 2% | ALU 乘法器（M 扩展） |
| 分布式 RAM | 132 | 39,500 | 0.33% | 1% | 寄存器堆 32×32 |
| USCM | 1 | 32 | 3.13% | 4% | 时钟/全局资源 |
| HCKB / RCKB | 0 / 0 | 120 / 40 | 0 / 0 | 0% | 未使用 |

> PDS 的 `Utilization(%)` 列是向上取整的，所以 1.45% 显示成 2%。
> 报告里建议同时给出精确值与 PDS 显示值，避免被质疑「2% 是不是虚报」。
>
> 与改造前相比：LUT 2,301 → **2,316**（+15），FF 1,914 → **1,913**（−1）。
> **FF 少的那一个正好对应删掉的 `ex_flush_d` 触发器**，与改动完全吻合；
> LUT 增加来自新增的取指地址 mux（`ex_target` 旁路），属于正常映射结果。

### 4.2 资源效率计算

赛题未定义 `CoreMark/LUTs` 的精确口径（分子是归一化的 CoreMark/MHz 还是完整得分，
分母是 SoC 全部 LUT 还是仅 CPU 核）。**本设计同时给出两种口径，并声明主口径**。

| 口径 | 计算式 | 结果 |
|---|---|---|
| **A（主口径）**：归一化性能 / 千 LUT | 2.787 ÷ 2.316 | **1.127 CoreMark/MHz 每千 LUT** |
| B：完整得分 / 千 LUT（27 MHz） | 70.50 ÷ 2.316 | 30.44 CoreMark 每千 LUT |
| B′：完整得分 / 千 LUT（47.81 MHz） | 124.84 ÷ 2.316 | 53.90 CoreMark 每千 LUT |

**为什么用 A 作主口径**：它与赛题四.1(1) 的 CoreMark/MHz 同源，剔除了平台固定
频率这个不可控变量，能纯粹反映「单位逻辑资源换取的流水线效率」，也便于与其他
队伍在同一天平上比较。

**分母口径声明（诚实起见）**：分母 2,316 LUT 是**整个 SoC 顶层 `cpu_top`** 的用量，
即包含 UART、GPIO、总线与统一存储器的控制逻辑 —— 没有只算 CPU 核。
理由是提交物是整个 SoC，且这样取值对评委最保守（分母偏大、效率偏低）。

## 6. 优化空间（由本次剖析数据支撑，详见 `doc/ila_analysis.md`）

CoreMark 计时区间（**358,846** 周期，当前设计）内，**24.8% 的周期被浪费在
控制冒险与数据冒险上**：

| 来源 | 损失周期 | 占计时区间 |
|---|---|---|
| 分支/跳转（37,098 次；命中 1 拍 / 未命中 2 拍） | 50,070 | **14.0%** |
| load-use 停顿 | 20,720 | 5.8% |
| 除法停顿 | 0 | 0% |
| 合计 | 94,916 | **24.8%** |

理论上限（假设完全消除这两类损失）：`10^6 / 288,056 = 3.472 CoreMark/MHz`，
即当前 2.787 的理论天花板仍是 3.472。**分支已是占比最大的一项**（14.0%），
且资源余量充足（LUT 仅用 1.45%），有空间加分支预测器。

> **已经拿掉的一大块**：取指重定向把分支惩罚从 3 拍压到 2 拍，分支损失
> 111,294 → **74,196** 拍，计时区间 420,070 → 382,972（−8.83%）。
> **剩下能拿的主要是预测器** —— `+PROF` 的分支方向统计显示，区域内后向分支
> 25,664 条中 **90.8% 都跳转**，"后向分支预测跳转"这种简单静态规则就能覆盖
> 绝大部分循环回边，是下一步成本最低的方案。

## 8. 口径勘误（2026-09-21 上午，针对**改造前**的设计）

> ⚠️ **本节记录的是取指重定向改造【之前】的设计**，其中的 420,070 / 1,529,499
> 等数值在当前设计下已不适用 —— 当前数值见 §9。保留本节是为了留下口径推导过程。

既有文档（`doc/test_report_riscv-tests.md`、`CLAUDE.md`、`pds/README.md`、
`doc/base_task_status.md` 等）中「仿真 ≈ **420,414** 周期/迭代」这个数**无法复现**。

当时实测（ITER=1，`+PROF` 直接读取 CoreMark 的 `Total ticks`，并读数
start_time/stop_time 两次读 `0x7FF4` 的周期号交叉验证）：

```
start_time cycle : 21,533
stop_time  cycle : 441,603
region cycles    : 420,070   <- 与 CoreMark 自报 Total ticks 逐位一致
```

且那一次改动前后 `ITER=1` 的测试台总周期均为 **1,529,499**（逐位一致），
说明整条执行序列没有变化 —— 因此**改动前的仿真也必然是 420,070**，
文档里的 420,414 应属推算或笔误。

**已同步（2026-09-21）**：既有文档中「仿真 ≈ 420,414」已统一更正为
「仿真 **420,070**（ITER=1，CoreMark 计时区间实测）」，涉及
`CLAUDE.md`、`doc/base_task_status.md`、`doc/test_report_riscv-tests.md`、
`pds/README.md`、`doc/paper/*.md`。修正后板上/仿真差值为 **0.0057%**（原写 0.08%），
论证反而更强。

同一批次还更正了另一处结论：**分支惩罚是 3 拍而非 2 拍**（依据见 `doc/spec.md` §3.1）。
但这条更正**随后又被设计改动取代** —— 见 §9。

> 注意：「每迭代周期」不等于「ITER=1 的测试台总周期」——后者含约 108 万拍的
> 一次性 UART 打印开销。这个区分始终成立，只是两个数值都随改造变了。

## 9. 2026-09-21「取指重定向」改造后的数据更新

改造内容（`rtl/core/core.v`）：**删除 `ex_flush_d`，改为在冲刷当拍就把跳转目标地址
旁路给取指端**。因为取指是同步读 BRAM（1 拍延迟），提前一拍发目标地址，目标指令
就能早 1 拍进 IF/ID。第二轮又在 ID 级加了静态后向预测，命中时不再等 EX 解析。
分支惩罚 3 拍 → 2 拍 → **1 拍**。

本文档第 0–6 节的数据已按**第三轮优化后**的设计更新，三轮演进对照如下：

| 指标 | 基线 | 阶段 1（取指重定向） | **阶段 2（ID 级预测）** | 累计变化 |
|---|---|---|---|---|
| 每迭代周期 | 420,070 | 382,972 | **358,846** | **−14.6%** |
| CoreMark/MHz | 2.380 | 2.611 | **2.787** | **+17.1%** |
| 分支惩罚 | 3 拍 | 2 拍 | **1 拍**（命中）/ 2 拍（未命中） | −2 拍 |
| 分支损失占计时区间 | 26.5% | 19.4% | **14.0%** | −12.5 pp |
| LUT | 2,301 | **2,316** | +15 |
| FF | 1,914 | **1,913** | −1 |
| Estimated Fmax | 46.4209 MHz | **47.8126 MHz** | +3.0% |
| Setup slack | +15.495 ns | **+16.122 ns** | +0.63 ns |
| 资源效率（主口径） | 1.035 | **1.127** | +8.9% |

**数据来源**：
- 资源与时序取自 **2026-09-21 14:08** 的 PDS 综合/布线/时序报告，与改造后的 RTL 同批
  （`pds/RV32I_1/multiseed_summary.csv`、`report_timing/cpu_top.rtr`）
- 性能与损失构成取自 `+PROF` 仿真（CoreMark 计时区间 358,846 拍）
- 完整验证记录（正确性 49/1/0、CRC 逐位一致、自洽校验）见
  `doc/reports/2026-09-21_branch_opt_verify.md`

> ⚠️ **两条纪律**
> 1. **板上数值尚未复测。** 2.787 是仿真口径；板上需按 ITER=820 重烧后确认。
> 2. **读 PDS 报告前先确认它与当前 RTL 同批。** 改造前的备份在
>    `report_timing/bak/`、`synthesize/bak/`，别把两批数据混用 ——
>    这也是本次差点踩的坑：`bak/` 里的 `snr.db`/`rtr.db` 仍含已删除的 `ex_flush_d`。
