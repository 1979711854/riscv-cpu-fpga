# I/D Cache 实现与评估（2026-10-11）

> 任务书 v7 §5.A 的 A.2/A.3。**结论：两路组相联 I/D Cache 已实现、功能正确、
> 命中率 98~99.8%，但因为后端是单周期片内 BRAM，它是负收益，所以默认关闭。**
> 本文是答辩口径的证据来源。

## 1. 结构

```
                ┌── I-Cache 16KB（A1 取指口，2 路）── 命中 1 拍 / 缺失 2 拍
core ──取指口 ──┤
                └── A2 取指口【不缓存】，直通 unified_mem（恒 1 拍）
                ┌── D-Cache 16KB（访存口，2 路）──── 命中 1 拍 / 缺失 2 拍
core ──访存口 ──┤
                └── 写通路【不缓存】，组合直进 BRAM（写通、零寄存器）
```

**地址切片**（字地址 14 位）：`index = word[10:0]`（2048 组）、`tag = word[13:11]`（3 位）。
tag 只有 3 位 —— 因为地址空间总共只有 64 KB。

**存储**：
- **tag 阵列**：`{valid, recent, tag[2:0]}` 每项 5 位，**组合读**（LUTRAM）。
- **数据阵列**：两路各 2048×32，**同步读 1 拍**（BRAM，与 `unified_mem` 同相）。

**替换**：每项带 1 位 `recent` 做 NRU 近似 LRU。

**写策略**：写通 + 写命中更新 + 缺失不分配。store 照旧组合打进 BRAM。

---

## 2. [重点] 为什么 tag 必须组合读

访存契约是「T 拍给地址、**T+1 拍** `mem_rdata` 有效」，而 `mem_ready` 是 **T 拍的组合信号**。
若 tag 用同步读，缺失要到 T+1 才知道 —— 那时 WB 级**已经把错数据写进寄存器堆了**
（`load_src = mem_rdata` 是组合的，寄存器堆在 T+1→T+2 沿写）。没有任何停顿机制能救。

所以命中/缺失**必须在 T 拍当拍**判定 ⇒ tag 阵列必须组合读。这也正是 A.1 假路径探针
要量的那一段（结果：85 MHz 下吃掉余量的 86%，见 `2026-10-11_A1_cache_tag_probe.md`）。

缺失只花 1 拍（共 2 拍完成），关键事实是：**停顿期间访存地址被冻住，后端 BRAM
下一拍的 `ram_rdata` 恰好就是本条 load 那个字**，所以数据天然对齐，不需要额外的
回填等待。

---

## 3. [重点] I-Cache 特有的两个坑（都实测踩到）

### 3.1 停顿信号不能组合去压 `mem_ready` —— 那是真组合环

取指口**没有就绪信号**（`core.v` 的契约写死"地址发出后恰好 1 拍数据有效"）。加一根
`imem_ready` 要牵连 `core.v` 里十来处承重逻辑（`if_id_valid` 气泡判定、`if_addr_d`
退回、`p_redirect` 门控、IF/ID 保持、重定向冲刷拍数假设……），所以选择**借 `mem_ready`
当取指停顿** —— core 的 freeze 通路本来就把"重读同一个地址"做得严丝合缝，`core.v` 零改动。

但取指地址**就是 `fetch_addr` 本身**，而 `fetch_addr` 的组合 mux 里有一项是 `!mem_ready_int`：

```
hit_any(fetch_addr) → stall → mem_ready → fetch_addr → hit_any(fetch_addr)   ← 真组合环
```

**破法：stall 先过一级寄存器。** 代价是停顿比缺失晚一拍，一次缺失花 2 拍（D 侧是 1 拍）。

### 3.2 回填的 index 必须用"缺失那一下的快照"

停顿那一拍 `fetch_addr` 虽然被冻在 `if_addr_d`，但 **`trap` / `ex_flush` / `ex_mispred`
优先级更高、且不受 `mem_ready` 门控** —— 那一拍 `imem_addr` 可能已经跳到重定向目标上了。
若回填直接用当拍的 `idx`，就会"把 A 的数据写进目标那一行的索引"，**缓存被静默写坏**。

实测症状：CoreMark 死循环在 `pc=0x84/0x88`，**而 riscv-tests 49/1/0 全过**
（小测试的代码短、撞不到这个边角，这是个只有大程序才暴露的坑）。

### 3.3 读数据只有"上一拍真的命中"才用阵列

复位清扫期间缓存恒不命中，阵列还是未初始化的 **X**；用它会把 X 送进
`imem_rd → IF/ID → PC`（实测 `pc` 变 `0xxxxxxxxx`，整颗 CPU 死掉）。
一律回退后端 BRAM —— 而 BRAM 本来每个周期就在读同一个地址，回退零代价。

## 5. [重点] 答辩口径（A.3）

> "我们**实现并评估**了 2 路组相联 I/D Cache（各 16 KB，tag 组合读 + 数据同步读，
> NRU 替换，写通 + 写命中更新）。
> 实测命中率 D 98.47% / I 99.82%，但**计时区间只掉 0.19% / 0.64% —— 命中 1 拍的
> 收益是零**（后端本来就是单周期片内 BRAM，没有慢速后端可藏），缺失反而要停 1~2 拍。
> 所以它是**负收益**，**默认关闭**，跑分一律用关的配置报 324.5。
> 这是**评估后的架构判断**，不是没做。"

配套证据：命中/缺失计数器（只读 MMIO `0x8000_0018`~`0x24`）+ 串口上报
（`core_portme.c` 的 `portable_fini`，在计时区间之外）。

**反例对照**：参考数据里那份用了 Cache 的设计，D-Cache 缺失率是 **0.000%**
（5,135 次 / 5.66 亿次访问）—— 也说明 Cache 对他们的分数没有贡献。

## 6. 未覆盖 / 局限（如实记录，**别对外说成已验证**）

- **AMO 与 Cache 的组合没有专门测试**：`tb_amo_cpu` 还没转 tohost（见
  `2026-10-10_design_app_side.md` §6 的"覆盖 A"），所以"AMO 与 D-Cache 共存正确"
  目前只有推理、没有实测。CoreMark 不用 AMO，所以跑分不受影响。
- **写分配策略放弃了**（缺失不分配 + 写命中更新）：换来的是 store 仍然 1 拍完成、
  `st_ld` / `fence.i`（自改码）语义与不开 Cache 时**完全一致**。
- **I-Cache 不缓存 A2 取指口**（`imem_addr2`）：换来的是不引入额外停顿、面积省一半。
- **合成时间**：见 §7 —— 组合读 tag 阵列（2048 项 × 2 路 × 2 个 Cache）让 PDS 的
  DFF-inference 明显变慢，这是"真做 Cache"的工程代价之一，如实记录。

## 7. [重点] 综合时序：85 MHz 下塞不进任何形态的 Cache（四个配置实测）

同一份 RTL、同样的 85.0051 MHz 约束，只改 Cache 开关与容量，逐个 P&R（8-seed 多种子）：

| 配置 | CPU 域 slack | Estimated | 失败端点 | 结论 |
|---|---|---|---|---|
| **完全不开**（生产口径） | **+0.544 ns** | 89.13 MHz | 0 | ✓ 收敛，就是 324.5 那版 |
| 只开 I-Cache（16 KB） | **−1.128 ns** | 77.57 MHz | — | ✗ |
| I + D（16 KB） | **−1.586 ns** | 74.91 MHz | 289 | ✗ |
| **I + D（缩到 4 KB）** | **−1.092 ns** | ~78 MHz | — | ✗（面积砍 75%，只换回 0.5 ns） |

### 7.1 两个反直觉的实测结论

**(a) "做小"只解决三分之一。**
16 KB → 4 KB（面积砍 75%）把 slack 从 −1.586 拉回 −1.092，**剩下的 −1.09 ns 是逻辑深度
本身**：`BRAM 输出 → tag 比较 → way mux → mem_rdata`，缩面积缩不掉。

**(b) 代价远超逻辑深度，主要来自"面积引起的全局布局扰动"。**
不含 Cache 时余量 +0.544 ns，只加一个 16 KB I-Cache 就掉到 −1.128 ns（**掉 1.67 ns**）。
A.1 的假路径探针当时只量到 0.452 ns，并在报告里就写了这个现象：
"加 253 LUT 后 placer 全局重排，老路径布线变差"。

### 7.2 [重点] 降频演示这条路**是坏的**，别再试

想"降频让带 Cache 的位流收敛"，实测发现**行不通**：

| 请求频率 | `RATIO0` | Estimated | slack |
|---|---|---|---|
| 85.0051 MHz | 13.5 | 74.91 MHz | −1.586 |
| 71.7206 MHz | 16.0 | **61.92 MHz** | **−2.208** |

**约束放松，PDS 就偷懒** —— 请求 71.72 MHz，它反而只做出 61.92 MHz，slack 比请求 85 时**还差**。
这就是 `CLAUDE.md` 约定 25 记的那条（"调低约束它也偷懒"）在**带 Cache 的设计上重新发作**。
沿途改过的常量（`UART_DIV` 738→623、`EE_TICKS_PER_SEC`、`expectLines` 17104→17106）
**已全部还原**。

### 7.2b [重点] 判时序时踩的坑：`report_timing/` 里可能是【旧文件】

收尾时读到 `report_timing/cpu_top_board.rtr` 显示 **−0.645 ns**，一度以为"Cache 关掉了
还退化 1.2 ns"。**是误判** —— 那是 `report_timing/` 目录里**上一次**留下的文件。

**正确判法（本次用的）**：拿【同一条命令】分别跑基线 RTL 与改动后 RTL，
各读 `place_route/seed_<best>/cpu_top_board.rtr`：

| RTL | 最优 seed 的最终 slack |
|---|---|
| 基线（commit `ede2d3b`） | +0.544 ns / 89.127 MHz |
| 本会话（Cache 全关） | **+0.578 ns / 89.398 MHz** |

**⇒ 没有退化。**（旁证：两者的 **8-seed `Setup(Slow)` 值在同一区间** —— 基线 −1.07~−1.51、
本会话 −1.08~−1.41，**所以那个 seed 指标根本不能用来判退化**，它只是布线前的参考。）

### 7.3 根因与结论

根因是任务书 v7 §5.A.1 早就写死的那一句：**后端是单周期片内 BRAM，命中 1 拍 = 零收益**。
Cache 的全部作用就是往关键路径上加"tag 比较 + way mux"，什么也换不回来。

**⇒ 85 MHz 下不打开，是正确的架构判断；打开反而是纯亏。**
（旁证：参考设计自己的日志写着 D-Cache 缺失率 **0.000%**、5,136 次缺失 / 5.66 亿次访问
—— 那个 Cache 对他们也没有任何贡献。）

### 7.4 以后要"开了还能收敛"的唯一可行路径

**把访存地址计算提前到 EX 级**（= 任务书 v7 §4 的**任务 C：消除 load-use 停顿**）。
地址提前一拍 → tag 检查才有地方藏。但：

> [!] **这是假说，不是结论。** 任务 C 本身也要吃时序余量（§5.C 原话："直接吃那 4.6%"），
> 所以更可能是"C 拿到 +10.4% 的**周期**收益，但主频掉一档，Cache 依然塞不进"。
> **必须先按 §5.C 的判据做假路径评估**（插一级等价逻辑综合一次，半天），别直接开工。
> 而且排任务 C 的理由应该是 **它值 +10.4%（真涨分）**，不是"为了给 Cache 腾地方"（Cache 值 0 分）。
