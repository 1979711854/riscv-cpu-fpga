## 2. 任务清单

### T1 · HARD 档提速【P0，最优先】

**现象**：HARD(6 层) 一手要 **2.8 ~ 11.9 秒**，玩家以为板子死了。

**已有的受控测量**（`scripts/gomoku/measure_ai.c`，自对弈到采样点、在**同一局面**上跑三档）：

| 盘上子数 | NORMAL 节点 | HARD 节点 | HARD 板上约 |
|---|---|---|---|
| 2（开局）| 1355 | 14535 | 8.7 s |
| 10 | 1720 | 17074 | 10.2 s |
| **16** | 536 | **19854** | **11.9 s** |
| 22 | 1379 | 17372 | 10.4 s |
| 40（残局）| 382 | 4665 | 2.8 s |

板上秒数 = 节点数 × 0.6 ms（板上实测系数）。

**[重点] 两条已经排除的路，别再走一遍：**

1. **加开局库 —— 没用。** HARD 是**全程都慢**，最贵的是**中盘**（16~22 子），不是开局。
   开局库只能让第一手不慢。
2. **调小 `AI_NODE_BUDGET` —— 没用。** HARD 开局那手是 24,246 节点 / 14.5 秒，
   而预算是 40,000 —— **它是在预算内正常搜完的，不是被截断**。
   把预算压到 24,000 以下，第 6 层会被中途掐断、退回第 4 层的结果 →
   **HARD 就等于 NORMAL 了，只是白等几秒。**

**唯一对症的方向**：瓶颈是"6 层 × 宽度 14"的节点数，而宽度是**全局常量**
`AI_WIDTH`（`ai.c`），所有档位共用 —— 现在**没有可用的旋钮**。
**做法：把搜索宽度改成按档位传下去**（EASY/NORMAL 保持 14，HARD 调窄，比如 8）。

**验收（两条都要满足，缺一不可）**：

1. `measure_ai.exe` 显示 **HARD 在所有阶段的节点数 ≤ 约 4000**（板上 ≤ 2.5 s）
2. **HARD 的棋力仍然强于 NORMAL** —— `test_ai.c` 里的棋力自对弈测试必须过

> [!] 宽度降了棋力一定掉。**必须用自对弈证明"HARD 仍然 > NORMAL"**，
> 否则这个档位就没有存在意义 —— 那就该直接删掉 HARD，而不是留一个假的。

### T2 · HUD（屏幕上显示文字）【P0】

**现状**：屏幕上**只有棋盘和光标**。没有"轮到谁"、没有难度、没有胜负提示。
玩家得自己看棋子颜色判断轮次。

**交接文档里写着"v1 刻意不做文字，省 10KB 字库"—— 这个顾虑现在已经不成立了。**
合并视频子系统之后，图块区的空间是：

| 项 | 值 |
|---|---|
| 屏幕 | 640×480 = **40×30 个 16×16 图块** |
| 图块区 | 64KB = **256 块** |
| 五子棋已用 | **36 块**（tile 0..35，见 `TILE_OF`）|
| **空着** | **220 块 / 56KB** |
| 棋盘占位 | 列 12..26、行 7..21（`BOARD_COL0=12`、`BOARD_ROW0=7`）|
| **上下留白** | **行 0..6（7 行）与行 22..29（8 行）** |
| 调色板 | 256 项只用了 **7** 项（`P_BG/P_LINE/P_BLACK/P_BLACK_HI/P_WHITE/P_WHITE_EDGE/P_CURSOR`）|

**所以一套 16×16 ASCII 字库（95 个字 = 95 块 = 24KB）放得下，还很宽松。**

**建议内容**（不重要，可自定）：
* 顶部：`TURN: BLACK` / `LEVEL: NORMAL`
* 底部：`AI: nodes 1287  depth 4  666ms` ← **这一行最有价值**，
  它把 CPU 的工作量直接摆给评委看
* 胜负：`BLACK WINS`

**渲染方式**：现有渲染层是 tile 制（查名表 `VIDEO_NT + row*256 + col` 得图块号，
再查图块表 `VIDEO_PAT + tile*256 + py*16 + px` 得调色板索引）。
**字库照 `gen_tiles.py` 的模式生成**（它是 Python 生成器，自带 ASCII 预览，见其文件头）。
**别手写像素数据。**

**验收**：`run_sim.ps1` 通过 + 上板能看到字 + 串口有对应的文本回显（见 §4 纪律）。

## 3. 技术约束（写代码前必须知道）

1. **总内存 32KB**（统一 BRAM，指令+数据共用）。当前固件静态占用 19,287 字节，栈余量 9,385。
   **AI 的递归搜索栈在里面** —— 加功能要盯着这个数（`build.ps1` 会打印）。
2. **显存是【字节使能 32 位口】**，`sb/sh/sw` 都能逐字节写，**不需要读-改-写**。
3. **`board.c` / `ai.c` 是"一份源码两处用"**：同一份文件既编进 x86 单测、又编进 RV32 固件。
   **所以它们不许依赖 libc / 动态内存 / 浮点 / 任何硬件头**（见 `board.h` 文件头）。
   要加平台相关的东西，加到 `hw_port.c` 或 `main.c`。
4. **帧同步**：主循环每帧等一次 vblank。改显存要在 vblank 里做，否则会撕裂。
5. **串口是当前唯一的观察窗口**（上板侧还没有显示器）。

## 4. [!] 串口可观测性 —— 这是硬纪律

2026-10-04 一天里，**因为"板子做了但不说"连踩 4 次**（提交 `dd4eecd` 修了 5 处）。
每一条的表现都是"看起来像死机/按键没生效"，排查起来极费时间。

**规则：任何玩家可感知的动作，串口都必须有对应输出。**

| 动作 | 必须输出 |
|---|---|
| 开局 | 一串完整棋盘（**注意开局棋子数是 0，不算"变化"**，得单独触发）|
| 移动光标 | `cursor=H8` |
| 切难度 | `level=2 HARD (6-ply)` |
| 落子失败（该点有子）| `occupied -- move the cursor and try again` |
| AI 开始思考 | `AI thinking (HARD 6-ply)...` ← **AI 是同步阻塞跑的，不喊这一声就是十几秒静默** |
| AI 落子 | `AI moved, nodes=… depth=… t=…ms` |

> [!] 加提示时要**先判断再打**。踩过的坑：把 "AI thinking..." 挂在"长按"上，
> 结果往已有子的点长按会打出这句话却**没有下文**（落子失败、AI 根本没跑）——
> 比不打还糟，直接被误判成"AI 卡死"。

## 5. 坑（全是踩过的，按踩到的频率排）

1. **`expectLines` 守卫会拦你，那是守卫在工作。** 改固件导致 `mem.hex` 字数变了，
   `build_bitstream.ps1` 会 `exit 1` 并打印期望值。确认是编译期常量变了就更新那个数字。
2. **[!] 任何一次综合都会覆盖 `generate_bitstream\cpu_top_board.sbit`**，
   而**所有位流文件名和字节数完全一样**（9,188,552）。别靠文件名猜，记 md5。
3. **改完固件必须跑 `run_test.ps1`。** 仿真能过不代表板上能过。
4. **别碰 `rtl/`。** 五子棋是纯固件。改了 RTL 要走 CPU 全量回归
   （riscv-tests 49 PASS / 1 FAIL / 0 TIMEOUT + CoreMark 363,515 拍）。
5. **[!] 仿真口径是 27 MHz，`run_sim.ps1` 写死了 `-Sim`**（按键阈值 1ms/5ms、AI 用 EASY）。
   板上口径喂给仿真会等到超时 —— **这不是 bug**。
6. **时钟 85.0051 MHz**：`UART_DIV=738`、`EE_TICKS_PER_SEC=85005100`。
   毫秒换算走 `CPU_HZ/1000`（自动跟着走，**别写死常数**）。
7. **命令都是单个字符**（CLI 里）。列字母是 A–O，`L2` 既是合法落子又像命令，语法上没法区分。

## 7. 背景：为什么这个应用场景值得做

评审看重的是**设计复杂度**，不是题材新颖度。而这里底下是：

* 一颗**自研的 RV32IM 五级流水线 CPU**（85 MHz、动态分支预测、完整异常中断）
* 一套**自研的 480p60 tile PPU + TMDS 串行器**（HDMI 输出）
* 一块 **32KB 的内存**里塞下了规则、搜索 AI、渲染与状态机
* 因为装不下帧缓冲，**渲染是实时 tile 合成的**

HUD 那行 `AI: nodes 1287 depth 4 666ms` 之所以重要 —— 它把上面这些**摆到屏幕上给评委看**。
**深度是看不见的，得让它可见。**
