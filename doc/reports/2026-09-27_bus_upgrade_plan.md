## 0. 一页速览

**一句话结论：第一步不是"选哪个协议"，而是"让 CPU 能等"。**

APB / AHB / AXI 三个协议，无论选哪个，**都要求主机能在一次传输没完成时挂住不动**。
我们现在的访存通路是"固定 1 拍、无 ready"，**CPU 根本不会等** ——
在这个能力补上之前，接任何标准总线都是空谈。

## 1. 为什么第一步是加"访存等待"而不是选协议

### 1.1 三个协议的时序本质：都要等

| 协议 | 一次传输最少几拍 | 要握手吗 | 主机必须具备的能力 |
|---|---|---|---|
| **APB** | **2 拍**（SETUP 拍 `PSEL=1,PENABLE=0`；ACCESS 拍 `PSEL=1,PENABLE=1`）| **要 `PREADY`** | 在 ACCESS 拍 `PREADY=0` 时**挂住不动**，可挂任意多拍 |
| **AHB** | ≥2 拍（地址拍 + 数据拍，支持流水/突发）| **要 `HREADY`** | 在 `HREADY=0` 时挂住，且要能处理流水线的在途请求 |
| **AXI** | ≥1 拍，但要 `valid/ready` 对握 | **五通道各自握手**（AW/W/B/AR/R）| 每个通道都要能"我拉高 valid 一直等你 ready"，或"我 ready 低就表示不收" |

结论：**三个协议的共同点不是"多少拍"，而是"主机必须能被从设备拖住"。**
协议选型是第二步的事；第一步是让主机具备"被拖住"的能力。

### 1.2 我们现在的通路，是被写死成"不可能等"的

必须读一遍 `rtl/bus/mem_bus.v` 的**文件头注释**（第 3~25 行），那里写死了两条承重约束。
其中这一条直接判了"直接接 AXI/APB"的死刑：

> 2) 读选择位与读数据都必须在 MEM→WB 那个沿寄存（`rsel_d` 一族）。不能给
>    读通路再插一级寄存器，否则读数据被推到 T+2，而 WB 在 T+1 采样，
>    **没有任何 stall 机制能救（冒险单元不知道内存有几拍）**。
>    所有地址源（RAM / 兼容区 / 外设区）一律 1 拍延迟，不搞特例。

把这句话翻译成工程语言：

* **不是"我们没有 ready 线"这么简单，而是"整条流水线没有'等'这个概念"。**
  冒险单元只有三种停顿源：load-use `stall`、`div_stall`、分支/异常重定向，
  它们都假设"访存恒 1 拍"。
* 一旦某个从设备要 3 拍才给数据，而 CPU 仍然按 1 拍推进 MEM/WB，
  **`mem_wb_*` 会在这 3 拍里反复采样同一个 `mem_rdata`**，
  采到的是等待期间的任意中间值 —— 而且**没有任何现成的机制会阻止它**。

同一件事，`doc/spec.md` §4.1 末尾已经预先写好了结论：

> 将来若要做多拍内存（外挂 SRAM、慢速外设），**必须给总线加 `ready` 并接进冒险单元**，
> 不能靠事后打补丁。

`rtl/core/core.v` 第 7~10 行的取指口契约同理：

> 契约：同步读、恰好 1 拍延迟（第 T 拍给地址 → 第 T+1 拍出数据）、只读，
> 且【不做任何仲裁/冲突检测】。本模块的 stall/flush 补偿逻辑依赖 A 口
> 每拍都能独立工作，加仲裁会直接破坏取指时序。

> **[重点] 这三处（`mem_bus.v` 头注释 / `spec.md` §4.1 / `core.v` 取指口注释）
> 是同一件事的三个视角。读完它们，本章的结论就不需要论证了。**

## 2. 现状：我们的总线是什么（以及它为什么现在够用）

### 2.1 特征表

来源：`rtl/bus/mem_bus.v`、`rtl/bus/addr_map.vh`、`rtl/top/cpu_top.v`

| 维度 | 我们的做法 | 后果 |
|---|---|---|
| **主机数** | **1**（只有 core 的 MEM 级）| 加不了 DMA、加不了第二个主机；任何"另一个读写者"都得先经过 CPU |
| **握手** | **无**。core 与 mem_bus 之间是**固定延迟**协议：第 T 拍给 `mem_addr`，第 T+1 拍 `mem_rdata` 必定有效 | **多拍设备接不进来**（这正是 §1 的结论）|
| **从设备接口** | **自定义裸线**：`gpio_we` / `uart_tx_we` / `uart_rx_ack` / `periph_wdata` + 读回 mux | 第三方 IP **不能直接挂**，每个都要手写一层胶合（把 APB/AXI 事务拆成这些裸线）|
| **从设备选通语义** | **电平敏感**：`uart_tx_we` 直接接 `uart_tx.tx_start`，`uart_rx_ack` 直接接 `uart_rx` 的弹出使能 | 现在**恰好**正确，因为 `mem_we`/`mem_re` 天然只高 1 拍。**一旦能等待，这个前提就没了** —— 见 §3.3 |
| **取指口** | **直通**统一存储器的 A 口，不做任何仲裁/缓冲（`mem_bus.v` 第 30~32 行）| 与访存口共用一块 BRAM 的两个端口，**天然双口、零冲突**。想加仲裁 = 破坏取指时序（`core.v` 注释原话）|
| **地址译码** | **单点**：全部收敛在 `mem_bus.v`，顶层 `cpu_top.v` 只做连线；映射表在 `addr_map.vh` | 这个是好设计，**不要动** |
| **中断** | `irq_timer`（CLINT 电平比较器，`mem_bus.v` 内）| 与本次改造无关，但别顺手把它改成脉冲（见 `mem_bus.v` 第 72~85 行的理由）|

### 2.2 [重点] 语气：这是"为了扩展而改"，不是"现在很烂"

**这套总线对当前的设备集合（1 拍 BRAM + 几个寄存器型外设）是最优解**：

* **1 拍 BRAM**：片上双端口，读恒定 1 拍命中，**没有缺失惩罚**——
  没有任何延迟需要被握手隐藏。
* **寄存器型外设**（GPIO / UART / CLINT）：写进去就生效，读回来就有效，同样是 1 拍。
* **没有握手 = 没有握手开销**：省掉的正是"拉 valid、等 ready、判断"这些状态机节拍
  与它们带来的组合路径。**CoreMark 的 CPI 能压到 1.2294，这套零开销总线是贡献者之一。**
* 资源占用：LUT **3,721**（占器件 **2.3%**）、FF **2,441**、DRM **16**、APM **11**。
  总线本身几乎不占面积 —— **面积不是改造的动机，能力才是**。

> 所以给队友定调：**第 0 步的目标不是"修好一个坏东西"，而是"补上一个扩展所必需的能力"，
> 而且补的过程中必须做到"什么都不变"（见 §3.4 的验收判据）。**

## 3. 第 0 步【P0】给 CPU 加 `mem_ready` / `mem_req`

**这是全篇最重要的一节。** 目标：让 MEM 级能停住，且**在不停的时候逐位等于现在的行为**。

> **[!] 拿到代码后先做一件事**：如果工作区里**已经有一份别人写的实现**（可能是未提交的
> 快照），**不要默认它已经对了** —— 按 §3.3 的五条风险逐项核对，
> 尤其是第 1 条（取指地址补偿）和第 2 条（外设选通），
> 这两条**在 `mem_ready` 恒 1 的回归里根本测不出来**，只有 `+MEMWAIT` 才暴露。
> 本文是这份实现**必须满足的规格**，不是它的说明书。

### 3.1 接口约定（先定死，再动手）

新增两个信号，都在 `core` 与 `mem_bus`（或未来的桥）之间：

| 信号 | 方向 | 语义 |
|---|---|---|
| **`mem_req`** | core → 从设备 | **MEM 阶段"进入"那一拍的单周期脉冲**。表示"这里有一次**新的**访存开始"。等待期间**保持为 0** |
| **`mem_ready`** | 从设备 → core | 从设备说"这次访存**完成了**"。**可以为 0 拉任意多拍** |

配套的隐式规则（必须一起写进 RTL 的注释里）：

1. **`mem_ready` 恒 1 时，行为必须与现在逐位相同** —— 这是整个改造的安全绳。
   也就是说 `mem_ready` 只是"允许推进"，不是"额外加一拍"。
2. **等待期间地址与数据必须保持不变**：`mem_addr` / `mem_wdata` / `mem_byte_en` /
   `mem_we` / `mem_re` 在整个 `!mem_ready` 期间冻结（靠冻结 EX/MEM 实现，见 §3.2）。
3. **读数据仍在 MEM→WB 沿由从设备给出**，读通路**不加寄存器**（`mem_bus.v` 约束 2 不许破）。
   `mem_ready` 那一拍，从设备保证 `mem_rdata` 有效，下一拍 WB 正常采样。
4. **`mem_req` 不是给存储器看的，是给"有副作用的外设"看的**（见 §3.3 第 3 条）。
5. **契约的另一半：空闲期 `mem_ready` 必须为 1。**
   允许从设备在"本次访存尚未完成"期间拉低 `mem_ready`，
   **但不允许在没有访存在途时拉低** —— 那会让 CPU 在没有访存可等的时候被冻死，
   表现为挂死在任意一拍、PC 不动、且没有任何异常（因为冻结不是异常）。
   建议在桥/存储器里用"只有 `mem_req` 来过、且事务未结束"作为拉低的唯一条件。

> **[!] 命名提醒**：`core` 上**已经有一个 `mem_re` 输出**（`core.v` 第 23 行、
> 第 119 行 `assign mem_re = ex_mem_mem_read;`），它现在只被 `mem_bus` 用来产生
> `uart_rx_ack`。本次新增的是 **`mem_req`（多一个 q）**，两者不是一回事：
>
> * `mem_re` = "MEM 级这条指令是 load"（**电平**，等待期间一直是 1）
> * `mem_req` = "这是一次新的访存开始"（**单周期脉冲**）
>
> 现在两者恰好等价（因为 MEM 从不 stall）。**加了等待之后它们就分叉了**——
> 千万别把 `mem_req` 写成 `mem_re` 的别名。

### 3.2 `core.v` 要改的三处

`core.v` 里所有级间寄存器的更新条件都是"`!stall && !div_stall`"这一类平面条件，
改造就是在**"该不该动"的判定里多一个 `mem_ready`**。三处：

| # | 位置（`rtl/core/core.v`）| 现在 | 改成 |
|---|---|---|---|
| 1 | **EX/MEM**（第 700~726 行）| `if (!resetn \|\| div_stall \|\| trap)` 清空，`else` 无条件推进 | `mem_ready=0` 时**保持**（不清、不推进）|
| 1 | **MEM/WB**（第 729~749 行）| `else` 无条件推进 | 同上，`mem_ready=0` 时**保持** |

> **注：EX/MEM 可以"不显式门控"** —— 只要 ID/EX 冻住了，`EX/MEM <= ID/EX` 每拍
> 重锁存的都是**同一份数据**，效果等价于"保持"。**能门控就门控（语义自明），
> 但不门控也不算错** —— 别把这两种写法当成对错之分。
> **真正必须门控的是 MEM/WB**：不门控的话，被停住的那条 load 会带着还没回来的
> `mem_rdata` 提前写回（WB 的寄存器写口每拍都在写）。
| 2 | **PC**（第 577~590 行）| `else if (!stall && !div_stall) pc_r <= pc_r + 4;` | 条件再或上 `mem_ready` |
| 2 | **IF/ID**（第 593~617 行）| `else if (!stall && !div_stall)` | 条件再或上 `mem_ready` |
| 2 | **ID/EX**（第 620~689 行）| `if (... \|\| stall \|\| trap)` 清空，`else if (!div_stall)` 推进 | `mem_ready=0` 时**保持**（不进清空分支，也不进推进分支）|
| 3 | **新增输出** | —— | 端口加 `mem_req`，并在 MEM 段生成"新访问"单周期脉冲（见下方代码）|

`mem_req` 的推荐实现（一个"这次访问是否已经在等"的标志位）：

```verilog
reg access_in_flight;
always @(posedge clk or negedge resetn) begin
    if (!resetn)                access_in_flight <= 1'b0;
    else if (mem_ready)         access_in_flight <= 1'b0;   // 本次事务结束
    else if (mem_re || mem_we)  access_in_flight <= 1'b1;   // 正在等
end
assign mem_req = (mem_re || mem_we) && !access_in_flight;
```

* **`mem_ready` 恒 1 时**：`access_in_flight` 每拍都被清零 → `mem_req` 恒等于
  `(mem_re || mem_we)`，而 MEM 每拍推进一次，**所以 `mem_req` 恰好是单周期脉冲，
  与现在的 `mem_re`/`mem_we` 等价** —— 这正是 §3.4 第 1 条判据要求的"逐位相同"。
* **等待时**：第一拍 `mem_req=1`（新访问），此后 `access_in_flight=1` → `mem_req=0`，
  直到 `mem_ready=1` 才重新允许下一次访问。

> **[!] [重点] 第 1 条和第 2 条最容易被抄错：`mem_ready=0` 是"保持"，不是"清空"。**
>
> 现有三种停顿的语义**各不相同**，先看清这张表再改：

| 停顿源 | `pc_r` | IF/ID | ID/EX | EX/MEM | 目的 |
|---|---|---|---|---|---|
| **`stall`**（load-use）| **保持** | **保持** | **清成气泡** | 无条件推进 | 让 load 的结果前递回来；EX 里插气泡 |
| **`div_stall`**（多拍除法）| **保持** | **保持** | **保持** | **清成气泡** | 除法指令停在 ID/EX 等 `div_done`；EX/MEM 插气泡 |
| **`mem_ready=0`（新增）** | **保持** | **保持** | **保持** | **保持（关键！）** | 让 MEM 级那条访存**原样等下去**，不许被气泡顶掉 |

* `div_stall` 是**清 EX/MEM**（气泡），因为除法指令此刻在 ID/EX 里等；
* `mem_ready=0` 是**保 EX/MEM**（不清），因为要等的那条访存指令**就在 EX/MEM 里**。
  **照抄 `div_stall` 的写法会把访存指令直接清掉，load 读到 0 / store 丢失，
  而且 `st_ld`/`ld_st` 这类用例的失败现象会非常难查。**
* `ID/EX` 在 `mem_ready=0` 时也必须**保持**而不是清空：它里面躺着下一条指令，
  上游要整体冻结，否则等待结束后会丢一条指令或多跑一条。

**关于 `mem_bus.v` 要不要改：读通路不用改。**
因为等待期间 `mem_addr` 冻结（EX/MEM 保持），`mem_bus` 内部的 `rsel_d` /
`legacy_rdata_d` / `periph_rdata_d`（第 152~162 行）每拍重算的都是同一个值，
在 `mem_ready=1` 那一拍自然给出正确读数。**动的只有"有没有副作用"的那些选通**（下节）。

### 3.3 [!] 风险与纪律（这一节必须先读完再动手）

**1) 冻结前端必须接进现有的 `stall` / `div_stall` 承重逻辑。**

`CLAUDE.md`【关键约定 6】的原话：

> **取指补偿逻辑是承重的**：stall 时是 `imem_addr` 退回 `if_addr_d`，**不是 `pc_r` 后退**。
> 搞反会复现"指令被复制执行"的老 bug。细节见 `rtl/core/core.v` PC 段注释。

`core.v` 第 557~573 行的注释把机制讲透了，摘要两句：

> stall / div_stall 时：`pc_r` 与 `if_addr_d` 都【保持不动】，同时上面 `fetch_addr` 的
> mux 把取指地址【退回 `if_addr_d[14:2]`】—— 也就是重读上一拍已经读过一遍的同一个 word。
>
> 注意：是**取指地址后退，不是 `pc_r` 后退**。若把 `pc_r` 真的往后推 4 字节，
> 连续两拍 stall 会让同一条指令被取两次（非幂等指令被重复执行），历史上就踩过这个坑。

**落地点**：`fetch_addr` 的 mux 条件（第 162 行附近）现在写的是
`(stall || div_stall) ? if_addr_d : ...`。如果新加的 `mem_ready` 让前端冻结了，
**但忘了把这个 mux 也带上 `!mem_ready`**，那么冻结期间发出的地址会和 `pc_r` 分叉，
等待结束那一拍 `if_id_instr` 采到的是**另一条指令** —— 症状与历史上的
"指令被复制执行 / 整体错位"同类，且**只在注入等待时才出现**（`mem_ready` 恒 1 时测不出来）。

> **做法**：定义一个统一的"前端冻结"条件（例如 `wire front_stall = stall || div_stall || !mem_ready;`），
> **让 `pc_r` / `if_id_*` / `id_ex_*` / `fetch_addr` mux 四处引用同一个信号**，
> 不要各写各的、更不要只改其中三处。

**2) 电平敏感的外设选通，必须改用 `mem_req`（本次实读 RTL 发现的新风险）。**

现在的选通是**电平**语义，靠"`mem_re`/`mem_we` 天然只高 1 拍"才正确：

* `rtl/periph/uart_rx.v` 第 120 行：`else if (ack && !empty) rptr <= rptr + 5'd1;`
  —— **`ack` 高几拍就弹出几个字节**。
* `rtl/periph/uart_tx.v` 第 35 行：`else if (tx_start && !fifo_full) begin fifo[wr_idx] <= tx_data; ...`
  —— **`tx_start` 高几拍就往 FIFO 里塞几个相同字符**。
* 而 `rtl/bus/mem_bus.v` 第 173 行把 `uart_rx_ack` 直接挂在 `mem_re` 上、
  第 171 行把 `uart_tx_we` 直接挂在 `mem_we` 上。

**后果**：只要 `mem_ready=0` 保持 2 拍，`mem_we`/`mem_re` 就会高 2 拍 →
一次 UART 发送会往 FIFO 里塞 2 个相同字符、一次 UART 接收会弹掉 2 个字节。
**这是静默的数据损坏，不会报错。**

**落地**：把 `mem_bus` 里所有**有副作用的选通**改挂 `mem_req`（新访问那一拍）：

```
uart_tx_we  = periph_hit && mem_we && mem_req && (periph_off == `PERIPH_UART_TX)
           || (legacy_utx && mem_we && mem_req);
gpio_we     = periph_hit && mem_we && mem_req && (periph_off == `PERIPH_GPIO);
uart_rx_ack = periph_hit && mem_re && mem_req && (periph_off == `PERIPH_UART_RX);
```

* RAM 的 `b_wr_en`（第 132 行）**可以不改**：重复写同样的数据是幂等的。
* `done`（第 181~185 行）与 `mtimecmp`（第 192~197 行）也是幂等的，**可以不改**，
  但为了口径统一，建议一并挂 `mem_req`。
* **判据**：改造后跑演示程序，串口输出的字符数与改造前**逐字节相同**。

**3) `sim/tb_coremark.v` 的 `+PROF` 区间检测是电平检测，注入等待后会失真。**

第 340 行：`if (u_core.mem_re && u_core.mem_addr == 32'h7FF4) begin ... in_timed <= (t_timer_n == 0) ? 1'b1 : 1'b0; end`
—— 靠"恰好一拍"来翻转 `in_timed`。等待期间 `mem_re` 会高多拍 → 区间标记会误翻转，
`+PROF` 的周期分解就不准了。第 324~331 行的分支计数（挂在 `id_ex_branch` 上）同理。

**影响范围有限**：`+PROF` 默认关闭（`tb_coremark.v` 第 54~59 行的设计原则），
**不影响 §8 的回归判据**。但注入等待时要看分解数据，就得把这些被动计数器一并改挂 `mem_req`。

**4) `!mem_ready` 期间不要受理中断（优先级仲裁问题，容易漏）。**

中断在 **EX 级**采样（`csr_file.v` / `core.v` 的 `int_take`）。如果 `mem_ready=0`
让整条流水线冻结，**而 EX 级恰好有一条中断被受理**，会发生：
`mepc` 被写成那个**尚未提交**的 PC，同时 pc 重定向到 `mtvec`
—— 而 MEM 级那次访存**永远等不到完成**，整个上下文就错位了。

**建议做法**：把中断受理门控在 `mem_ready` 上（`int_take &= mem_ready`）。
中断是**电平**信号（`irq_timer` 是电平比较器、`irq_ext` 是 UART RX 非空），
**晚几拍受理完全无害** —— 这比"在访存中途强行陷入"安全得多。
同步异常（非法指令 / EBREAK / 未对齐）若发生在冻结期间，也要一并考虑
"先让访存落地，再陷入"，否则会丢掉一次已发出的 store。

> 这一条**只在注入等待时才会暴露**（`mem_ready` 恒 1 时 `int_take` 的时序不变），
> 所以**必须靠 §3.4 第 3 条判据（注入等待 + 跑中断/异常汇编测试）来兜住**。
> 现成的中断测试：`sim/tests/timer_irq.S`、`sim/tests/exceptions.S`
> （一键 `scripts\run_own_tests.ps1`）—— **建议在 `+MEMWAIT=2` 下也跑一遍这两个**。

**5) [!] 必须单独一次做、单独一次回归。**

* **不要**把"加 `mem_ready`"和"加显示外设 / 接 APB / 改地址映射"放进同一次提交。
  第 0 步的正确性**只能靠"什么都没变"来证明**（§8），混进别的改动就没法判了。
* **不要**顺手重构 `mem_bus` 的地址译码、也不要动 `irq_timer` 的电平语义。
* **不要**为了"顺手"把 `mem_rdata` 打拍 —— `mem_bus.v` 约束 2 明确禁止。

### 3.5 [!] 实测踩到的三个坑（**纸面推不出来，务必先看这节**）

> 2026-09-27 按 §3.2 动手实现了一遍，用 `+MEMWAIT=2` 做验证时连撞三个坑。
> **前两个已定位并修复，第三个（id_redirect）改完仍未通过验证。**
> 下面每条的"现象"都是逐拍 trace 实测到的，不是推理。

#### 坑 1 · `fetch_addr` 漏了 `!mem_ready` → 静默丢指令

**在哪**：`core.v` 的 `fetch_addr` mux（那条 `(stall || div_stall) ? if_addr_d : pc_r`）。

**现象**：`+MEMWAIT=2` 下程序一个字节都打不出来，`pc` 停在 **0x18d0**。

**根因**：访存停顿的第一拍会把 IF/ID 冻结，而那一拍本来要收下的是上一拍发出的那次取指
（地址 = `if_addr_d`）。冻结把它拦掉了，**所以必须重发同一个地址** —— 这正是
`if_addr_d` 那条支路存在的理由，和 `stall` 完全同理。漏掉它就退回 `pc_r`（去取下一条），
那条被拦掉的指令永远补不回来，**程序从停顿点开始整段错位**。

**修法**：`(stall || div_stall || !mem_ready) ? if_addr_d : pc_r`

#### 坑 2 · EX/MEM 也必须门控 → 写丢失

**在哪**：`core.v` 的 EX/MEM 寄存器块。

**现象**（逐拍 trace）：

```
21  pc=2c  mem_addr=00005748  we=1  rdy=0   ← store 提出，等 ready
22  pc=20  mem_addr=0000574c  we=0          ← 地址已换成下一条，store 被覆盖
```

**根因**：一开始按"前端冻住 ⇒ `id_ex_*` 不变 ⇒ EX/MEM 重锁存同值无害"推理，
**是错的** —— 冻结和 `EX/MEM <= ID/EX` 是**同一个沿**发生的，而那一拍的 ID/EX 里
已经是**下一条**指令了。不门控的话，没完成的 store 被下一条覆盖 → **这次写永久丢失**，
且伴随 `mem_addr` 变成下一条的垃圾地址（实测出现过 `0x00000000`，会砸掉 `_start`）。

**修法**：EX/MEM 加 `else if (mem_ready)`。

#### 坑 3 · `id_redirect` 漏了 `mem_ready` → **分支预测状态不一致（未解决）**

**在哪**：`core.v` 的 `id_redirect = id_pred_taken && !ex_flush && !stall && !div_stall`。

**现象**：`+MEMWAIT=2` 下 BSS 清零循环**冲过上限** `0x6128` 一直转
（`pc` 停在 0x24，`rs1_val` 已到 0x6200，`id_ex_pred_taken` 却是 0）。

**根因分析**：`id_ex_pred_taken <= id_redirect` 是在 ID/EX 里**锁存**的，而 `id_redirect`
的另外三个因子（`ex_flush`/`stall`/`div_stall`）来自**后级、逐拍在变**。

- 没有访存停顿时，分支在 ID 只停 **1 拍**，两边天然一致；
- 一旦访存停住**多拍**，分支会在 ID 滞留好几拍 → 可能"某一拍真的重定向了、
  锁存那一拍却没置上 `pred` 标志" → **状态不一致**。

后果是 `ex_mispred = !ex_resolve_taken && id_ex_pred_taken` 永远不触发 ——
**"预测 taken 但实际 not-taken"这条恢复路径失效**，分支一旦被预测 taken 就再也纠不回来
（`ex_flush` 只覆盖反方向）。

**已试的修法**（`id_redirect` 也与上 `mem_ready`）**改完 pc 变成 0x2c，仍未通过**。
说明这处还有别的东西没对齐 —— **留给接手的人继续查**。

**排查建议**：`sim/tools/tb_memdbg.v` 是这次写的逐拍调试台（打印
`pc / mem_we / mem_ready / ex_flush / id_redirect / id_ex_branch / branch_taken /
id_ex_pred_taken / id_ex_funct3 / rs1_val / rs2_val / 四个前递`），
用 `+MEMWAIT=2` 跑它、和 `+MEMWAIT=0` 的同一段对比，能直接看出从哪一拍走岔。
注意**分支比较用的是 `rs1_val`/`rs2_val`，不是 `alu_a`/`alu_b`**（后者是 ALU 输入，
分支时不一定取 rs2 —— 这一点我一开始看错了信号，绕了弯路）。

> [!] **结论与建议**：
> `mem_ready` 机制**已实现且"恒 1 时逐位不变"已验证**（`+MEMWAIT=0` 下 RT-Thread 全自检通过）。
> 但**多拍路径尚未跑通** —— 上面三个坑说明这块承重逻辑的耦合面比预想的大。
> **接手时把它当"有脚手架的半成品"，不要当"已完成的功能"。**
> 建议按 §3.3 的纪律单独一次做、每改一处立刻用 `+MEMWAIT=2` 验一次，
> 不要一次改多处再一起测。

## 4. 第 1 步【P1】两个桥：都是外挂，不再碰 CPU

**前提：第 0 步已验收通过。** 做完第 0 步之后，这两个桥就退化成纯粹的
**"协议翻译层"** —— 输入是一组带 `mem_req`/`mem_ready` 的简单读写事务，
输出是一个 APB/AXI 事务。**CPU 内部一行都不用再改。**

### 4.1 A1 · APB 主桥（接标准外设）

**做什么**：把一次访存翻成 **SETUP + ACCESS 两拍**；

* SETUP 拍：`PSEL=1, PENABLE=0, PWRITE, PADDR, PWDATA`
* ACCESS 拍：`PSEL=1, PENABLE=1`，**等 `PREADY`**；`PREADY` 未到期间
  **把 `mem_ready` 拉低**，CPU 就在 MEM 级等着。
* 读：`PREADY=1` 那一拍把 `PRDATA` 送给 `mem_rdata`（仍遵守"读数据在 MEM→WB 沿有效"）。

**为什么值得做**：**Pango 自己的硬核 IP 就是 APB 接口** —— 接了 APB 桥，
Pango 例程里的外设可以近乎直接搬进来，不用一个个手写胶合。

**证据（本次实测核对过）**：`D:\pango\PDS_2022.2-SP6.4\example\PG2L100H_adc_test\rtl\adc.v`
的端口就是 APB 形态：

```
input        PCLK     ,   // APB clock（1M~100M）
input [7:0]  PADDR    ,   // status register address
input        PSEL     ,   // operation enable
input        PENABLE  ,
input        PWRITE   ,   // write enable
output       PREADY   ,   // JTAG operation flag
inout [15:0] PDATA    ,   // APB data
```

### 4.2 A2 · AXI 主桥（接 HMIC / DDR3）

**做什么**：把一次读写翻成**一个 AXI 事务**；`valid/ready` 未对握时拉低 `mem_ready`。
一个读事务至少要覆盖 AR 通道对握 + R 通道数据返回；写事务覆盖 AW/W（+B）。
**桥内部要有小的 outstanding/缓冲**，否则一次 DDR3 访问的延迟会全额暴露给 CPU
（这正好是 §5 说 Cache 有意义的前提）。

**为什么值得做**：**HMIC（Pango 的 DDR3 硬核存储控制器）的接口是 AXI。**

**证据（本次实测核对过）**：
`D:\pango\PDS_2022.2-SP6.4\ip\system_ip\ipsxb_hmic_s\ipsxb_hmic_eval\ipsxb_hmic_s\example_design\rtl\axi_bist_top_v1_0.v`
的端口是标准 AXI：

```
input   axi_awready    ,   output  axi_awvalid  ,
input   axi_wready     ,   output  axi_wvalid   ,
input   axi_arready    ,   output  axi_arvalid  ,
input   axi_rvalid     ,
```

> **[!] 注意 A2 的前置条件比 A1 多得多**：接了 AXI 只是第一步，
> 后面还要有 DDR3 的初始化序列、1066 Mbps 的时序收敛、地址映射的重新划分
> （32 KB BRAM 变成 Cache 还是"紧耦合内存"，程序放哪儿、栈放哪儿）。
> **A2 = 一个新项目的工作量，不是"加个桥"。** 见 §6 与 §7.3 的排期建议。

### 4.3 为什么做完第 0 步它们就"不再碰 CPU"

| | 第 0 步之前 | 第 0 步之后 |
|---|---|---|
| CPU 侧看到的 | 只有"1 拍必回" | "可以等任意拍" |
| 接 APB 要改 | `core.v` + `mem_bus.v` + 冻结逻辑 + 外设选通 | **只加一个 `rtl/bus/apb_master.v`**（新文件）|
| 接 AXI 要改 | 同上 | **只加一个 `rtl/bus/axi_master.v`**（新文件）|
| 回归风险 | 每次接协议都要重跑全量回归 + 重新评估 CPI | 桥不参与回归（`mem_ready` 恒 1 那条路不变）|

> **这就是"第 0 步是 P0、桥是 P1"的全部理由**：第 0 步是唯一碰流水线的一步，
> 做完之后所有扩展都变成"外挂模块"，风险与收益都变得可控。

## 5. 第 2 步【P2，有条件】Cache + 突发

### 5.1 只有做完 A2 之后它才有意义

Cache 的**唯一价值**是"隐藏慢速后端的延迟"。现在没有慢速后端，所以：

* 后端 = 单周期 32 KB 片上双端口 BRAM，**访存恒定 1 拍命中、零缺失惩罚**；
* 加 Cache 后：**命中 → 仍然 1 拍（零收益）；缺失 → 多 2 拍（纯亏）**；
  还要额外付出 LUT/BRAM 与一致性维护的复杂度。

**只有 A2（AXI + DDR3）落地后，才第一次出现"慢速后端"**（DDR3 一次访问几十上百拍），
此时 Cache 才从"纯亏"变成"可能值得"。**顺序不能反。**

### 5.2 可以直接复用的答辩话术

`doc/reports/2026-09-25_progress_report.md` §3.1 已经把"当前为什么不做 Cache"写成了成文话术，
建议照这个顺序讲（**第 4 条是量化依据，最有力**）：

1. Cache 的价值来自"隐藏慢速后端的延迟"，后端越快收益越小；
2. 我们的存储器是**片上双端口 BRAM，访存恒定 1 拍命中、零缺失惩罚**
   （实测：CoreMark 计时区间里 `mem_re + mem_we` 的访存次数与周期数对照，
   没有出现过一次访存等待）；
3. 加 Cache 之后命中仍 1 拍（零收益）、缺失多 2 拍（纯亏），还要额外面积与一致性复杂度；
4. **占位对比：CoreMark 的代码 + 数据总共只占 16.4 KB，而我们有 32 KB** ——
   **整个工作集本来就全在片内**，Cache 要"缓存"的东西已经全在最快的存储器里了；
5. 结论：这是**"架构不匹配"，不是"没做"** —— 如实写"已评估、决定不做、理由是负收益"。

> [!] **别说成"没时间做"** —— 那显得是欠账。说"评估后判定为负收益，主动不做"，
> 并给出可验证的理由（单周期 BRAM、工作集 16.4 KB < 32 KB）。
>
> **[!] 口径变化提醒**：如果将来真的做了 A2（DDR3 变成后端），
> **上面这套话术就要改写** —— 那时"没有慢速后端"不再成立，
> Cache 变成"可做且有收益"。**报告里要写清是哪个阶段的口径，别把两段混着写。**

### 5.3 突发（burst）同理

见 §6 第 1 条。突发的价值同样只在 A2 之后兑现。

## 6. [!] 明确"不做什么"，并给出理由

**1) 不要为了"总线突发"而做突发。**

赛题高阶任务①的原文里确实有"**总线突发**"这四个字，但：

* 现在后端是 **1 拍命中的片上 BRAM** —— 一次传输本身就只有 1 拍，
  **"把多个 1 拍传输合并成一次突发"省不出任何时间**：突发省的是
  "多次传输之间的地址/握手开销"，而这笔开销我们**本来就没有**。
* 换句话说：**没有慢速后端时，突发是零收益**。理由与不做 Cache 完全同构（§5.1）。
* 突发的价值只在 A2 做完后兑现 —— 那时它是 AXI 桥内部的实现选择，
  **属于第 1 步 A2 的实现细节，不是独立的一步**。

**2) 不要在加 `mem_ready` 之前动 APB / AXI。**

* 三个协议都要求"主机能等"（§1.1），CPU 不能等就都接不上；
* 强行先写桥，会写出一堆"假设从设备总能 1 拍返回"的胶合逻辑，
  而这些假设**在接真 IP 的当天就会全部作废**，返工量大于从零写；
* 桥的核心难点从来不是协议时序（那部分是查手册的活），
  而是**"请求发出去之后主机怎么等"** —— 这个能力**只在第 0 步里获得**。

**3) 不要顺手做的事**（都在别人地盘上）：

* 不动 `mem_bus` 的地址译码与 `addr_map.vh`（唯一真相，改一处要同步改三处）；
* 不动 `irq_timer` 的电平语义（`mem_bus.v` 第 72~85 行写明了为什么必须是电平比较器）；
* 不给读通路加寄存器（`mem_bus.v` 约束 2）；
* 不给取指口加仲裁（`core.v` 第 7~10 行）；
* 不为了"现代化"把总线换成 AXI 全互联 —— 单主机场景下那是纯开销。

## 7. 与应用场景的关系 + 排期建议

### 7.1 [重点] SPI TFT 显示**不需要**改总线

**这是本节最重要的一句，能省掉大量误判。**
`doc/reports/2026-09-25_handoff_rtthread_gameconsole.md` §2 定的显示方案
（SPI TFT，ILI9341 / ST7789）**不需要 `mem_ready`，也不需要任何桥**：

* 写路径可以做成**"写进 FIFO 就 1 拍响应"** —— CPU 写完就走，
  SPI 控制器自己在后台按 SPI 时钟把 FIFO 排空。
* 这正是 `rtl/periph/uart_tx.v` 已经在用的模式（1024 深 FIFO，`tx_start` 入队，
  发送机空闲时自动取下一个），**照抄即可**。
* 代价是 SPI 时钟必须比 CPU 慢、且 FIFO 要够深 —— 但这是**显示器件的固有速度**，
  不是 CPU 的瓶颈。屏幕刷一帧的耗时由 SPI 带宽决定，**加 `mem_ready` 也不会变快**。

> **所以：马里奥这条线（RT-Thread → 显示 → 游戏）与本次总线改造完全解耦。**
> **别用"要做游戏"当作改总线的理由。**

### 7.2 那为什么要改？

因为**只有把马里奥跑起来之后，"总线改造"才是有实测依据的优化，而不是猜需求**：

| 触发条件（实测依据）| 对应的改造 |
|---|---|
| 想接某个**现成的标准 IP**（Pango 硬核外设 / 第三方 APB 外设）| 第 0 步 → **A1** |
| 32 KB 装不下游戏 + RT-Thread 的资源，**必须上 DDR3** | 第 0 步 → **A2** |
| 接上慢速后端后，实测 CPI 被访存延迟拖垮 | **第 2 步（Cache + 突发）** |

**没出现上表第一列的需求，就不要提前做第二列。**

### 7.3 排期建议

```
RT-Thread（已通仿真）→ 上板 → 显示外设 → mem_ready → 按需 APB / AXI
```

| 序 | 任务 | 状态 | 与本文的关系 |
|---|---|---|---|
| 1 | RT-Thread Nano 移植 | **[OK]**（仿真已通，提交 `a96fb56`）| 无 |
| 2 | RT-Thread 上板 | 待做 | 无 |
| 3 | 显示外设（SPI TFT）| 待做 | **无**（§7.1）|
| 4 | 游戏本体 | 待做 | 无 |
| **5** | **第 0 步：`mem_ready` / `mem_req`** | **本文的 P0** | —— |
| 6 | 第 1 步 A1 / A2（按需）| 本文的 P1 | 依赖 5 |
| 7 | 第 2 步（有条件）| 本文的 P2 | 依赖 6 的 A2 |

> **理由**：先把马里奥跑起来，游戏本身会给出一堆真实的性能数据
> （渲染耗时、内存余量、CPU 占用）。**带着这些数据再决定"要不要 DDR3 / 要不要 Cache"，
> 才有可验证的依据；否则做出来的是"猜的需求"** —— 这正是 `doc/reports/2026-09-25_progress_report.md`
> §2.2 定下的总方针（"高阶任务选做，性能优先，不适配架构的宁可不做"）。
