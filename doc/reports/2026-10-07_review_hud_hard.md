## 一、要返工：HARD 档（唯一的设计问题）

### 现象

他自己在 `test_ai.c` 里写了两条 B3 验收标准，**两条都没过**：

```
[FAIL] test_ai.c:243  HARD 应比 NORMAL 多赢（B3 验收）
[FAIL] test_ai.c:244  HARD 单步节点应 ≤ 4000（B3 验收）
```

实测数据：

```
C. 自对弈（HARD 6 层 对 NORMAL 4 层，跑 6 局）
   第 1/3/5 局：57 手，赢家=黑，本局最多 6847 节点
   第 2/4/6 局：21 手，赢家=黑，本局最多 6543 节点
   合计：黑胜 6 / 白胜 0
   HARD 赢 3 局 / NORMAL 赢 3 局 / 平 0 局；HARD 单步最多 6847 节点
```

### 根因

改法是 `AI_WIDTH_HARD = 8`（默认 14）——**方向是对的**（任务书 §B3 说的就是"把宽度按档位传下去"）。
但**参数没调到位**：

> HARD 的优势是"**多 2 层**"，而宽度从 14 收到 8 是"**每层少 6 个候选**"。
> 6 层的宽收窄带来的损失，**大于**多 2 层挣回来的收益 → 棋力掉到和 NORMAL 打平。

3:3 而且**执黑方全胜**，说明两个引擎之间已经没有可分辨的强弱差 —— 先手优势决定胜负。

### 给他的选项

| 选项 | 做法 |
|---|---|
| **A（首选）** | 宽度试 **10~12**，在"≤4000 节点"和"强于 NORMAL"之间找平衡点 |
| **B** | 如果调不出来，**删掉 HARD 这一档**，只开 EASY / NORMAL |

> [!] **选项 B 不是退让。** 一个不比 NORMAL 强的档位没有存在意义 —— 留着它只是让玩家
> 白等几秒。任务书 §B3 的验收标准写的就是这个意思："否则这个档位没有存在意义，不如删掉"。

### 附带发现：那个"6 局"其实只有 2 局

节点数**只有两个值、完全重复**（6847 与 6543 各 3 次）—— 引擎是确定性的，
所以 6 局 = HARD 执黑 3 局 + 执白 3 局，每种**原样重复 3 次**。

**样本量是 2，不是 6。** 所以"3:3"这个结论的强度比看上去弱得多 ——
**别把它读成"接近打平，再调一点就行"**，它其实只说明"两种开局各赢一次"。

## 二、测试写错了（不是代码问题，别去改 `render.c`）

```
[FAIL] test_render.c:387  未定义字符应落空格字模
```

测试代码是：

```c
render_text(4, 0, "@");
CHECK(g_nt[4 * 256 + 0] == FONT_TILE_BASE, "未定义字符应落空格字模");
```

**`@` 是 `0x40`，本来就在 `0x20..0x7E` 范围内**（`FONT_N_GLYPHS = 95`），它不是"未定义字符"。
`render_text()` 的行为**与文档一致**：范围内 → 用它自己的字模；范围外 → 落空格。

**修法：换一个真正越界的字符，例如 `"\x7F"`。** 代码不用动。

## 四、要盯的一个数：栈余量掉到 6157 字节

| | 之前 | 现在 |
|---|---|---|
| 静态占用 | 19,287 | **22,515** |
| **栈余量**（栈顶 0x7000）| 9,385 | **6,157** |

**AI 的递归搜索栈就在这 6 KB 里。** HARD 是 6 层递归，每层 `cand[AI_WIDTH]` + `order[]`，
粗估 200~300 字节/层 ≈ 1.5~1.8 KB —— **目前够用，但余量只剩原来的 2/3**。

**以后再加屏幕元素（更多 HUD 行、字库扩容）要重新看这个数。** 不要等到"运行中莫名跑飞"才想起来。

## 五、做得好的地方（**别在返工时改坏**）

**① 字库方案比我建议的省得多。** 我用的是"16×16 字库、95 字 × 256 字节 = 24KB"的估法；
他用的是**紧凑 5×7 位图，95 字 × 7 字节 = 665 字节**，上电时放大 2× 写进显存。
**省了 97%。** 这是更专业的选择 —— 常驻内存的字库本来就该是紧凑位图，放大交给上电初始化做。

**② 字库生成挂进了 `gen_tiles.py`**（+396 行），文件头写明"自动生成、不要手改"。改字形改脚本即可。

**③ 绕开了字库的空字形缺口。** 字库里 28 个标点字形是空的
（`" # $ % & ' ( ) * + , ; < = > ? @ [ \ ] ^ _ \` { | } ~`），
**但 HUD 实际用到的字符全都有**（字母、数字、`:`、空格）。
而且底部那行本来可以写成 `NODES=1287`，他写成了 `NODES 1287` —— **用空格代替 `=`**
（`=` 恰好是空的）。这是正确的规避，不是疏忽。

**④ 演示模式做得完整**：`g_game.demo` 状态 + `DEMO_DELAY_MS 1500` 的节拍控制 + 标题屏
`DEMO: HOLD UP` 的入口，`test_game.c` 里还补了 "H. 演示模式（自对弈）" 的用例（59 项全过）。

**⑤ `draw_hud()` 与串口输出用的是同一份数据**（`ai_nodes` / `ai_depth` / `ai_ms`），
不存在"屏幕上和串口对不上"的风险。
