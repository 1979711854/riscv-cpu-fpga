## 3. 任务 A · 菜单系统

### 要的交互（这是用户明确描述过的）

```
标题屏
  ┌────────────────────────┐
  │        GOMOKU          │
  ├────────────────────────┤
  │    ▶ 人机对弈           │   ← 上下键选择
  │      AI 对弈            │     长按任意键确认
  └────────────────────────┘
         ↓ 选「人机对弈」
  ┌────────────────────────┐
  │  难度：▶ EASY          │   ← 同样的操作方式
  │        NORMAL          │
  │        HARD            │
  └────────────────────────┘
         ↓ 再选
  ┌────────────────────────┐
  │  执子：▶ 黑先（X）      │   ← 人机对弈才有这一步
  │        白后（O）        │
  └────────────────────────┘
         ↓ 选「AI 对弈」（从第一级直接进难度）
  ┌────────────────────────┐
  │  黑方：▶ NORMAL        │   ← 两边【分别】设难度
  │  白方：  HARD          │
  └────────────────────────┘
         ↓ 再选每手间隔
  ┌────────────────────────┐
  │  间隔：▶ 快（0.5s）     │
  │        中（1.0s）       │
  │        慢（2.0s）       │
  └────────────────────────┘
```

**操作方式统一为**：**上下键选择 + 长按确认**（和用户要求一致）。
"AI 对弈"那一支里，黑方和白方是**两个独立的列表**，用左右键在"黑方/白方"之间切换列，
上下键改当前列的难度 —— **这一步你来定实现方式，但两边必须能分别设。**

### 数据结构要改的地方

现在 `game_t` 里只有**一个** `level`。要拆开：

| 字段 | 用途 |
|---|---|
| `mode` | 人机对弈 / AI 对弈 |
| `level_black` / `level_white` | **双方各自的难度**（人机对弈时只用人那一方对手的）|
| `human` | 人执黑还是白（**已存在**，现在硬编码成黑）|
| `step_ms` | AI 每手间隔（三档：500 / 1000 / 2000）|
| `menu_stage` | 菜单层级（模式 / 难度 / 执子 / 间隔），以及每级的高亮项 |

**`game_ai_turn()` 现在用 `gm->level` —— 改成按当前执子方查 `level_black`/`level_white`。**

**`demo` 字段可以并进"Ai 对弈"** —— 现在的演示模式是 `NORMAL vs NORMAL` 固定，
合并进菜单后就是"双方可设难度的 AI 对弈"，`DEMO_DELAY_MS` 换成 `step_ms`。

## 5. 任务 C · AI 思考时画面卡住

### 现象与根因

用户原话：**"我下完棋之后，AI 思考的时候画面跟卡住了一样，直到 AI 下棋，不够流畅"**。

**根因**：AI 是**同步阻塞**跑的，搜索期间主循环完全停住：

```c
for (;;) {
    video_wait_vblank();          /* ① 等回扫 */
    input_poll(...);              /* ② 采样按键 */
    game_tick(&g_game, ...);      /* ③ AI 在这里阻塞 0.1~7 秒 —— 主循环停了 */
    draw_frame();                 /* ④ 刷屏 —— 只有 AI 跑完才会执行到 */
}
```

**所以两个症状**：
1. **你刚下的那颗子要等 AI 想完才一起出现**（因为 `draw_frame()` 在 ③ 之后）
2. 思考期间画面**完全静止**

### 方案：**G1 + G2**（用户已认可，不建议上 G3）

#### G1 —— 人落子后立刻刷一次屏

把"人走完"和"AI 走"拆开：**人落子 → 立刻 `draw_frame()` → 再跑 AI → 再 `draw_frame()`**。

效果：**你马上就看见自己刚下的子**，不用等 AI。

#### G2 —— AI 按迭代加深的层数分批

`ai.c` 的主循环现在是：

```c
for (d = 2; d <= depth; d += 2) {     /* 迭代加深 */
    ... 完整搜一层 ...
}
```

**改成"每次调用只加深一层"**，返回主循环刷屏后再继续。这样思考期间画面会跳 2~3 次，
**而且 HUD 那行 `AI: NODES` 的数字在涨 —— 评委能看见 AI 在逐层加深搜索**，演示效果反而更好。

**实现要点**：
- 给 `ai.c` 加一个可保存的搜索状态（当前层 `d`、已搜到的最优着法、累计节点数）
- `ai_choose_move()` 拆成 `ai_search_begin()` + `ai_search_step()`，或加一个"单步模式"开关
- **不要动递归结构本身** —— 只在外层迭代加深那里切分
- 每步之间要有**时间上界**（比如 300ms），否则一层搜完还是要等很久

#### 为什么不做 G3

用户问过"G3 难度大吗？能体现 RT-Thread 吗？" —— **RT-Thread 那条路被内存卡死了**：

```
gomoku 固件静态占用     22,507 字节
RT-Thread Nano 内核     ~15,000 字节
─────────────────────────────────
合计                    ~37,500 字节  >  32 KB 硬墙  ✗
```

**而且 RT-Thread 这个加分项已经单独拿到了**（2026-09-27 上板跑通，banner + ping/pong）。
**不要为了它把五子棋塞进去。**

G3（无 RTOS，把递归 α-β 改成显式栈的状态机）技术可行，但递归改迭代**极易引入隐性 bug**，
而收益只是"从跳几次变成全流畅"。**不建议。**

## 6. 任务 D · `video_wait_vblank()` 加超时（P1，顺手做）

现在的实现是个**没有超时的忙等**（`scripts/gomoku/video_port.c:45`）：

```c
/* [重点] 这里忙等，而且没有超时保护 —— 如果视频 PLL 没锁（pix_clk 不走），
 *         这个位永远不变，程序会卡死在这里、串口也不打印，看起来像"死机"。 */
while ((REG32(VIDEO_STATUS) & 1u) == 0u) ;
```

**注释自己承认了问题却没修。** 2026-10-07 实测踩到过一次（误触配置键导致视频域没起来，
CPU 永久挂在主循环第一句 → 屏幕黑 + 按键全死 + 串口静默）。

**改法**：加一个 `hw_mtime()` 超时（比如 50ms），超时就返回并允许后续重试。

**判据**：视频失锁时，串口仍能打印、按键仍能响应 —— **不再"死机"**。

## 7. 纪律与坑

### 7.1 必须跑的两条基线

```
双发射（默认，= 板上口径）   49 PASS / 1 FAIL / 0 TIMEOUT + CoreMark 313,886 拍/迭代
单发射（-Single）            49 PASS / 1 FAIL / 0 TIMEOUT + CoreMark 363,515 拍/迭代
```

**改 RTL 时两条都要跑**；改五子棋固件只跑 `run_test.ps1` 即可（它含 RV32 交叉编译检查）。

### 7.2 [!] 板子上的按钮：**别按 SW2/D22**

| 丝印 | 是什么 | 按了会怎样 |
|---|---|---|
| **SW2（旁边是 D22 灯）** | **接 FPGA 配置逻辑**（`INIT_B`/`PROGRAMN` 类专用脚）| **FPGA 重新加载配置 → 设计被卸载 → 两个 PLL 全灭、屏幕黑、串口静默**。因为位流只从 JTAG 下到 SRAM、flash 是空的，**必须重新下载位流才能恢复** |
| **SW3（KEY0 / C22）** | **真复位** | CPU 重启，两个 PLL 保持锁定，屏幕回到标题屏 |
| SW4~SW7 | 用户按键 | 对应 `key[0..3]` |

> **2026-10-07 实踩**：用户误按 SW2 以为"复位后死机"，排查了半天。
> **判据：按完两个 PLL 灯还亮不亮** —— 亮 = 真复位；全灭 = 按的是配置键。

### 7.3 串口可观测性（硬纪律）

**任何玩家可感知的动作，串口都必须有输出** —— 2026-10-04 一天因为这类毛病连踩 4 次。
逐条清单见 `doc/reports/2026-10-06_taskbook_v3.md` §4.3。

**加提示时要"先判断再打"**：踩过的坑是把 `AI thinking...` 挂在"长按"上，
往已有子的点长按会打出这句话却**没有下文**（落子没成功、AI 根本没跑），比不打还糟。

### 7.4 [!] 变短的字符串必须整行重写

**2026-10-07 实踩**：`render_text_center` 只写字符串本身、不擦这一行剩下的部分，
标题屏从 `LEVEL: NORMAL`(13 字) 切到 `LEVEL: EASY`(11 字) 时**居中起点变了**，
两端各留一个 `L` ⇒ 屏幕显示成 **`LLEVEL: EASYL`**。

**已修**：`render_text` 改成**整行一次写完**（先铺满空格字模再覆盖文字），
`test_render.c` 里加了 4 条回归锁（其中一条"居中变短后两端都补空格"
当场抓出了第一版修法只补右端的缺陷）。

**做菜单高亮时注意同类问题**：高亮项会移动，**上一处的高亮必须被擦掉**。

### 7.5 中文 Windows 上的编码陷阱（两个，都踩过）

1. **无 BOM 的 `.ps1` 被 PowerShell 5.1 按 GBK 读** → 中文注释吃掉引号配对 →
   报"缺 `)`"的**假语法错**。**新增脚本务必加 BOM。**
2. **原生命令输出被按 GBK 解码** → git 给的中文文件名变乱码 → `Test-Path` 失败。
   需要 `[Console]::OutputEncoding = UTF8` 且 `$OutputEncoding = UTF8`。
   样板见 `scripts/pack_for_teammate.ps1`。

### 7.6 构建与位流

- **`expectLines` 守卫会拦你，那是守卫在工作** —— 固件大小变了就更新它
- **任何一次综合都会覆盖 `generate_bitstream\cpu_top_board.sbit`**，
  而**所有位流文件名和字节数完全一样**（9,188,552）。
  归档名必须带配置：`_dual_` / `_single_`，**这次的还要带 `_60hz_`**（见下）
- 位流一律用 `scripts\build_bitstream.ps1 gomoku` 生成（它打印 md5 + DUAL_ISSUE）

### 7.7 [!] 视频时序：改了就重算刷新率

当前 `video_core.v` 的 `H_TOTAL = 810`（**不是标准 VESA 的 800**）：
像素时钟 25.5MHz 不是 25.175（两者与 27MHz 晶振不可通约），所以行总周期要补到 810
才有 **59.96Hz** —— 否则是 60.71Hz，**大屏显示器的缩放器会锁不住、画面抖动撕裂**。

> **2026-10-07 实踩**：HDMI 首次接真显示器就是这个症状，修完立刻正常。
> **改这段时序前先读 `video_core.v` 里那段注释，并同步改 `sim/tb_video_core.v`。**
