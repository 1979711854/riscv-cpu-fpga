# 双发射配对率：当前实况与剩余空间（2026-10-15）

> 起因：`2026-10-15_pce_region_result.md` §7 判死了"提频/时序侧"之后，
> 回头清点"周期侧还剩什么"。**结论出乎意料：此前流传的几项待做里，两项不成立。**

---

## 1. 一句话

**周期侧唯一剩下的实质机会 = 让 lane B 能发访存指令（load 带出 store），上界 +7.46%。**
其余几项（`pair_analyze.py` 算出的"分支配对 +4.18%"、BHT 扩容、单做 store）**都不成立或早已实现**。

---

## 2. [重点] 发现：`pair_analyze.py` 的模型与实现已经脱节

`scripts/pair_analyze.py` 的 docstring 自称：

> **规则来源**：`rtl/core/core.v` 的 `pair_now`（实现）与本文件的 `PURE_ALU` / `BREAK`（模型）
> 是同一套规则的两种写法。

**实际不是。** 该模型写于 2026-10-10（双发射还没做），`BREAK = {BRANCH, JAL, JALR, SYSTEM, FENCE}`
把 lane A 是这些就判"本组 1 宽" —— 那是 **Stage-0 的保守假设**。

而 `rtl/core/core.v:696` 的 `pair_now` 实际是：

```verilog
assign pair_now = (DUAL_ISSUE != 0) &&
                  (imem_rd != 32'd0) && (imem_rd2 != 32'd0) && !p_pred_taken &&
                  !p_muldiv_a && !p_amo_a &&
                  p_opcode_b_ok && (p_f7_b != 7'b0000001) && (p_rd_b != 5'd0) &&
                  (p_rd_a != p_rs1_b) && (p_rd_a != p_rs2_b) && (p_rd_a != p_rd_b);
```

**对 lane A 没有任何 opcode 限制**，唯一的相关门控是 `!p_pred_taken`。
⇒ **"预测不跳转的分支可以配对"这件事，实现早就做了。**

### 交叉验证（很硬）

| 来源 | 双提交拍数 |
|---|---|
| **实测反推**：`region commit` = 214,703 拍，288,056 条指令 ⇒ 288,056 − 214,703 | **73,353 对** |
| **模型**「保守 + 分支配对」（不含 bypass） | **72,256 对** |

**差 1.5%，吻合** —— 差的正是实现还多放开了 jalr / system / fence
（`pair_now` 不限制它们，只要没被预测跳转）。

⇒ **`pair_analyze.py` 打印的「③ ① + 允许预测不跳转的分支配对（放宽，上界）」不是上界，
就是现状。** 照它算会得出"还有 +4.18% 可挖"的错误结论（本次差点据此开工）。

---

## 3. 数据（以【实现近似】为基准）

方法与自检：用 `pair_analyze.py` 的规则框架 + 一份临时变体脚本，离线复放规则，
输入 `sim/programs/pairtrace.txt`（**288,056 行 = 每迭代指令数**，口径判据满足）。
三个自检全部 PASS（本模型能逐位复现 `pair_analyze.py` 的 ①②③ 三档，说明改写无误）。

| 规则 | 配对数 k | 相对实现基线 | 周期 | **分数提升** |
|---|---|---|---|---|
| **当前实现**（模型口径「保守+分支配对」）| 72,256 | — | 229,597 | — |
| + lane B 允许 **store** | 73,235 | +979 | 228,618 | **+0.43%** |
| + lane B 允许 **store + load** | **88,202** | **+15,946** | **213,651** | **+7.46%** |

> 换算到得分：370.23 →（上界）**398 CoreMark**。

**两个折扣（必须一起说）：**
1. **取指带宽**：模型对当前实现的已知乐观度 ~5%（模型 63,042 vs 实测反推的另一口径）。
2. **时序**：新增逻辑要吃掉 85 MHz 的余量（当前仅 **+0.034 ns**）。

**break-even**：`85.0051 ÷ 1.0746 ≈ 79.1 MHz` —— 频率掉到 79 以下才亏，缓冲约 7%。

## 4. 顺带清掉的几项

| 曾被列为待做 | 实际 |
|---|---|
| 分支配对（模型③，+4.18%）| **早已实现**，不是待做项 |
| BHT 扩容 256→1024 | **实测只 +0.10%，已回退**（`2026-10-13_handoff_pathB.md` §3）|
| 单做 lane B 的 store | 只有 **+0.43%**，不值得 |
| 消除 load-use 停顿 | 插入点在关键路径上，**做不了**（约定 45 / `2026-10-15_earlyld_rest_timing_assessment.md`）|
| 加流水级数 / 提频 / Cache / 区域约束 | 均已实测否证 |

## 5. 结论

**要让周期侧再动，只有一条路：给 lane B 加访存能力。** 上界 +7.46%，
但它是目前唯一能进的、且量级不小的门。

**代价与风险（还没量）**：
* `core.v:262` 注释明写「lane B 写回数据**无 load 分支**（`wb_sel=01` 对 lane B 不可能）」，
  `id_ex_b_*`（`core.v:247-251`）也只带了 ALU 类字段 —— 要扩这一组寄存器。
* **访存端口仲裁**：lane A 与 lane B 同拍都要访存时的冲突，必须显式处理。
* 冲刷路径要确认覆盖 lane B 的访存副作用。
* 全在 `fetch_addr` 那条独木桥附近，**改完必须重量时序**（约定 53 的判据）。

**[!] 未验证的部分**：+7.46% 是**静态规则复放的乐观上界**，不含取指带宽与新增逻辑的时序代价。
真正的数只有改了 RTL 跑 `+PROF` 才知道。

## 6. 复现

```powershell
# 1) 生成单发射的 +PAIRTRACE（双发射下 +PAIRTRACE 看不见 lane B，会算出 228,183 这个错数）
scripts\run_coremark.ps1 -Iter 1 -Single
cd sim
vvp tb_coremark_single.vvp "+ITER=1" "+IMEM=programs/imem.hex" "+DMEM=programs/dmem.hex" "+PAIRTRACE"
# -> sim/programs/pairtrace.txt，行数必须是 288,056

# 2) 复放保守规则（原脚本）
python scripts\pair_analyze.py sim\programs\pairtrace.txt

# 3) 复放"放开 lane B load/store"（本次用的临时变体，未入库）
#    与 2) 的 ①②③ 逐位对得上即为自检通过
```

**[重点] 读 `pair_analyze.py` 的输出时**：`预测区间周期数` / `预测得分` 是**从单发射基线
363,515 外推的**，**不适用于当前双发射实现**（脚本自己的 docstring 已声明）。
能用的只有 `k`（配对数）、`p`（配对率）与 `reasons`（不配对原因分布）。
