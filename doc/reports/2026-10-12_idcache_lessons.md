## 2. 技术经验

### 2.1 「信号名里的流水级 = 它属于哪一级」——张冠李戴类 bug
`wb_rdata_snap` 服务 **MEM/WB** 级的 load，却在停顿沿用 **`ex_mem_ld_fast`**
（EX/MEM 级、**下一条**指令）去选数据源。
⇒ **写 RTL 时凡是"用 A 级的信号决定 B 级的行为"，先停下来问一句"它俩是同一个时刻吗"**。
这类 bug 的可怕之处：
* 编译不报、lint 不报；
* **短仿真不崩**（本例 8,124 拍才跑飞，riscv-tests 代码短，碰不到）；
* 只在"特定时序组合"下才发作。

### 2.2 一个 bug 需要"四个条件同时成立" ⇒ 它一定会躲过你的回归
触发条件：`EARLY_LD=1` **且** `ICACHE_EN=1`（提供大量停顿）**且** `DCACHE_EN=1`
**且**"普通 load 在 WB、快通路 load 在 EX/MEM"。
⇒ 教训：**回归矩阵要覆盖 switch 组合，不能只跑"默认那一条"**。
默认四条回归全是 `EARLY_LD=0`，天然盖不住它。

### 2.3 板上症状能"逐字"在仿真里复现 ⇒ 就不必上 ILA
板上是"banner 反复、字符交织"；仿真里同一配置在 **cyc≈8,124** 跑飞、`pc` 跳 0
（`mtvec` 复位值 = `_start`）⇒ **同样是 banner 循环**。
⇒ 用一句判据：**"仿真和板上的现象是不是同一个"**。是 ⇒ 在仿真里调（便宜 100 倍）；
不是 ⇒ 才需要 ILA。**别一上来就上 ILA**。

### 2.4 A/B（**唯一变量**）才是根因证据
真正定案的是"**同配置、同固件，只改这一行**"：
* 未修版：150 s 跑不完、banner 反复 28 次、字符交织（**与板上症状逐字一致**）
* 已修版：一次跑完（1,551,521 拍）、无 trap、四个 CRC 全对

⇒ **"某个长仿真过了"永远不能当根因证据**（你无法证明它跑的是出问题的那个配置）。

### 2.5 二分定位：把"两个变量的组合"拆成两个单变量
"只开 D（同一降频口径）"通过 ⇒ 立刻把故障从"整块 Cache"压到"**I-Cache**"。
⇒ **凡是"两个新东西一起上就坏"的问题，先各上一个**。

### 2.6 静态时序排除要 setup / hold **两组都看**
第一次只记了 setup，被指出"hold 违例恰好是仿真看不出、板上偶发错指令的经典成因"，
补测 hold 后两组建模都没问题 ⇒ 才敢把静态时序排除。
⇒ **排除一项假设时，要排干净**，半张表不算。

## 3. 方法论经验（口径与测量）

### 3.1 [!] 「仿真过了 ⇒ 逻辑对」**不成立**，除非**配置打印全对**
本轮最大的坑。项目此前记录的"I+D `ITER=50` 长仿真四个 CRC 全对"
与本 bug **直接冲突**（未修 RTL 8,124 拍就崩）—— 几乎肯定是那次**漏了 `-EarlyLd`**。
⇒ **判据：跑完先看 vvp 首行 `SIM CONFIG:`**（本轮加进脚本，写进 `results.txt` 首行）。

### 3.2 口径必须**显式**、并**核对**
`-DCache -ICache -EarlyLd` 一个都不能少。默认值、`.v` 里的 parameter 默认值、
"上次跑的那条命令"，**都不能当依据**。

### 3.3 [!] **文档里的历史数字会骗你 —— 关键数字要自己重量**
文档记的"I+D = **265,408** 拍/迭代（+9.8%）"是**漏了 `EARLY_LD`** 的口径
（那个开关省 20,385 拍，244,034 + 20,385 ≈ 265,408）。
* **后果 1**：优化排序被判错（"压 I-Cache 缺失通路 ≈ +6%"这条其实上限只有 0.9%）。
* **后果 2**：`ITER` 会被算错（用 265,408 算会得到 3372，实际该用 **243,933 → 3668**）。
⇒ **凡是要写进报告/位流的数字，先在本机重量一遍**，并**把口径（开关+平台）一起记下来**。

### 3.4 [!] **得分要自己算，别抄日志那行**
`Iterations/Sec` 在这个 port 上是 `HAS_FLOAT=0` 的**整数截断**：
I+D 真实 **313.63**，日志打 **333**；D-only 真实 **351.86**，日志打 **374**。
判据：`ITER × 时钟 ÷ Total ticks`。

### 3.5 [!] **`.sbit` 的 md5 跨仓库不可比**
同一设计在两个仓库副本：**网表逐字节相同、时序逐位相同**，`.sbit` 的 md5 却不同
（**内嵌工程路径**）。⇒ 比"同不同设计"要**比网表**。

### 3.6 [!] **布局抖动比你以为的大**：同一 RTL 两次 PnR 反推的 Fmax 差 **0.42 ns**
（85 MHz 那次 ⇒ 77.5 MHz；76.5 MHz 那次 ⇒ 80.1 MHz）
⇒ **"76.5 有余量"推不出"80 一定行"**；**单次 slack 不能外推**，要卡某档就多 seed 实测。

### 3.7 仿真里"字符翻倍"是**测试台假象**，不是板上那种"交织"
I+D 仿真的日志里 banner 是 `[[bbuuiilldd]]`（每个字符打两遍）——
因为**tb 的 UART 捕获没有板上那层 `bus_first` 门控**
（`mem_bus.v` 的 `uart_tx_we` 只在停顿的**第一拍**发一次，tb 是"每拍都打"）。
⇒ **看到仿真日志异常，先分清"是 DUT 的问题还是 tb 的问题"**。

## 4. 流程经验

1. **并行综合必须用不同仓库副本** —— 同一个 PDS 工程目录不能并发
   （两个任务抢 `cpu_top.v`/`mem.hex`/`place_route/`）。本轮就是这么同时跑 85 + 76.5 的。
2. **改频率是"改三处 + 事后全部还原"的事务**（见 `CLAUDE.md` 约定 50）。
   不还原的话，下次出的"跑分位流"时钟口径就是错的，而且**从名字和日志都看不出来**。
3. **改任何 RTL 都要递增 `DESIGN_REV`**（约定 42）—— 本轮修复就漏了一次，
   导致"修好的位流"和"失败的位流"串口首行**一模一样**，事后无法区分。
4. **"带开关的位流"要 grep 网表**（约定 46）—— 只看脚本打印会被"根本没改文件"骗过。
5. **本机环境坑（工具链）**：`scoop` 的 `iverilog`/`vvp` shim 会往 stderr 打
   `Shim: Could not determine if target is a GUI app`，而脚本里 `& iverilog ... 2>&1`
   配 `$ErrorActionPreference = "Stop"` ⇒ **脚本会在编译那一步静默中止**。
   绕过办法：先用真实路径的 `iverilog.exe` / `vvp.exe` 手动跑一次
   （或把 shim 换成 `@echo off` 包装的 `.cmd` 前置到 PATH）。
   **这不是设计问题、也不是脚本逻辑错**，别去改 RTL。

## 5. 下次做类似任务，照这个顺序走

```
1) 先量"当前基线"，且把口径（开关 + 平台 + 命令）一并记下来
2) 板上现象 ↔ 仿真现象 对齐（同一配置），能对齐就别上 ILA
3) 二分：把"多变量组合"拆成单变量（本例：只开 D）
4) 找到可疑信号后，问一句"它服务的流水级和它的来源级是同一个时刻吗"
5) A/B：唯一变量 = 那一行，用它当根因证据（不是"某个仿真过了"）
6) 回归：把触发条件涉及的 switch 组合【显式】补齐，并核对 SIM CONFIG
7) 出位流：验网表（dcache/icache 实例数）+ 记 setup/hold/失败端点
8) 上板：先对 md5、看串口首行 RTL=、再算分（自己算）、核对四个 CRC
9) 归档 + 更新索引/报告，并把口径与"作废的旧结论"一起标出来
```

## 6. 遗留的"没做到"（诚实记录）

* **I+D 没能在 85 MHz 跑**：−1.143 ns / 343 失败端点。PCE 区域约束**没试过**（要开 GUI）。
* **`fence.i` 仍是 NOP**：现状安全（无自修改代码、无片外存储），但将来要补。
* **Cache 对分数贡献 = 0**：后端是单周期片内 BRAM。想让它"有收益"只能把后端变慢 —— 那是净亏，**不做**。
* **`.sbit` 不在仓库里**：队友必须自己综合（步骤见 `2026-10-12_taskbook_v8.md` §7）。
* **本轮所有"板上通过"的证据都是串口日志**，没有 ILA 波形（这次不需要）。
