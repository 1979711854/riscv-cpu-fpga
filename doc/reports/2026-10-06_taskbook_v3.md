## 2. 任务 A · 资源效率优化【P0】

### 为什么做

双发射把 `CoreMark/LUTs` 从 0.0534 打到 **0.0392（−27%）** —— 这是赛题三项性能指标里
**唯一净亏的一项**（另两项：效率 +15.8%、Fmax −4.8%）。LUT 从 4,377 涨到 **6,909（+58%）**。

**设备只用 4.32% 的逻辑，所以这不是"装不下"，是"比值不好看"。** 但赛题就是这么评的。

### 已经定位的三个抓手（**但先别动手，先量**）

核内这几个模块是**成对重复**的（`rtl/core/core.v`）：

```
293: control u_ctrl      /  349: control u_ctrl_b      ← 译码器 ×2
335: imm_gen u_imm       /  371: imm_gen u_imm_b       ← 立即数生成 ×2
549: alu     u_alu       /  577: alu     u_alu_b       ← ALU ×2
```

而 **lane B 只允许 `OP / OP-IMM / LUI / AUIPC` 四种**（见 `pair_now` 的条件）。于是：

| 抓手 | 说明 | 预期 |
|---|---|---|
| **① `imm_gen` 换窄版** | lane B 的立即数**只可能是 I 格式或 U 格式**，但例化的是全 5 格式（I/S/B/U/J）。砍掉 S/B/J 三套 mux | 省 80~150 LUT，**零风险**（功能等价）|
| **② `control` 换窄版** | lane B 用不到 `branch_b / mem_read_b / mem_write_b / csr_addr_b / sys_mret_b…`。换成只出 `reg_write/alu_op/alu_a_sel/alu_b_sel/wb_sel` 的窄译码 | 需先量综合裁掉了多少 |
| **③ 收窄 lane B 的 ALU** | ALU 里最贵的是**桶形移位器**（SLL/SRL/SRA）。不再配对移位指令就能砍掉它 | 收益最大，**但会降配对数** |

### [!] 第一步必须先量，别凭猜砍

**先拿分层资源报告**：DUAL=0 vs DUAL=1 的**逐模块 LUT 对比**。两条路：

- PDS GUI 里的资源报告入口
- 或**增量综合实验**：把某个模块临时换成空壳，看 LUT 掉多少（差异法）

**按大小排序再动手，一次只改一个** —— 三个一起改，出了问题分不清是哪一个。

**具体可用的测量工具**：`scripts/gomoku/measure_ai.c` 是应用侧的样板（受控对比、量化输出），
资源侧也照这个思路写个小工具/脚本。

### 验收标准

1. **先交分层明细**（DUAL=0 / DUAL=1 逐模块 LUT），再动手
2. 改完后 `CoreMark/LUTs` **明显改善**，且 **CoreMark 每迭代周期不变或更好**
   （拿 `run_coremark.ps1 -Iter 1` 读 `Total ticks` 对）
3. **双发射和单发射两条基线都要过**（§4）
4. PDS 重新综合确认 **slack 没变差**（现在只有 +0.270 ns，很薄）

> [!] **别为了省 LUT 把配对数砍到没有意义。** 如果某个改法让 lane B 几乎配不上对，
> 那就等于退化成单发射 —— 那不如直接出单发射版（`-Single`），至少 LUT 是省下来的。

## 4. [!] 纪律（都是踩过的，按重要性排）

### 4.1 配置口径 —— 仿真和综合必须是同一个配置

```
rtl/core/core.v:5          parameter DUAL_ISSUE = 0    ← 核的默认
rtl/top/cpu_top.v:52       parameter DUAL_ISSUE = 1    ← 上板是双发射
tb_riscv.v / tb_coremark.v 吃 -DDUAL；默认 0
tb_demo / tb_rtthread / tb_gomoku / tb_video_bars 例化 cpu_top → 本来就是双发射
```

**2026-10-06 之前这里是个坑**：跑标准脚本测的是单发射，烧到板上的是双发射，
**两边不是一个配置**。现在已修：脚本显式传配置、测试台 t=0 打印
`SIM CONFIG: DUAL_ISSUE=%0d`、`results.txt` 首行记录配置。

**[重点] 两条并列基线，每次改动两条都跑，不能混：**

| 配置 | riscv-tests | CoreMark 每迭代 |
|---|---|---|
| **双发射（默认，= 板上口径）** | 49 PASS / 1 FAIL / 0 TIMEOUT | **313,886** |
| 单发射（`-Single`） | 49 PASS / 1 FAIL / 0 TIMEOUT | **363,515** |

### 4.2 别碰 `rtl/`（做五子棋时）

五子棋是纯固件。改了 RTL 要走 CPU 全量回归（上面两条基线都跑）。
**做任务 A 时例外** —— 那本来就是改 RTL。

### 4.3 串口可观测性 —— 任何可感知的动作都要有输出

2026-10-04 一天里因为"板子做了但不说"连踩 4 次，每次的现象都是"看起来像死机"。

| 动作 | 必须有输出 |
|---|---|
| 开局 | 完整棋盘（**注意开局棋子数是 0、不算"变化"，得单独触发**）|
| 移动光标 | `cursor=H8` |
| 切难度 | `level=2 HARD (6-ply)` |
| 落子失败 | `occupied -- move the cursor and try again` |
| AI 开始思考 | `AI thinking (HARD 6-ply)...` ← AI 是同步阻塞跑的，不喊就是十几秒静默 |
| AI 落子 | `AI moved, nodes=… depth=… t=…ms` |

> [!] 加提示要**先判断再打**。踩过的：把 "AI thinking..." 挂在"长按"上，
> 往已有子的点长按会打出这句话却**没有下文**（落子没成功、AI 根本没跑），
> 比不打还糟 —— 直接被误判成"AI 卡死"。

### 4.4 中文 Windows 上的编码陷阱（两个，都踩过）

1. **无 BOM 的 `.ps1` 被 PowerShell 5.1 按 GBK 读** → 中文注释吃掉引号配对 →
   报"缺 `)`"的**假语法错**；更坏的情况是**不报错却跑出垃圾结果**。
   **仓库里四个脚本已统一加 BOM，新增脚本务必照做。**
2. **原生命令输出被按 GBK 解码** → git 给的中文文件名变乱码 → `Test-Path` 失败。
   需要 `[Console]::OutputEncoding = UTF8` 且 `$OutputEncoding = UTF8`。
   样板见 `scripts/pack_for_teammate.ps1`（这个脚本两次都中过，注释里写清了）。

### 4.5 构建与位流

- **`expectLines` 守卫会拦你，那是守卫在工作**，确认是编译期常量变了就更新它
- **任何一次综合都会覆盖 `generate_bitstream\cpu_top_board.sbit`**，
  而**所有位流文件名和字节数完全一样**（9,188,552）。
  **归档名必须带配置：`_dual_` / `_single_`** —— 差别只是"分数差 15.8%"这种不显眼的东西
- 位流一律用 `scripts\build_bitstream.ps1 <变体>` 生成（它会打印 md5 和 DUAL_ISSUE）

### 4.6 仿真口径

`run_sim.ps1` 写死了 `-Sim`（按键阈值 1ms/5ms、AI 用 EASY）。**板上口径喂给仿真会等到超时**，
那不是 bug。`tb_gomoku` 单次仿真**要 20~50 分钟真实时间**（它的超时保护本身就有 6e9 ns 仿真时间）。
