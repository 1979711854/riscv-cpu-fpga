## 3. 各任务细节

### 3.1 [必修] `video_wait_vblank()` 会永久挂死

**现象（2026-10-07 实测）**：按复位后，**固件卡死** —— 串口只打出 banner，
之后一句都不再有；按键也全死。

**根因**：`scripts/gomoku/video_port.c:45`

```c
/* [重点] 这里忙等，而且没有超时保护 —— 如果视频 PLL 没锁（pix_clk 不走），
 *         这个位永远不变，程序会卡死在这里、串口也不打印，看起来像"死机"。*/
while ((REG32(VIDEO_STATUS) & 1u) == 0u) ;
```

**日志证据**：banner 每 7 行重复一次（一个 banner 正好 7 行），
且**只有第一次启动打出 `level=`** —— 后面每次都走不到主循环第一拍。
主循环的第一句就是 `video_wait_vblank()`。

**为什么复位后会没有 vblank**：`rtl/video/video_top.v:91` 的
`wire vid_resetn = resetn & locked;` —— **视频域跟着按钮复位一起被复位**，
视频没恢复就永远没有 vblank。

**改法（两条都做）**：

1. **`video_wait_vblank()` 加超时**：用 `hw_mtime()` 判，超时（比如 50ms）就返回。
   **判据：视频失锁时，串口仍能打印、按键仍能响应 —— 不再"死机"。**
2. **把 `vid_resetn` 与按钮复位解耦**：改成只由视频 PLL 锁定门控
   （`wire vid_resetn = locked;`），按钮复位不再打断视频。
   这样按复位只重启 CPU，画面不中断。

> [!] 一个固件因为外设没就绪就永久挂死，本身就是缺陷。**注释承认了问题却没修。**

### 3.2 [必修] 双重 LEVEL 显示

    ...

    ...

**进对局后，标题屏留在行 3 的那行没被清掉。**
（注意：2026-10-07 修的是"**同一行内**的残字"，这个是"**别的行**没清" —— 同类问题的另一种形态。）

**改动会随任务 C 的菜单重排一起做掉，别分两次。**

**回归锁**：`test_render.c` 里补一条 —— 从标题屏进对局后，标题专用行必须是空格字模。

### 3.5 AI 思考时画面卡顿（P0）—— **实测最长 1.4 秒**

**现象**：用户原话 —— **"AI 下棋的瞬间，红色光标会卡顿一下"**。

**实测**：AI 一手 **171 ms ~ 1,433 ms**（NORMAL，31 手一整局）。这一整段时间里
**主循环停住 → 光标闪烁也停了**。

**根因**：AI 同步阻塞，`draw_frame()` 要等 AI 跑完才执行。

**改法（G1 + G2，已在 v4 任务书论证过）**：

- **G1**：人落子后**立刻刷一次屏**，再进 AI —— 你马上看见自己刚下的子
- **G2**：AI **按迭代加深的层数分批**，每层搜完回主循环刷一次屏 ——
  画面跳 2~3 次，且 **HUD 那行 `AI: NODES` 的数字在涨**（演示上是加分项）

**不做 G3**（RT-Thread 或纯协程重写）—— 内存装不下 / 递归改迭代风险太高，见 v4 §3.5。

### 3.7 [新] 统一存储器 32 KB → 64 KB

**用户已拍板要做，时间充足。** 这一改**一次解锁两件事**：

```
gomoku 22.5 KB + CoreMark 16.8 KB + RT-Thread ~15 KB = 54.3 KB  <  64 KB  ✓
```

之前被判"32 KB 墙不可行"的两条 —— **CoreMark 编进五子棋**、**RT-Thread + 五子棋共存** —— 都能做了。

#### 器件完全撑得住

| | |
|---|---|
| 当前 DRM 占用 | **53.5 / 415（12.9%）** |
| CPU 统一存储器 32 KB | ≈ 7~8 块 DRM |
| 扩到 64 KB | 再多 ≈ 8 块 → **61.5 / 415，余量 85%** |

#### [!] 最关键的约束：兼容区 `0x7FF0` 必须搬，而它散在很多地方

现在的映射（`rtl/bus/addr_map.vh`）：

```
RAM      0x0000_0000 ~ 0x0000_7FEF     字索引 addr[14:2]
兼容区   0x0000_7FF0 ~ 0x0000_7FFF     ← 【不可移动】
                                        CoreMark 的移植层把它硬编码了
```

**`0x7FF4`（mtime）/ `0x7FF8`（done）/ `0x7FFC`（UART TX）在 `core_portme.c`、
`ee_printf.c`、`start.S` 里都是字面量。** 扩 RAM 就要把它们搬到新地址，
**而这几个文件不搬干净就是静默错位**（CoreMark 跑不完、串口不出字，但没有任何编译错误）。

#### 改动清单（11 处，必须一次做对）

| # | 文件 | 改什么 |
|---|---|---|
| 1 | `rtl/bus/addr_map.vh` | `RAM_LAST_BYTE` `0x7FEF` → `0xFFEF`；兼容区移到新地址 |
| 2 | `rtl/mem/unified_mem.v` | `mem0[0:8191]` → `[0:16383]`（**`mem1` 同理**，双发射有两个阵列）|
| 3 | `rtl/core/core.v:555` | `imem_addr = fetch_addr[14:2]` → `[15:2]` |
| 4 | `rtl/bus/mem_bus.v:178` | `ram_word = mem_addr[14:2]` → `[15:2]` |
| 5 | `rtl/bus/mem_bus.v` | 兼容区的译码条件（`addr[15:8]==0x7F && addr[7:4]==0xF`）跟着改 |
| 6 | `scripts/coremark_port/core_portme.c` | `LEGACY_*` 地址 |
| 7 | `scripts/coremark_port/ee_printf.c` | 同上 |
| 8 | `scripts/coremark_port/start.S` | 同上 + **栈顶** |
| 9 | 各链接脚本（`coremark_port/link.ld`、`riscv_tests_link.ld`、`gomoku`、`rtthread`）| RAM 大小 + 栈顶 |
| 10 | `sim/mem_model.vh` | 仿真模型的 RAM 大小与地址切片（**不同步就会出现"仿真过、板上错"**）|
| 11 | `scripts/demo/addr_map.h` + `doc/spec.md` | 软件侧影子定义 + 文档映射表 |

#### 验收

- **riscv-tests 两条基线都跑**（双发射 / `-Single`）：49 PASS / 1 FAIL / 0 TIMEOUT
- **CoreMark 的 `Total ticks` 仍是 313,886**（扩内存不该改周期数）
- 五子棋 270 项单测
- **`+PROF` 的周期构成闭合式不变**：`288,056 + 20,720 + 9,396 + 45,343 = 363,515`
- 板上：CoreMark 跑完 + 五子棋能下
- **DRM 占用**从 53.5 涨到 61.5 左右（PDS 报告核对）

> [!] **别忘了 `mem1`。** 双发射有两个指令阵列（`mem0` / `mem1`），
> 只改一个的话，第二取指口读到的还是 32 KB 窗口 —— 症状是"某些地址取指错"，极难查。

### 3.8 [新] RT-Thread 版五子棋（依赖 G）

**为什么做**：① RT-Thread 是赛题明写的加分项（"运行操作系统"），现在只有独立的 ping/pong
演示，**把它和主应用合起来更有说服力**；② **它能顺便把 G3 做掉** ——
AI 放低优先级线程、渲染放高优先级线程，**AI 思考时画面照样刷新，不再卡 1.4 秒**。

**现有基础**（都已经在仓库里）：

- `scripts/rtthread/` —— RT-Thread Nano BSP，**已上板跑通**（banner + ping/pong 双线程）
- 五子棋的 `board.c` / `ai.c` / `render.c` / `game.c` / `input.c` **都是平台无关的纯逻辑**
  （文件头都写明了"一份源码两处用"），**不需要改**

**要做的事**：

| # | 做什么 |
|---|---|
| 1 | 把五子棋那 5 个 .c 加进 RT-Thread 的构建（`scripts/rtthread/build.ps1` 的源文件列表）|
| 2 | `main.c` 的主循环拆成线程：**渲染线程**（高优先级，跟 vblank 走）+ **AI 线程**（低优先级）+ **输入线程**（或并入渲染）|
| 3 | 线程间用信号量/邮箱传"该谁走、走到哪"，**别用共享全局裸读** |
| 4 | 显存写入仍要**在 vblank 窗口内**（这是老规矩，和有没有 RTOS 无关）|
| 5 | 栈：RT-Thread 线程栈 + 五子棋的 AI 递归栈，**32 KB 时代 AI 用了 6 KB 栈**，现在要重新分配 |

**验收**：

- RT-Thread banner 出来，且五子棋能下完整一局
- **AI 思考时画面不卡**（G3 的核心判据：AI 那 1.4 秒里光标仍在闪）
- 单测 270 项仍全过（那些是平台无关的，跑在 x86 上）
- 固件体积 ≤ 64 KB（扩内存后）

> [!] **风险在哪**：RT-Thread 的调度 + 显存的 vblank 时序，两个都是"时序敏感"的东西。
> **先让最简单的版本跑起来**（一个线程跑全部，只是挂了 RTOS），**再拆线程**。
> 一次做太多，出了问题分不清是 RTOS 的还是五子棋的。

```
片上总共 32KB 统一存储器
现在 静态占用 22,507 字节，栈余量 6,165（AI 的递归栈在里面）
mem.hex 11,072 行 —— 改了固件 expectLines 会变，守卫会拦，那是守卫在工作
```

**这堵 32KB 墙已经挡掉了两件事**：RT-Thread + 五子棋共存、CoreMark 编进五子棋。
**任何"加功能"的提案先算体积。**

> **[!] 但任务 G 就是来拆这堵墙的。** 扩到 64 KB 之后本节作废 —— 介时以
> `rtl/bus/addr_map.vh` 的 `RAM_LAST_BYTE` 和新栈顶为准。
> **在 G 完成之前，仍然按 32 KB 算体积。**

## 5. 纪律与坑（都是踩过的）

1. **两条并列回归基线**：双发射（默认）49/1/0 + 313,886 拍/迭代；
   单发射（`-Single`）49/1/0 + 363,515。**改 RTL 两条都跑。**
2. **[!] 变短/换行的字符串要整行重写** —— `render_text` 已改成整行写（先铺满空格再覆盖）。
   **菜单高亮移动时同理：上一处的高亮必须被擦掉。**
3. **[!] 板子上别按 SW2/D22** —— 那是 FPGA 配置键，按了设计被卸载（两灯全灭/屏幕黑/
   串口静默），必须重新下载位流。**真复位是 SW3。判据：按完两个 PLL 灯还亮不亮。**
4. **中文 Windows 的编码陷阱**：无 BOM 的 `.ps1` 被按 GBK 读 → 假语法错；
   原生命令输出被按 GBK 解码 → 中文文件名变乱码。样板见 `scripts/pack_for_teammate.ps1`。
5. **别碰 `rtl/`** —— 五子棋是纯固件。任务 A 的第 2 条要改 `video_top.v`，那要走 RTL 全量回归。
6. **串口可观测性**：任何玩家可感知的动作都要有输出，且**要先判断再打**
   （踩过：把 `AI thinking...` 挂在"长按"上，落子失败时打出却没有下文）。
