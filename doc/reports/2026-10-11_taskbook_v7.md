| 88.2768 MHz | 13.00 | 77.4473 MHz | **−1.584 ns** | 376 | −217.5 |

证据（**在磁盘上，`report_timing/` 被 gitignore，照项目既有做法由文档引用**）：
`pds/RV32I_1/report_timing/oclk_866mhz_FAIL_-2.127ns_1402endpoints.rtr`、

（同目录下先前的 `aext_85mhz_FAIL_-0.096ns.rtr` 也是这个做法 —— `git ls-files` 里 0 个。）

### 2.2 [!] 两条**容易读错报告**的地方（都核实过）

**(a) `clk|u_pll/u_gpll/CLKOUT0_Inferred` 就是 CPU 域，不是"PLL 里的东西"。**
它是 PDS 给 PLL 输出时钟自动起的名字，说的是"这条路径的时钟是谁"。**85 MHz 通过的那次，
同一行、同一个名字，是 `+0.544 ... 0 15571`。**

**(b) `Estimated < Requested` 不是"工具没生成请求的频率"，是恒等式：**

```
Estimated = 1 / (请求周期 − slack)
  85.00: 1/(11.764 − 0.544) = 89.1266 MHz   ← 与报告完全吻合
  86.61: 1/(11.546 + 2.127) = 73.1368 MHz   ← 完全吻合
  88.28: 1/(11.328 + 1.584) = 77.4472 MHz   ← 完全吻合
```

**负 slack 的定义就是 Estimated < Requested。** 它只反映"RTL 跑不跑得到"，
**永远不会因为 PLL 配置而不同** —— 所以"跑一遍各档看 `Requested == Estimated`"
这个判据本身是错的，且"PLL 能不能出 90/95/100 MHz"**不用综合就能回答**：
`VCO 1147.5 固定，CLKOUT0 = 1147.5 ÷ RATIO0`，`RATIO0` 合法范围 **1.0~128.0**，
90→12.75、95→12.079、100→11.475，**全都能出**。**别再花时间扫 PLL。**

### 2.3 [重点] 真正的结论：**不是"余量不够"，是工具在紧约束下换到更差的路线**

看 **place 阶段**（还没布线）的 8-seed 指标：

| 请求 | place 阶段 setup slack |
|---|---|
| 85.00 MHz | **−1.10 ~ −1.15** |
| 86.61 MHz | −4.08 ~ −4.55 |
| 88.27 MHz | −3.97 ~ −4.32 |

**周期只紧 0.22~0.43 ns，place 指标却差了约 3 ns —— 一个量级。**
而且 **86.61 比 88.27 还差** → **不是"越紧越差"的单调关系，是工具行为不稳定**。
所以中间档探索没有意义，**85.0051 就是唯一可用档位。**

> [!] 由此得到一条必须记住的反直觉结论：
> **请求 85 MHz 时 PDS 报的 Estimated 89.13 MHz 是乐观的**（那时约束不紧、工具有余力），
> **不能当"实际可达上限"用**。`CLAUDE.md` 约定 25 那句"收紧约束会让 PDS 更用力优化"
> **在逼近真实上限时会反转** —— 那时收紧只会更差。
> **报告里引用"可达频率"必须说清是在哪个请求值下测的。**

> [!] **真要上 90+ MHz，唯一的路是修关键路径本身** —— 现在最差路径是
> `u_multiplier/N15_m1/gopapm → mem_wb_alu_result[28]`（11 级逻辑，slack +0.544 ns）。
> 那是 §4 里的"路径优化"，**不是提频试验**。

## 5. 各任务细节

### A. Cache（不做 DDR3）—— **拿高阶任务①**

**定位（重要，别搞错）**：**这是为了"功能完整性 / 高阶①"，不是为了涨分。**
参考数据里那份用了 Cache 的设计，D-Cache 缺失率是 **0.000%**（5,135 次 / 5.66 亿次访问）
—— **Cache 对他们的分数没有贡献**。我们做它，是为了把赛题列出的条目补上。

**做法（唯一不掉分的架构）**：
```
CPU ──1 拍──> 片内 64 KB（栈 / 热数据 / CoreMark）  [保持不变]
     ├─ I 侧 ─> L1 I-Cache ─┐
     └─ D 侧 ─> L1 D-Cache ─┴─> 后端 = 【片内 BRAM】（不是 DDR3，用不到片外存储）
```
**把 CoreMark 的 `link.ld` 指到片内段 → 分数不变。**

**容量**：CoreMark 数据 **16.4 KB**、代码 **14.3 KB** → 建议 **I 16 KB + D 16 KB、2 路组相联**
（= 高阶①的字面要求）。**DRM 够**：现在用 85.5 / 415，还剩 **329.5**；32 KB 的 cache ≈ 15~16 个 DRM。

**缺失代价只有 1~2 拍**（检测缺失 + 从片内 BRAM 取回），所以即使命中率不完美，
代价也小（命中率 95% → 只掉 2.2%）。

> [!] **前置是 §5.A.0 ——`mem_ready` 收尾。别跳。**
> Cache 命中 1 拍、**缺失 2 拍**，**那本身就是可变延迟**，core 现在"假定访存恒 1 拍"
> 的假设会被打破。

#### A.0 前置：`mem_ready` / `mem_req` 收尾

`doc/reports/2026-09-27_bus_upgrade_plan.md` §3.5 记了三个实测坑：**前两个已修，
第三个（`id_redirect` 漏 `mem_ready`）当时未通过**。那次之后 **A 扩展 + 双发射
把这段逻辑整个重写过**（现在多了 `mc_stall`/`mem_ready_int`），
**所以坑 3 的状态要用当前 RTL 重新验一遍**，别沿用旧结论。

**验收（判据很硬，也最有价值）**：`+MEMWAIT=1` / `=2` / `=3` 下
**四条基线全部通过**（riscv-tests 双/单 49/1/0、自写测试 2/0、CoreMark 四个 CRC 不变）。
`sim/mem_model.vh` 已有 `+MEMWAIT=n` 开关，**不用写新工具**。

#### A.1 **[重点] 先花半天量时序，别直接写完整 Cache**

Cache 会把 **tag 比较 + way 选择 + 命中/缺失 mux** 压到访存关键路径上，
而余量只有 **4.6%**（+0.544 ns / 11.764 ns）。

**做法**：在 `mem_bus` 里插一级"**假 tag 比较 + way mux**"（行为上恒命中，
只是把延迟和逻辑加进路径），综合一次看时序报告。**半小时，零风险。**

- ✅ slack 仍为正 → 放心写完整 Cache
- ❌ slack 变负 → 二选一：改成**直接映射**（tag 比较只有一级），或接受降一档频率
  （但 §2 已证收紧约束会变差，**降频要同时把请求值与 4 处常量一起改**）

#### A.2 实现与验收

- I/D Cache 各 16 KB、2 路组相联、可编译开关（照 `DUAL_ISSUE` 的范例，**默认关**）
- 命中/缺失计数器 + 串口上报（**答辩要用**）
- **跑分一律用关掉的配置**报 324.5（即便只掉 1~2%，也没必要冒时序风险）
- 验收：开关打开时功能正确（四条基线全过）；关掉时数字与 324.5 逐位相同

#### A.3 答辩口径（**必须准备，否则会从加分变减分**）

> "我们**实现并评估**了 2 路组相联 I/D Cache。实测命中率 X%、缺失率 Y%。
> **但因为后端是单周期片内 BRAM，它是负收益，所以默认关闭。**
> 这是**评估后的架构判断**，不是没做。"

**这样做反而是加分的**（说明会做量化取舍）；而"做了并默认开着、分数掉了一截"是纯亏。

### E. 提高双发射配对率（低风险小收益）

实测：当前规则下约 **43.8% 的指令成对**（离线模型 p = 0.2802，双发射实测反推 41.6%，
模型误差 5%）。**放宽到理论极限（连"预测不跳转的分支"也配对）也只有 46.6%**
→ **全部收益约 3.5~7%**。

单独发射的原因：**`b_not_alu` 34.8%**（B 不是纯 ALU：load/store/branch 等不能当第二条）、
**`break_a` 31.2%**（A 是分支/跳转/系统指令）。

**做法**：`rtl/core/core.v` 的 `pair_now` —— 主要方向是**让 lane B 也能是 load/store**。
**收益上限就 3.5~7%，别为它做大改**；顺手做可以。

复现分析：

## 6. 纪律（**在 v6 §5 之上新增两条**）

沿用：每阶段上板验证 + 归档位流｜判据先行且可证伪｜一次只动一个子系统｜
特征做成可编译开关（照 `DUAL_ISSUE`）｜提交按里程碑拆、不自动 push。

**新增 1 · 提频无余量（§2，三点实测）**：`STATIC_RATIO0 = 13.5`（85.0051 MHz）
**是唯一可用档位** —— 13.25（86.61 MHz）实测 slack **−2.127 ns / 1402 端点失败**，
13.0（88.28 MHz）实测 **−1.584 ns / 376 端点失败**，**两个都比 85 差一个量级**。
**别再试任何档位，也别扫 PLL。** 真要动频率，记得 `CLAUDE.md` 约定 27 的
**4 处常量 + ITER + expectLines** 一起改。

**新增 2 · `-O3` 之后"每迭代周期数"与 ITER 相关**：

| 测量 | 拍/迭代 |
|---|---|
| 仿真 ITER=1 | 262,018.0 |
| 仿真 ITER=20 | 261,983.3 |
| 板上 ITER=3796 | **261,969.8** |

`-O3 -funroll-all-loops` 下 `for (i<ITERATIONS)` 有约 **48 拍的一次性开销**，
ITER=1 时没被摊掉。**算 ITER 要用大 ITER 下的值**（或更稳：用 `+PROF` 的
`region cycles` —— 它框的是纯 `iterate()`）。
> 判据不变：**`region cycles` 必须等于 `Total ticks`**（看到 `1` 就是
> `portable_init` 的打印踩了 `0xFFF4`，见约定 42）。

## 8.3 Cache（高阶任务①）—— 阶段性总结

### 8.3.1 实现了什么（代码已入库，默认关）

| 项 | 内容 |
|---|---|
| 模块 | `rtl/bus/cache_d.v` / `cache_i.v`，各 **16 KB / 2 路组相联 / NRU 替换** |
| 组织 | **行 = 1 字**；tag 阵列**组合读（LUTRAM）**——这是本设计能"命中 1 拍"的唯一原因 |
| 写策略 | 写通 + 写命中更新（`st_ld` / `fence.i` 语义与不开时逐位一致） |
| 开关 | `cpu_top.v` 的 `DCACHE_EN` / `ICACHE_EN`（**默认都是 0**）；仿真 `-DDCACHE/-DICACHE`、脚本 `-DCache/-ICache`；出位流 `build_bitstream.ps1 -Cache`（I+D）或 **`-DCacheOnly`（只开 D，新增）** |
| 计数 | 只读 MMIO `0x8000_0018~0x24`，固件在 CoreMark 报告后打 4 行 `[cache] D hits/miss/I hits/miss` |
| 复位 | 上电用 2048 拍清扫两个 tag 阵列的有效位（期间强制不命中）|

### 8.3.2 评估结论：**收益 0**（不是没做，是量化后判定）

* **根因**：后端是**单周期片内 BRAM** ⇒ **命中 1 拍 = 零收益**，Cache 的全部作用
  只是往访存/取指路径上加逻辑。（旁证：参考设计的 D-Cache 缺失率 **0.000%**。）
* 开 D-Cache 的实际代价：每迭代 241,633 → **241,998（+0.15%）**；四个 CRC 仍逐位一致。
* **"总线突发"已论证不做**：突发省的是"多次传输之间的地址/握手开销"，而这份开销我们**本来就没有**
  （见 `bus-` 升级计划 §6.1）—— 与"不做 Cache"是同一个理由。

### 8.3.3 [重点] 任务 C 之后重测：**D-Cache 已经不吃余量了，I-Cache 仍然不行**

同一套 `pds_shell -run pnr`，**只换开关**：

| 配置 | 任务 C **之前** | **任务 C 之后** |
|---|---|---|
| 都不开 | +0.544 | +0.045 |
| **只开 D-Cache** | （未单测）| **+0.151 ✓** |
| **I+D 全开** | −1.586 ✗ | **−0.857 ✗**（8 seed 全负）|

* **D-Cache 的代价消失了** —— 因为任务 C 让**快通路 load 不再占用 B 口**，
  tag 比较 + way mux **整体离开了访存关键路径**（§7.4 的假说成立）。
* **I-Cache 仍塞不进**：它的关键路径是
  `D-Cache 数据阵列 → 前递/分支/重定向 → fetch_addr → I-Cache tag 比较 → 命中`，
  **15~17 级、Route 占 63%（7.8 ns，是不开 Cache 时 3.5 ns 的两倍多）**。
  ⇒ **根因是布局拥塞（阵容挤开），不是某一级逻辑太深**；
  单跑 8 个 seed 全是负的 ⇒ **继续压逻辑没用**。
* **降频这条路不要再试**（约定 43 §7.2 已实测：请求 71.72 MHz 反而 slack −2.208）。

| **I+D 版** | `EARLY_LD=1` + 两个都开 @85 MHz | **不收敛**（−0.857）。要做需先解布局拥塞（见 8.5 P0-2）|

## 8.4 RVC（C 扩展）—— **[X] 已评估，不建议做**（新报告）

**报告：`doc/reports/2026-10-11_rvc_feasibility.md`**。摘要：

* 同一份 CoreMark 只换 `-march` 实测：**指令条数 7,885 → 7,939（+0.7%，几乎不变）**，
  只有**编码**变小（平均 4.00 → 3.30 字节/条，`.text` −17.3%）。
  **RVC 不删指令、只压编码** ⇒ 我们"单周期 BRAM 后端 + 双口取指（每拍 2 条）"两处都
  已经不吃密度红利 ⇒ **分数收益 ≈ 0**，而代价是前端改造（`+4`→`+2/+4` 散布全设计、
  取指对齐器、双发射配对重做）+ 时序风险。
* **对手领先的真正原因不是 RVC，是 IPC**：把拍/迭代折算成 IPC ——
  A 组 ≈ **1.06**、我们 ≈ **0.89**（**+19%**）。差的是**发射效率**，不是指令编码。
* 唯一"非分数"价值：代码体积 −17%，以后要把更大应用塞进 64 KB 时可能救急
  （现在 RT-Thread+五子棋镜像 21.5 KB / 32.8 KB，**还没撞墙**）。

## 8.6 纪律（交接必看，都是踩过的）

1. **综合前 `git status` + 核开关**。本轮踩过：`rtl/top/cpu_top.v` 被换回任务 C **之前**的版本，
   照那样综合会**静默产出不含任务 C 的位流**（`core`/`mem_bus` 双双退回默认 0，
   **日志、文件名、DESIGN_REV 全都看不出来**）。
   **唯一骗不了人的判据是拍数**：241,633 vs 262,018 差 7.8%。
2. **每个位流都归档**到 `pds/RV32I_1/bitstreams/` + 在 `bitstreams/README.md` 加一行
   （md5 + 用途 + 是否上过板）。`.sbit` 本身 gitignore（9 MB/个），**只有索引进库**。
   **别烧 `generate_bitstream/cpu_top_board.sbit`** —— 那个名字会被任何一次综合覆盖（约定 23）。
3. **改 RTL 后 `DESIGN_REV` 加一**（现在 `0x2026_1015`，`csr_file.v`），串口首行自证。
4. **四条回归**：`run_riscv_tests.ps1`（49/1/0）、`run_own_tests.ps1`（2/0）、
   AMO（`tb_amo_int.v` + `amo_int.S`）、`run_coremark.ps1`（四 CRC + `+MEMWAIT=1/2/3`）。
5. **换 ITER / 换 Cache 开关 = 换固件 = 必须重综合**（存储器是 BRAM 初始化、没有加载器）。
6. **时序余量只剩 0.4%**：任何改动都要先问"它落不落在最差那条链上"，
   并按 `AGU_PROBE` 的做法**先插假路径综合一次**（一次综合换掉几周的错误投入）。
7. **[!] 同一个 PDS 工程目录【不能并发综合】**（2026-10-11 实踩）。

   > 一致（Cache 关 +0.045 / 只 D +0.151 / I+D −0.86），以及
