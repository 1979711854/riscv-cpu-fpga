## 2. 【重要】提频试验：**85 MHz 是上限，别再试**

`pds/RV32I_1/ipcore/pll/pll.idf` 的 `STATIC_RATIO0` 13.5 → 13.0（85.00 → 88.27 MHz），
重新生成 PLL 并重综合，**实测失败**：

```
clk|u_pll/u_gpll/CLKOUT0_Inferred
    Requested 88.2768 MHz  ->  Estimated 77.4473 MHz   Slack -1.584 ns
```

**[重点] 这不是"余量不够"，是工具行为。** 看 place 阶段的指标：

| 综合 | 8 个 seed 的 place slack |
|---|---|
| 请求 85.00 MHz | **−1.10 ~ −1.15** |
| 请求 88.27 MHz | **−3.97 ~ −4.32** |

**周期只缩了 0.43 ns，指标却恶化了 2.9 ns** —— 收紧约束让 PDS 布出了更差的结果。
按这个比例，中间档 86.6 MHz（周期只差 0.22 ns）也会掉进同一个坑（指标仍会恶化约 1.5 ns
→ 预估 slack ≈ −0.95）。**所以 13.0 / 13.25 都不必再试。**

> [!] 这次试验有一个**反直觉但必须记住的结论**：
> 请求 85 MHz 时 PDS 报的 **Estimated 89.13 MHz 是乐观的**（那时约束不紧、工具有余力），
> **不能当"实际可达上限"用**。`CLAUDE.md` 约定 25 里"收紧约束会让 PDS 更用力优化"
> 这条**在逼近真实上限时会反转** —— 那时收紧只会更差。
> **报告里引用"可达频率"时要说清是在哪个请求值下测的。**

## 5. 各任务细节

### A. Cache（不做 DDR3）—— **拿高阶任务①**

**定位（重要，别搞错）**：**这是为了"功能完整性 / 高阶①"，不是为了涨分。**
参考数据里那份用了 Cache 的设计，D-Cache 缺失率是 **0.000%**（5,135 次 / 5.66 亿次访问）
—— **Cache 对他们的分数没有贡献**。我们做它，是为了把赛题列出的条目补上。

**做法（唯一不掉分的架构）**：
```
CPU ──1 拍──> 片内 64 KB（栈 / 热数据 / CoreMark）  [保持不变]
     ├─ I 侧 ─> L1 I-Cache ─┐
     └─ D 侧 ─> L1 D-Cache ─┴─> 后端 = 【片内 BRAM】（不是 DDR3，用不到片外存储）
```
**把 CoreMark 的 `link.ld` 指到片内段 → 分数不变。**

**容量**：CoreMark 数据 **16.4 KB**、代码 **14.3 KB** → 建议 **I 16 KB + D 16 KB、2 路组相联**
（= 高阶①的字面要求）。**DRM 够**：现在用 85.5 / 415，还剩 **329.5**；32 KB 的 cache ≈ 15~16 个 DRM。

**缺失代价只有 1~2 拍**（检测缺失 + 从片内 BRAM 取回），所以即使命中率不完美，
代价也小（命中率 95% → 只掉 2.2%）。

> [!] **前置是 §5.A.0 ——`mem_ready` 收尾。别跳。**
> Cache 命中 1 拍、**缺失 2 拍**，**那本身就是可变延迟**，core 现在"假定访存恒 1 拍"
> 的假设会被打破。

#### A.0 前置：`mem_ready` / `mem_req` 收尾

`doc/reports/2026-09-27_bus_upgrade_plan.md` §3.5 记了三个实测坑：**前两个已修，
第三个（`id_redirect` 漏 `mem_ready`）当时未通过**。那次之后 **A 扩展 + 双发射
把这段逻辑整个重写过**（现在多了 `mc_stall`/`mem_ready_int`），
**所以坑 3 的状态要用当前 RTL 重新验一遍**，别沿用旧结论。

**验收（判据很硬，也最有价值）**：`+MEMWAIT=1` / `=2` / `=3` 下
**四条基线全部通过**（riscv-tests 双/单 49/1/0、自写测试 2/0、CoreMark 四个 CRC 不变）。
`sim/mem_model.vh` 已有 `+MEMWAIT=n` 开关，**不用写新工具**。

#### A.1 **[重点] 先花半天量时序，别直接写完整 Cache**

Cache 会把 **tag 比较 + way 选择 + 命中/缺失 mux** 压到访存关键路径上，
而余量只有 **4.6%**（+0.544 ns / 11.764 ns）。

**做法**：在 `mem_bus` 里插一级"**假 tag 比较 + way mux**"（行为上恒命中，
只是把延迟和逻辑加进路径），综合一次看时序报告。**半小时，零风险。**

- ✅ slack 仍为正 → 放心写完整 Cache
- ❌ slack 变负 → 二选一：改成**直接映射**（tag 比较只有一级），或接受降一档频率
  （但 §2 已证收紧约束会变差，**降频要同时把请求值与 4 处常量一起改**）

#### A.2 实现与验收

- I/D Cache 各 16 KB、2 路组相联、可编译开关（照 `DUAL_ISSUE` 的范例，**默认关**）
- 命中/缺失计数器 + 串口上报（**答辩要用**）
- **跑分一律用关掉的配置**报 324.5（即便只掉 1~2%，也没必要冒时序风险）
- 验收：开关打开时功能正确（四条基线全过）；关掉时数字与 324.5 逐位相同

#### A.3 答辩口径（**必须准备，否则会从加分变减分**）

> "我们**实现并评估**了 2 路组相联 I/D Cache。实测命中率 X%、缺失率 Y%。
> **但因为后端是单周期片内 BRAM，它是负收益，所以默认关闭。**
> 这是**评估后的架构判断**，不是没做。"

**这样做反而是加分的**（说明会做量化取舍）；而"做了并默认开着、分数掉了一截"是纯亏。

### E. 提高双发射配对率（低风险小收益）

实测：当前规则下约 **43.8% 的指令成对**（离线模型 p = 0.2802，双发射实测反推 41.6%，
模型误差 5%）。**放宽到理论极限（连"预测不跳转的分支"也配对）也只有 46.6%**
→ **全部收益约 3.5~7%**。

单独发射的原因：**`b_not_alu` 34.8%**（B 不是纯 ALU：load/store/branch 等不能当第二条）、
**`break_a` 31.2%**（A 是分支/跳转/系统指令）。

**做法**：`rtl/core/core.v` 的 `pair_now` —— 主要方向是**让 lane B 也能是 load/store**。
**收益上限就 3.5~7%，别为它做大改**；顺手做可以。

复现分析：
```powershell
# [!] 必须用【单发射】跑 +PAIRTRACE —— 那个探针是单沿的，双发射下看不见 lane B
scripts\run_coremark.ps1 -Iter 1 -Single
cd sim
vvp tb_coremark_single.vvp +ITER=1 +PAIRTRACE +IMEM=programs/imem.hex +DMEM=programs/dmem.hex
python ..\scripts\pair_analyze.py programs/pairtrace.txt
# 判据：pairtrace.txt 行数必须是 288,056
```

## 6. 纪律（**在 v6 §5 之上新增两条**）

沿用：每阶段上板验证 + 归档位流｜判据先行且可证伪｜一次只动一个子系统｜
特征做成可编译开关（照 `DUAL_ISSUE`）｜提交按里程碑拆、不自动 push。

**新增 1 · 提频无余量（§2）**：`STATIC_RATIO0 = 13.5`（85.0051 MHz）**就是当前上限**，
13.0/13.25 都已推理为不可行。**别再花时间试**。真要动频率，记得
`CLAUDE.md` 约定 27 的 **4 处常量 + ITER + expectLines** 一起改。

**新增 2 · `-O3` 之后"每迭代周期数"与 ITER 相关**：

| 测量 | 拍/迭代 |
|---|---|
| 仿真 ITER=1 | 262,018.0 |
| 仿真 ITER=20 | 261,983.3 |
| 板上 ITER=3796 | **261,969.8** |

`-O3 -funroll-all-loops` 下 `for (i<ITERATIONS)` 有约 **48 拍的一次性开销**，
ITER=1 时没被摊掉。**算 ITER 要用大 ITER 下的值**（或更稳：用 `+PROF` 的
`region cycles` —— 它框的是纯 `iterate()`）。
> 判据不变：**`region cycles` 必须等于 `Total ticks`**（看到 `1` 就是
> `portable_init` 的打印踩了 `0xFFF4`，见约定 42）。
