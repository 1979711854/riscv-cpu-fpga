### 1.1 [重点] 评分公式其实是 CoreMark/MHz

赛题原文（选题一 · 四、性能测评标准）：

```
Score = CoreMark_Iterations / (Total_Time × Frequency)        ……(1)
(1) 执行效率：比较 CoreMark/MHz。
(2) 时钟频率：在满足时钟约束的前提下，处理器能达到的最高工作频率。
(3) 资源效率：计算 CoreMark / LUTs。
```

公式(1) 化简 = `Iterations ÷ 总周期数` = **1 / 每迭代周期数** ⇒ **频率被除掉了**。

**⇒ 三条指标的杠杆是分开的：**

| 指标 | 受什么影响 | 我们的现状 |
|---|---|---|
| **(1) 执行效率** | **只看每迭代周期数** | 无 Cache / 只开 D **4.139**；**I+D 4.099（仅 −0.96%）** |
| (2) 最高工作频率 | 关键路径 | 无 Cache ~85.3 MHz；**I+D ~80.1 MHz（−6.1%）** |
| (3) CoreMark/LUTs | 分子 + LUT 面积 | 0.0509（无 Cache，6909 LUT）；**0.0397（I+D，7896 LUT，−22%）** |

> [!] **指标(2) 问的是"能达到的最高工作频率"，不是"你跑多少"。**
> 项目一直奉行"留 7% 余量"的策略，在这条指标下需要重新权衡。
>
> [!] **合规点**：公式里 `Total_Time × Frequency` 必须等于实测 `Total ticks`
> ⇒ **固件的 `EE_TICKS_PER_SEC` 必须等于实际板上时钟**（约定 50 那套不能破）。
> [!] **口径歧义（待定）**：指标(3) 的"CoreMark"是指公式(1) 的值还是 iterations/sec？
> 两种算法结论差 10 个百分点（−13.6% vs −22%）。**建议报告里两种都摆出来**，
> 并注明各自口径 —— 这是本项目一贯做法。

### 1.2 [重点] 赛题点名 `BTB`，我们只有 `BHT`

原文：`高级控制逻辑：实现动态分支预测器（如 BTB）以及完整的 RISC-V 异常/中断处理机制`

`BTB` = Branch **Target** Buffer（**目标**预测）；我们的 `BHT`（256 项 2 位饱和计数器、带 tag）
= **方向**预测。`CLAUDE.md` 自己写着"**只预测条件分支方向**；`jal` 走静态预测、
**`jalr` 不预测**"。

- **风险**：评委追问"你的 BTB 呢"——现在答不上。
- **机会**：`jalr` 目前不预测 ⇒ 每次 `jalr` 都走 EX 冲刷。BTB（带目标）可让 `jalr` 也预测。
- **附带**：I+D 的关键路径是
  `D-Cache BRAM(tco) → 前递 → 分支解析/重定向 → PC mux → I-Cache 地址 → I-Cache BRAM(tco) → tag 比较 → way mux → 命中`
  —— **"重定向"正压在链中段**，BTB 有把它摘掉的可能。

### 1.3 高阶任务① 还有一半：`优化总线突发传输效率`

原文：`存储系统优化：设计并实现支持 2 路组相联的指令与数据 Cache 系统，优化总线突发传输效率。`

- 2 路组相联 I/D Cache → **[OK] 已实现并上板**

虽然后端是单周期片内 BRAM、**性能收益接近 0**，但**赛题明文要求，做了就是功能分**。

> **[重点] `乘法器去阻塞` 现在是收益最大、风险最低的第一候选（+4.0%），且是纯周期收益
> （赛题公式(1) 直接受益，与频率无关）。**
> 依据：`core.v:930` `mc_stall = div_stall || mul_stall`；`tb_coremark.v:437` 注释原文
> "**乘法的 1 拍停顿**"；本次实测 `region mul exec = 9,396`，与单发射闭合式的

> 换成"2 条在飞"的冒险/前递跟踪。**乘法器本体不动 ⇒ 时序风险低。**
> 判据：四条并列基线 + `region mul exec` 仍在 9,396 左右而 `region cycles` 掉下来。

- **必须有目标校验**：预测目标与实际不符时冲刷（当年特意用保守版绕开的正是这个坑）

**第二层：频率收益（先验证，别先实现）**
- **核心疑问**：BTB 是用 PC 索引的 ⇒ 路径变成 `BTB RAM → PC mux → I-Cache 地址 → I-Cache tag → 命中`，
  **仍然是"两个 RAM 串一拍"**，只是把前面的 D-Cache 换成了 BTB。
- ⇒ **能不能真变短，只取决于 BTB 是否足够小（32~64 项）以便进 LUTRAM 并贴着 PC mux。**
  若 BTB 也做 BRAM，**很可能等于没改善**。
- **做法**：照 `doc/reports/2026-10-11_taskC_agu_probe.md` 的方法，**先插假 tag 探针量 Δ ns**，
  再决定做不做。（器件 LUTRAM 只用了 **560 / 39,500**，余量巨大。）

### P0-B 总线突发（高阶① 后半，明文缺口）

- 范围：burst 接口（INCR/WRAP）+ Cache line fill 走突发 + 报告里给出传输效率对比
- **[!] 2026-10-12 读 `cache_i.v` 后确认：我们当前**无处可挂** ——
  `cache_i.v:3` 写明「**行 = 1 字**」⇒ 没有多字行 ⇒ 没有行填充 ⇒ 没有突发可优化。
  且 `cache_i.v:251`：`assign rdata = (hit0_r|hit1_r) ? (hit0_r ? d0_q : d1_q) : bram_rdata;`
  —— **后端 BRAM 每拍都在读同一地址、miss 直接零代价回退** ⇒ 这套存储系统**没有慢速后端可藏延迟**，
  Cache 在这里既不省带宽也不省延迟（与约定 43 一致）。**
- ⇒ 要交这条**只能人为构造**：把 Cache 改成多字行（如 4 字/行），miss 走一次突发填充。
  代价：**miss 惩罚变长 ⇒ 公式(1) 变差**（量级：I miss 2,455 次/迭代 × 多花 1~3 拍 = **+0.1~3% 周期**）。
- **性能收益预期为负或零 ⇒ 这是功能分，不是性能分。** 报告里要如实写
  （本项目一贯"没收益就说没收益"），并且**实现时要把 burst 逻辑放在关键路径之外**
  （只在行填充时激活，不插进 load/store 或取指通路）。
- 判据：功能可演示 + 四条回归不变 + `+PROF` region cycles **不涨**（涨了就要在报告里说明代价）

> - 「way mux + `bram_rdata` 回退 mux」走的是另一条路（`hit0_r/d0_q → rdata → IF/ID`），**不在"地址→命中"上**

> ⇒ **"取指队列 / I-Cache 访问流水化"打的也是短段，收益同样有限**。

**真正的长段在 `fetch_addr` 这个组合 mux 之前**：`EX 的分支/重定向解析（含从 D-Cache 数据前递过来）→ PC mux`。
`fetch_addr` 的 mux 里挂着 `ex_flush` / `ex_mispred` / `trap`，**全都来自 EX**。

⇒ **候选收敛为三条（且都要先做假路径探针）**：

| 候选 | 打在哪一段 | 我的判断 |
|---|---|---|
| **BTB（带目标）** | 把 `EX → PC mux` 从环里摘出去 | **最对症**（详见 P0-A 第二层） |
| **定点插拍：`load → 分支/jalr`** | 链头（D-Cache 数据 → 前递） | 便宜，代价 ∝ 这类实例数 |
| ~~I-Cache 内部削 / 取指队列~~ | 链尾短段 | **降级**（收益小，还可能涨周期） |

## 6. 纪律（I+D 强制保留后新增的重点）

1. **必须显式带 `-DCache -ICache -EarlyLd`**，并核对 vvp 首行 `SIM CONFIG:`（约定 47）。
2. **ITER 按 243,933 算**（I+D 口径），不是 241,633。85 MHz 下 ≈ **4077**。
3. **改频率是"四处常量 + ITER + 全部还原"的事务**（约定 50）：
   `pll.idf` 的 `STATIC_RATIO0` → `ip_generate.exe` 重生成 `pll.v` → `cpu_top_board.v` 的 `UART_DIV`
   → `core_portme.c` 的 `EE_TICKS_PER_SEC` → 重算 ITER。**跑完全部还原。**
4. **归档位流前 grep 网表自证 `dcache` / `icache` 都在**（约定 46 —— 脚本打印过但没改文件真发生过）。
5. **改 RTL 就递增 `DESIGN_REV`**（`csr_file.v`），否则事后分不出烧的是哪版。
6. **回归四条并列基线**：241,633（默认）/ 262,018（`EARLY_LD=0`）/ 312,428（`-Single`）/ 243,933（带 Cache）。
7. **`Total_Time × Frequency == Total ticks`** ⇒ `EE_TICKS_PER_SEC` 必须是实际板上时钟（赛题公式合规）。
