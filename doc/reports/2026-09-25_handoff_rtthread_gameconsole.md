## 1. 开工前必须知道的现状

### 1.1 CPU 能力边界（**这些是硬约束，先记牢**）

```
RV32I + M 扩展 · 5 级流水线（IF/ID/EX/MEM/WB）
前递（EX/MEM、MEM/WB 两级）+ load-use 停顿 + 多拍除法器
统一存储器（指令+数据共用一块双端口 BRAM）
完整异常/中断（CSR + mret + 六类同步异常 + CLINT 定时器中断）
[!] 只支持 M 模式（MPP 硬连线为 11）—— 没有 S/U 模式
集成 UART（收发）/ GPIO / 存储总线
```

> [!] **只支持 M 模式**，这一条决定了 RT-Thread 必须用 **M 模式 port**（§3.2）。

### 1.2 内存与地址映射（**32 KB 是本次最大的约束**）

来源：`rtl/bus/addr_map.vh`（SoC 唯一真相，改这里要同步改另外两处）

| 区域 | 地址 | 说明 |
|---|---|---|
| **RAM** | `0x0000_0000` ~ `0x0000_7FEF` | **32 KB**（8192 word × 32 bit）**← 硬上限** |
| 兼容区 | `0x0000_7FF0` ~ `0x0000_7FFF` | 0x7FF4 周期计数器 / 0x7FF8 done / 0x7FFC UART 发字符（CoreMark 硬编码，**不可移动**）|
| GPIO | `0x8000_0000` | W LED[7:0] / R {key[7:0], led[7:0]} |
| UART_TX | `0x8000_0008` | W 发一个字符 |
| UART_RX | `0x8000_000C` | R {valid, 23'b0, data[7:0]}，读清 valid |
| MTIME | `0x8000_0010` | R 周期计数器 [31:0] = `mtime` |
| MTIMECMP | `0x8000_0014` | W/R，复位值全 1；`mtime >= mtimecmp` → MTIP 拉高 |

> [!] **32 KB 装不下帧缓冲。** 240×240 的 16bpp 帧缓冲要 **115 KB**。
> 所以游戏必须像 NES 那样 **tile/sprite 实时合成，不存整帧** —— 详见 §5.2。
>
> 栈顶必须 ≤ `0x7FF0`（CoreMark 用 0x7000）。给 RT-Thread 划内存区时注意别压到兼容区。

### 1.3 已实现的 CSR（**RT-Thread 移植可行性全系于此**）

来源：`rtl/core/csr_file.v`

| CSR | 地址 | RT-Thread 用途 | |

## 2. 任务 A【P0】显示外设 —— 先定方案

**当前设计一个显示外设都没有**（只有 GPIO/UART）。这是"游戏机"最大的缺口。

### 2.1 四条路线的对比（**先看完再决定**）

| 方案 | 要买什么 | RTL 工作量 | 效果 | 风险 | 建议 |
|---|---|---|---|---|---|
| **A1. SPI TFT 小屏** | **30~60 元**（2.4"/2.8" ILI9341 或 ST7789 模块）| **小**：SPI 主控（几十行）+ 初始化序列 + 刷屏 | 240×320 或 240×240 彩色，**够玩游戏** | **低** —— SPI 时序宽松，几 MHz 随便跑 | **[重点] 推荐** |
| **A2. 板载 HDMI 输出** | 不用买 | **大**：TMDS 编码 + 像素时钟 + 时序发生器（或调 IP）| 720p/1080p，最"游戏机" | **中高** —— 时序收敛难，参考设计少 | 有余力再说 |
| **A3. 串口传帧到 PC** | 不用买 | **很小**：MCU 侧把帧数据写 UART，PC 端 Python 显示 | 低分辨率、帧率受波特率限 | **低** | **先用它把游戏逻辑跑通** |
| **A4. 以太网传帧到 PC** | 不用买 | 中：需要 MAC（PHY 是 RTL8211F）| 中等 | 中 | 不如 A1 |
| A5. 只用现有 LED/按键 | 不用买 | 零 | 只能玩"贪吃蛇"级 | 无 | 保底演示 |

> **推荐组合：A3（先把游戏跑通）→ A1（上真屏）。**
> A3 不需要任何硬件，一两天就能看到东西在动；A1 是最平衡的"真游戏机"方案。

### 2.2 A1 的具体做法（SPI TFT）

1. **买**：ILI9341（2.4"/2.8"，320×240）或 ST7789（1.3"/2.0"，240×240）模块。
   选带 **电平转换/3.3V 兼容**的（FPGA IO 是 3.3V，屏多是 3.3V，一般直连）。
2. **接线**：`SCLK` / `MOSI` / `CS` / `DC`（数据/命令）+ `RST`，共 5~6 根
   —— 从 **扩展 IO / FMC 扩展口** 里挑空闲引脚（手册 §2.2.8 扩展 IO、§3.6 FMC 连接器）。
3. **RTL**：新增 `rtl/periph/spi_master.v`，挂到 `mem_bus` 上（照抄 `uart_tx.v` 的挂法）
   —— 地址映射要在**三处同步改**（`rtl/bus/addr_map.vh`、`scripts/demo/addr_map.h`、`doc/spec.md`）。
4. **`.fdc`**：给新引脚加约束（照抄现有 LED/KEY 的写法）。
5. **软件**：写 ILI9341 初始化序列 + 画点/画矩形/贴图函数。

> [!] **别做"全屏帧缓冲"** —— 32 KB 装不下（§1.2）。
> 用 **tile + sprite 实时合成**：屏幕按行扫描，每行现算该行属于哪些 tile/角色，
> 算完直接推给屏。这样内存只需要 **tile 表 + 角色表**（几 KB）。详见 §5.2。

### 2.3 A2（HDMI）为什么标"工作量大"

- HDMI 要 **TMDS 差分编码**，通常用 FPGA 的 **HSST 高速收发器**（本板有 8 路，6.6 Gbps）
- 需要**像素时钟**（720p = 74.25 MHz > 我们 54 MHz 的可达频率）→ 要么降分辨率，要么再提频
- Pango 的 IP Compiler 里有没有现成 HDMI IP，**先查**；没有就得手写，那是另一个项目的工作量
- **结论：除非时间非常充裕，不要选它。**

### 2.4 A5（保底方案）—— 别小看它

如果屏买不到/来不及，**LED + 按键也能做出可演示的游戏**：
贪吃蛇、打砖块（8×8 LED 点阵）、猜数字。**先保证有东西能演示**，再谈体验。

## 4. 任务 C【P1】游戏本体

### 4.1 [!] **不能跑 NES 模拟器**（先说清楚，别走弯路）

- NES 模拟器 + ROM 至少要 **几百 KB 内存**，我们只有 **32 KB** —— **装不下**
- 板子上的 **1 GB DDR3 是另一个项目的工作量**（§4.4）
- **所以：自己写一个精简的平台跳跃游戏。** NES 上跑《超级马力欧》是 40 KB ROM + 2 KB RAM，
  那是**专用硬件 + 手写汇编 + tile 渲染**的结果 —— 我们可以借鉴它的**架构**，
  但要用 C 重写一个**规模和难度都小得多**的版本。

### 4.2 游戏的技术架构（**照 NES 的思路，这是 32 KB 下唯一可行的做法**）

```
不用帧缓冲，用 tile + sprite 实时合成：

  背景层：一张 tile 地图（比如 16×16 像素的 tile，屏幕 240×240 = 15×15 个 tile）
          → 存"每个位置放哪个 tile"的索引表（15×15 = 225 字节！）
          → tile 图案本身存在 ROM 里（几个 tile 合起来几 KB）
  角色层：几个 sprite（16×16 或 16×24），每个存 位置(x,y) + 图案号 + 状态
          → 5 个角色 × 8 字节 = 40 字节

  渲染：按扫描线输出时，现算该行属于哪些 tile、有没有角色覆盖 → 直接推给屏
        （SPI 屏有自己的显存，所以"推过去"就完事）
```

**内存占用可以压到几 KB**，而不是 115 KB。

### 4.3 建议的游戏规模（**先做小，做完了再加**）

| 阶段 | 内容 |
|---|---|
| **v0（先跑通）** | 一个方块在屏幕上左右移动 + 跳跃受重力。**验证显示链路和定时** |
| **v1（可演示）** | 加滚动地图、平台碰撞、1~2 个敌人、能吃的东西 |
| **v2（像样）** | 多关卡、得分、音效（P2）、SD 卡存进度（P2）|

## 5. 加分项【P2，有余力再说】

| 项 | 为什么先不做 |
|---|---|
| **DDR3 扩展内存** | 板上有 1 GB DDR3（1066 Mbps、32-bit），但**要写/调一个 DDR3 控制器**（Pango 有 IP，但集成涉及新总线、仲裁、1066 Mbps 时序收敛）—— **本身就是另一个项目的工作量**。32 KB 够跑 RT-Thread + 小游戏，**先证明场景成立，再考虑扩内存** |
| HDMI 输出 | 见 §2.3 |
| 音频 | 板上音频模块接口，需要 PWM/DAC + 音频数据流 |
| SD 卡存档 | 需要 SPI/SD 控制器 + 文件系统，Nano 里没有文件系统 |
| 以太网 | 需要 MAC，工作量中偏大 |

## 7. 卡住了怎么办（**先看这张表**）

| 现象 | 原因（都是踩过的）|
|---|---|
| 板上跑的还是旧程序 | **PDS 不检查 `mem.hex` 时间戳**。用 `scripts\build_bitstream.ps1`，它带 sha256 校验。别手工 `run_coremark` + `sync_firmware` 两步走 |
| 串口没输出 | **只插了 Jtag，没插 USB-UART** —— 是两块独立接口，要插**两根** USB 线 |
| 烧完是别的程序 | Programmer 会记住上次分配的文件；**每次都要重新 `Operations → Assign New Configuration File`**（见 `doc/board_bringup.md`）|
| 综合报 `pll` 是黑盒 | PLL IP 必须以 **IP 源文件**形式加进 `.pds`（`wgt_my_ips_src`），不能当普通 `.v` 加 |
| 板上什么都不跑、零报错 | PDS 工程目录里 `mem.hex` 缺失或过期。PDS 只报一行 `Cannot open specified data file` 然后**照常出比特流** |
| 加了新外设后地址对不上 | 地址映射要在**三处同步改**：`rtl/bus/addr_map.vh` + `scripts/demo/addr_map.h` + `doc/spec.md` |
| 外设把 X 放上总线 | X 被 CPU 读走会污染分支比较，控制流会走错。**外设任何时候都不该输出 X** |
| RT-Thread 起来就崩 | 先查 `mtvec` 的 direct 模式假设、`mstatus.MIE` 的切换、栈顶是否越过 `0x7FF0` |

**更全的坑见 `CLAUDE.md` 的「关键约定」29 条。**
