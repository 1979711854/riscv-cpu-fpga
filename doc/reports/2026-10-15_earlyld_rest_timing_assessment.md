# 约定 45 剩余两项：时序可行性评估（2026-10-15）

> 触发：用户问"约定 45 剩余两项（`EARLY_LD` 扩展）能不能做"，并按 10-14 交接书 §5 的排序
> 把它列为候选。这份是**判据先行的评估**——不写代码，先把"能不能做"定下来。
>
> **结论：在当前 rev1022 的 P&R 结果上，两项都做不了** —— 而且原因比"余量小"更具体：
> **它们要加的位置，正好就是当前关键路径本身。**
> 附带把**真正的抓手**定位清楚了（是布线/布局，不是逻辑深度）。

---

## 1. 当前关键路径（rev1022，本轮实测，逐段）

来源：`pds/RV32I_1/report_timing/cpu_top_board.rtr` 的
`u_pll → u_pll` 最差路径（`+0.034 ns / 0 失败端点 / 20,507`，请求 85.0051 → 实测 85.2515 MHz）。

```
D18(clk) → clk_ibuf → GPLL → clkbufg(fanout 3320)
  → BRAM 阵列 mem0_3_1 读出            tco 1.644
  → ram_rdata_eff[27]        net  1.925   ← ★ fanout = 1
  → u_amo/amo_rdata_r[27]         0.101        (AMO 读数据 mux)
  → mem_rdata[27]            net  0.653
  → load_half[11]                 0.188        ┐
  → load_data_2[3]                0.235        ┘ load 解包
  → _N7352                   net  0.812
  → rs1_val[3]               net  0.263   ← ★ 前递结果
  → N552 eq 进位链            0.386+0.090+0.090+0.211   (分支比较器)
  → branch_taken             net  0.129
  → ex_resolve_taken         net  0.482   ← ★ fanout 17
  → if_addr_d[2]                  0.223
  → imem_addr[0]             net  0.665   ← ★ fanout 18
  → imem_addr2[12]           net  1.122   ← ★ fanout 16
  → BRAM 阵列 mem1_2_3 地址口 ADB0[13]
```

**数据路径 11.234 ns（周期 11.764 ns 中）**，其中：

| 类别 | 约计 |
|---|---|
| 逻辑（`td`/`tco`，不含时钟树）| ≈ 4.5 ns |
| **网线（route）** | **≈ 6.7 ns（约 60%）** |

> **[重点] 这条链与会话状态 §4.2（62 MHz 时代）记的那条【逐段一致】**：
> "BRAM 读出 → 装载数据/写回 → 前递 mux → `rs2_val` → `branch_taken` → `ex_resolve_taken`
> → 预测重定向 → `fetch_addr` → `if_addr_d` → `imem_addr` → BRAM 地址口"
> ⇒ **从 62 MHz 到 rev1022，瓶颈一直是同一条链，只是时钟从 62 提到 85。**
> （当年那句"下一步的抓手是高扇出复制与布局，不是加流水线级数"**今天仍然成立**。）

---

## 2. 为什么两项都做不了

| 项 | 要做什么 | 加在哪里 | 与关键路径的关系 |
|---|---|---|---|
| **基址在 EX**（4,744 拍 / 1.81%）| 真加 **EX→ID 前递**（两级加法器串成一条链）| 喂 `ld_base` → `ld_id_addr = ld_base + imm` | **就是路径上的 `… → load_data → rs1_val → …` 那一段的邻居**；前递 mux 与加法器都在 ID 级，而输入来自 EX 的 load 数据 |
| **紧前是 store**（1,869 拍 / 0.71%）| **store→load 字节合并旁路** | load 数据返回路径 | **正好压在 `load_half/load_data` 那两级上**（路径里明确出现）|

**余量只有 +0.034 ns（周期的 0.29%）**，而两项的插入点**都在关键路径上**——
不是"离得近"，是**就在那条路上**。⇒ **在当前的 P&R 结果上，两项都无法落地。**

> [!] 而且 `+0.034 ns` **远低于本项目的综合噪声（≈5.7%）**：换 seed 有可能直接翻负。
> 也就是说现在这个数本身就在"运气"区间里。

---

## 3. [重点] 真正的抓手：**网线，不是逻辑**

路径里最刺眼的一根：

```
ram_rdata_eff[27]   net (fanout=1)   1.925 ns
```

**单根网线、单扇出、1.925 ns** —— 这不可能是逻辑深度，**只能是"BRAM 阵列与消费它的逻辑在芯片上离得太远"**。
另外两根同量级：
* `imem_addr2[12]` net **1.122 ns**（fanout 16）—— 取指地址扇出到 BRAM 地址口
* `imem_addr[0]` net **0.665 ns**（fanout 18）

⇒ **把 CPU 域的关键单元约束到相近的物理区域，光这几根网线就有望收回 1 ns 以上**，
而那比"抠逻辑级数"划算得多（逻辑总共才 ≈4.5 ns，且已高度优化过）。

**已知可用、且【从未用过】的杠杆**：

| 杠杆 | 现状 |
|---|---|
| **PCE / 区域约束**（把 CPU 域框进一块区域，缩短布线）| **`.fdc` 里一条都没有**（grep `pce\|region\|floorplan` 为空）|
| 多 seed | 已用（8 seed），但那是**碰运气**，不是控制 |
| BRAM 输出寄存 | 会**加一拍延迟**，等于把 load 延后一级 —— **得单独评估**，代价可能吃掉收益 |

## 4. 建议的下一步（给 CPU 线）

**顺序：先攻布线，再谈逻辑。**

1. **第一步（便宜、可判定）**：在 `.fdc` 里给 CPU 域加一条 **PCE 区域约束**（把 `u_core` + 统一存储器的
   BRAM 阵列框到一个区域），重跑 `report_timing`，**只看 `u_pll→u_pll` 那行**。
   判据：slack 是否 > +0.2 ns。若显著回升 ⇒ 这条路走通，再谈提频与约定 45。
2. **第二步**：若区域约束有效，**复测可达频率**（当前 85.2515 MHz ⇒ 提频路此前"堵死"的结论要重来一遍）。
3. **第三步**：余量确实回来了，**再回来做约定 45 剩余两项**（按约定 45 原文："应当先插假路径量时序"——
   照 `doc/reports/2026-10-11_taskC_agu_probe.md` 的做法）。
4. **[!] 不要做的事**：加流水级数（会把 load-use 与分支惩罚各加一拍，净亏）；
   也不要在余量 0.034 ns 的情况下直接改关键路径上的逻辑。

> [!] **风险提示**：PCE 区域约束是"给工具加限制"，**可能反而变差**（项目里已有一次教训——
> 约定 43 记的"放松约束 PDS 会偷懒"，说明这类约束对结果非常敏感）。所以**第一步先小范围试、看数**，
> 不要一次性大改。
