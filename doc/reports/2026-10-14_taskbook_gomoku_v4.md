## 2. 板测结论：CPU 跑五子棋有没有问题？—— **没有**

**方法**（可复用）：`python scripts\gomoku\replay_log.py doc\board\uart_*.txt`
—— 逐快照提取棋盘 → 维护真值（`*` 位按落子交替律解析）→ 校验四件事：
① 任何格子颜色跨快照变化（棋子变色 = 真 bug）② `*` 必须遮住一颗子 ③ X/O 计数合法（X 先手）④ 五连检测。

**结论**（两份日志、29 个快照、两整局）：

| 检查项 | 结果 |
|---|---|
| 落子合法性 / 轮色交替 / 计数 | **全部合法**（人机局 14 手、AI 对弈局 14+ 手，零冲突） |
| 五连判胜 | **正确**。人机局 AI（白）在第 7 手 G5 完成竖五连 G5-G9 → `WHITE wins`，相位随即 GAME_OVER，无续走 |
| AI 着法质量 | 正常：人机局 AI 在 N8 **挡住**人的 J8-M8 四连；AI 对弈局（HARD vs NORMAL）着法全部合法且有攻防 |
| `*`（最后一手）标记 | 与人机局/AI 局实际最后落子一致 |
| 颜色/翻子 | **零次**棋子变色 |
| 视频/帧同步 | 两份日志均无 `[!] vblank timeout`（用户接了显示器，画面正常） |
| 版本自证 | 首行 `[build] FW=GOMOKU RTL=0x20261019` ✓（烧的确实是 `dd4fecb4` 对应 RTL） |

> [!] **唯一"看起来像 bug 其实不是"的例子**（写给以后的你）：人机局日志里 `WHITE wins`
> 出现在**人（黑）落子之后**——曾被人手工复盘误判为"判胜颜色错了/游戏没停"。
> 实际：那一帧人是把光标移到 O9 并落子，随后 AI 在 G5 成五，串口顺序是
> `cursor=O9` → `WHITE wins`（相位切换）→ `AI moved`（棋子数变化）→ 快照。
> **教训：手工数列对齐必错，用 replay_log.py。**

## 3. 板测/整合期发现的固件小瑕疵（都归你，P2，改动都在 `scripts/gomoku/**`）

| # | 现象 | 证据 | 修法 |
|---|---|---|---|
| 3.1 | **AI 对弈局回标题时打一行假的 `AI moved`**（带上一手的 nodes/t） | log2 L121 `title` → L122 `AI moved, nodes=4571 ...`：回标题把 stones 清 0，触发"棋子数变化"分支，而该分支在 `mode==GAME_MODE_AI` 时无条件打印 | `main.c` 的 stones-diff 分支加判据：`phase` 从 PLAYING 出去（或 `stones` 变少）时不打印 |

## 4. 用户原话需求（T6 核心，逐条就是验收标准）

> 1. **"HUD 太丑了，又简单又难看"** —— 对局屏 HUD 与整体视觉重做。
> 2. **"可以学习一些小游戏的 GUI"** —— 参考经典小游戏 UI 范式（§5 有清单）。
> 3. **"操作也不方便"** + 菜单结构原话：
>    - **主界面菜单竖着排序**；**按上或下移动选择菜单**；
>    - **长按任意键后进入二级菜单**（例：选中"AI 对弈"长按 → 进入二级界面"AI 对弈"）；
>    - **二级界面里再上下或左右移动来选择其他参数**。
>
> 与 T2 现行"向导式"菜单的区别（这是交互模型重构，不是加一层皮）：
> 现行 = 每层一个参数、↑/↓ 直接改值、长按/→ 进下一层、← 回上层；
> **目标 = 标准菜单：竖排列表 + 选中高亮 + ↑/↓ 移动选择 + 长按进入/确认 + 子菜单内 ↑/↓ 选参数、←/→ 改值 + ← 返回**。

**建议的菜单行为规格**（可实现性已核，细节你定，写完先在 §7 阶段 1 回归）：

```
主菜单（竖排，选中项高亮 + 箭头/棋子图标）:
   人机对弈      —— 长按进入子菜单
   AI 对弈       —— 长按进入子菜单
子菜单（人机对弈）:  难度 EASY/NORMAL/HARD    执子 黑/白    开始对局
子菜单（AI 对弈）:   黑方AI  白方AI  每手间隔(500/1000/2000ms)  开始对局
交互约定:
   ↑/↓   移动选择（主/子菜单一致；子菜单里选中"参数项"时也可用 ←/→ 直接改值）
   长按任意键  确认：主菜单=进入子菜单；子菜单"开始对局"=开局
   ←     返回上一层（最顶层无操作）
对局中保持不变:  短按方向=移动光标，长按=落子；SW3=复位
```

> [!] `game.c` 的 `menu_stage_t` 状态机要改成"选中项索引 + 每项的值"模型
> （现有 `MENU_*` 枚举可以留着当页面标识）。**x86 单测 `test_game.c` 的 A/H 两节要跟着重写**
> —— 那就是干这个用的。

## 6. 按我们平台的修正（**动手前必读**，外部文档的假设有一半不适用）

| 外部文档说 | 我们的实际 | 你的对策 |
|---|---|---|
| "32KB 总内存" | **统一存储器 64KB**（可用 `0x0~0xEFFF`，栈顶 `0xF000` = 61,440B）；当前固件静态 **25,720B** | 不是 32KB。但注意：**tile 源数据在固件 `.rodata` 里、占这 64KB**（`tiles.h` 36 块 = 9,216B）⇒ 外部文档"新增 35~55 tile ≈ 9~14KB"会把你推到静态 ~40KB、栈余 ~21KB。**两条路选一：① 装饰性 tile（边框/渐变/木纹）用代码在 init 时算出来**（1~2KB 代码换 10KB+ 数据）；② 数据 tile 控制在 ~30 块以内（见 §6.1 预算表） |
| "tile 预算 35~55 个" | VRAM pattern 64KB = **256 图块上限**；现用 36（棋盘）+ 95（字库）= **131，空闲 ~125** | VRAM 放得下；**真正的瓶颈是固件里的 tile 源数据**（上一行），不是 VRAM |
| "5 个用户按键 SW3~SW7，SW3 落子/暂停" | **只有 4 个用户键**（SW4~SW7=左/右/上/下）；**SW3 是系统复位**（`cpu_top_board.v`/`input.h` 有论证） | 外部文档的"SW3 暂停"**不适用**。暂停菜单建议**不做**（或组合键如同时长按左+右，你定并写进设计）；"落子"继续用长按 |
| "8×8 点阵字库" | 现有 `font.h` 是 **5×7 紧凑字形**，init 放大成 16×16 图块（tile 36..130），**只认大写**（小写折叠） | 字库**可以重画**（16×16 里画 8×12 甚至 10×14，立刻变"精致"），但 glyph 已占 95 个 tile；要加符号先数空闲 tile。中文没有，别计划 |
| "85MHz" | 当前上板档 **76.5052MHz**（rev1019 的 85MHz 档确定性时序不过 −0.153ns，见 §1） | 演示/交付都走 76.5 档；提频是独立的时序优化账（任务书 v11 §2.4），与本任务无关 |
| "操作系统 RT-Thread 5.3.1" | 裸机五子棋（`gomoku_run()` + 弱 `gomoku_ai_pump`）才是本线；**RT-Thread 是另一条固件线，与裸机共享 `game.c`/`render.c`/`board.c` 等** | GUI 改动会同时进两条线 ⇒ **改完必须跑 rtthread 四配置回归**（§8），别把 RT-Thread 线改坏 |
| "无帧缓冲、实时 tile 合成" / "无精灵层" | 一致 ✓（nametable 8KB + pattern 64KB + palette 256×24bit，40×30 图块） | 光标/最后一手标记/动画**全部靠换 tile 实现**（`render.c` 的 `render_tile_for` 是唯一真相）；动画节拍用主循环 60fps 帧同步 |
| "AI思考中... 省略号动画 500ms" | **裸机 AI 是同步阻塞的**（HARD 一手 2~6s，期间主循环停了） | 动画要等 **T4（AI 卡顿 G1/G2）** 才能真正转起来；T6 里可以先做**静态反馈**（思考图标/固定文案），把动画标成"T4 后启用" |
