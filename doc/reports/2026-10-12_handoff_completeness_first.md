## 2. I+D（完整的 2 路组相联 I/D Cache）—— 当前的唯一缺口

**事实**：`EARLY_LD=1 + DCACHE_EN=1 + ICACHE_EN=1 @85 MHz` ⇒ CPU 域 slack **−0.857 ns（8 seed 全负）**。
* 关键路径：`D-Cache 数据阵列 → 前递/分支/重定向 → fetch_addr → I-Cache tag 比较 → 命中`，
  **15~17 级、Route 占 63%（7.8 ns，是不开 Cache 时 3.5 ns 的两倍多）**。
* ⇒ **根因是布局拥塞，不是某一级逻辑太深**。所以"压逻辑"没用。
* **容量已经是 4 KB/侧**（不是文档旧写的 16 KB，见约定 43 的修正）⇒ **"缩小 Cache"这条也到头了**。
* **区域约束**：PDS 的 TCL **没有** `create_region` / `define_region`（实测报 invalid command），
  官方例子里也只有 IO/LOC 类属性 ⇒ 只能走 **PCE 图形界面**（`doc/Physical_Constraint_Editor_User_Guide.pdf`）。
  **没试过，留给队友**。

**已试 / 建议的路线（按成本）：**

### 2.3 [!] I+D 位流（`fa957dbd`）**板上失败** —— 症状与定位（2026-10-12）

日志 `doc/board/uart_20261012_010314.txt`（13 s）与 `_010344.txt`（10 s）：

| 观测 | 值 |
|---|---|
| 串口内容 | **只有 banner** 重复（`[build] FW=COREMARK RTL=0x20261015`）|
| 频率 | **7,627 次 / 13 s ≈ 587 次/秒**（另一份 4,473 次 / 10 s）|
| 其它标记 | **一个都没有**（`2K performance run` / `Total ticks` / `[cache]` 全无）|
| 形态 | banner 每次**完整重现**，相邻两份**字符互相交织**（`[build[build]…`）⇒ 上一轮的字符还在 UART FIFO 里新一轮就开始了 |

**读法**：CPU 跑飞 → 非法指令 → `mtvec`（复位值 **0** = `_start`）→ 反复从头跑；
失败点在 **banner 之后不久**。

**已排除**：
* **不是串口/时钟配错** —— 文本完全可读 ⇒ 波特率对 ⇒ 板上确实是 ≈76.5 MHz ✓
* **不是"I-Cache 回填写错行"那一类** —— `cache_i.v` 里的 `idx_r/tag_r/t0_r/t1_r` 快照
  正是为它加的（那段注释记的就是同一现象：CoreMark 死循环、小测试全过）✓
* **不是不收敛** —— slack **+0.410 ns / 0 失败端点**，网表 `dcache`660 / `icache`670 都在 ✓

**待验假设**：① **I-Cache 实现有边角**（短仿真掩盖）——最可能；② **76.5 MHz 这档的口径**
（某处常量/配置仍按 85 MHz）；③ I-Cache "命中寄存一拍 + 数据同步读"在**重定向 + 同拍地址变化**下选错 way。

**第一步二分（一次综合，最值）**：
> **只开 D-Cache、仍 76.5 MHz**（`-DCacheOnly` + `RATIO0=15.0` + 4 处常量=76,505,200 + ITER 按 241,998 折算）
> * **能跑 ⇒ 锁定 I-Cache**（再去查假设①③，并把仿真加长：`-Iter 3` 的 `-DCache -ICache`）
> * **也跑不动 ⇒ 是 76.5 MHz 口径**（逐一核 `UART_DIV`/`EE_TICKS_PER_SEC`/`CPU_HZ` 与 `RATIO0`）
> **别一上来就改 Cache 逻辑 —— 先二分。**
>
> **二分位流已出**：`bitstreams/coremark_dual_aext_ms_earlyld_dcache_76mhz_a69a19b5.sbit`
> （md5 `a69a19b5`；只开 D-Cache + 76.5 MHz + ITER=3700；setup **+0.717** / hold **+0.145** /
> 0 失败端点；网表 `dcache`659、**`icache`0** ✓）。
> **判据**：串口若能打印**完整 CoreMark 报告** + `[cache] D hits/miss` 非 0 + `[cache] I` 全 0
> ⇒ **锁定 I-Cache**；若同样只重复 banner ⇒ **是 76.5 MHz 口径**，先核 4 处常量与 `RATIO0`。

> **另一个未查项（重要）**：I+D 那次（`fa957dbd`）我只记了 setup（+0.410 / 0 失败端点），

### 2.2 性能损失多少、还能不能提回来（**都能**）

**I+D（76.5 MHz）+ 4 KB Cache** 仿真：**265,408 拍/迭代**（不带 Cache 的 85 MHz 版是 241,633）。
拆两半：

```
351.86 × (76.5052/85.0051) × (241633/265408) ≈ 288      ⇒ −18.1%
        └─ 时钟 −10.0% ─┘   └─ 周期 +9.8% ─┘
```

**周期那 +9.8% 全是 I-Cache 缺失**（命中仍是 1 拍，没变慢）：4 KB I-Cache 命中率 **99.72%**，
但**每次缺失冻结整条流水线约 5 拍**，4,387 次缺失/迭代 ⇒ 约 **+22,000 拍** ✗。

| 提回来的路 | 现在 | 目标 | 收益 |
|---|---|---|---|
| **① 压 I-Cache 缺失通路**（~5 拍 → 2 拍）| +9.8% 周期 | **+3.6%** | **≈+6%**（最值的一刀：`cache_i.v` 的 `stall_r` 现在冻**整条**流水线，可只冻取指/减拍）|
| ② 用降频换的余量把 Cache 放大到 **16 KB**（`IDX_BITS 9→11`）| 命中率 99.72% | 更高 ⇒ 缺失更少 | 与①同向，但**吃回时序余量**（在 76.5↔70 MHz 间找平衡）|
| ③ 性能主线（与 Cache 无关）| — | 配对率 +3.5~7% / 剩余 load-use +2.5% / BHT +1% | 见 §4 |
| ④ **提交位流就用 D-Cache 版**（85 MHz，分数与不带 Cache 版**完全相同**）| 351.86 | — | 有 Cache、真在跑、还不亏分 ✓ |

> [!] **一句话**：I+D 上板的代价 **−18.1%** = 时钟 −10% + I-Cache 缺失 −9.8%；
> **两半都有明确的收法**（①基本收回缺失那一半；主频那一半靠"①+②后重找平衡点"）。

> [!] **降频三处提醒**（口径别混，都是踩过的）：
> 1. `RATIO0` 改完要 `ip_generate.exe -i pll.idf` 重新生成 **PLL.v**（约定 38），
>    **不是**改 `CLKOUT0_REQ_FREQ`（那字段不参与生成）。
> 2. 约定 27 的 **4 处固件常量**要同步：`cpu_top_board.v` 的 `UART_DIV`(f/115200)、
>    `coremark_port/core_portme.c` 的 `EE_TICKS_PER_SEC`、`demo/addr_map.h` 的 `CPU_HZ`、
>    `rtthread/bsp/board.h` 的 `BOARD_SYSTEM_CLOCK_HZ`；再加 **ITER 重算**与
>    `build_bitstream.ps1` 的 `expectLines`。
> 3. 约定 43 §7.2 记过"放松约束 PDS 反而更差"（请求 71.72 → slack −2.208）——
>    **别一次降太多**，一步步量。

## 3. C 扩展（RVC）—— 按"完整性"方针：**可做**，但要按评估的步骤走

**评估报告：`doc/reports/2026-10-11_rvc_feasibility.md`。**
（那份报告是**按性能判的**：实测指令条数 +0.7%、只有编码 −17% ⇒ **分数收益≈0**，
所以结论是"不做"。**按完整性方针，这条结论不再适用** —— 它变成一个"条目"。）

**已有家底（不是从零开始）**：
* `rtl/core/rvc_expand.v` —— 16→32 位展开器**已写好**
* `sim/tb_rvc.v` —— **已验证**（期望值取自 GNU 汇编器实测编码，不是手推位域）
* ⚠️ **但没有任何模块引用它**（全仓 grep 只在它自己文件里出现）⇒ **从未集成**

**要做的四件事（难度从低到高）**：
1. **ID 级接上展开器**：`if_id_instr` 是 16 位时先过 `rvc_expand` 再进 `control` ✓（改动最小）
2. **`+4` → `+2/+4`**：全设计的 PC 算术都假设"每条 4 字节"（`pc_r`、`fetch_addr`、
   `ex_mispred_target`、jal 链接值 `wb_sel==2'b10`、`branch_target`/`jalr_target`、`p_target`）
   —— **每一处都要按"本条指令的实际长度"改**，而它们大半落在**最差那条链**上 ✗
3. **取指对齐器**：16 位粒度的指令流（可能横跨两个字）；现在没有这个模块
4. **双发射配对重做**（**最大的一块**）：`pair_now` 的前提是"两条 4 字节对齐指令、A2 口就是下一条"

**建议的做法（省时间的顺序）**：
* **先做【单发射 + RVC】**：单发射取指只有一个口、**没有"变长 + 配对"的难题**，
  工作量约为双发射版的 1/3，能先把"功能对不对"解决掉（四条回归必须全过）。
  代价：单发射本身慢 16%（262,018 → 312,428 拍/迭代）—— **按新方针这是可接受的**。
* 再决定要不要在双发射上重做配对。

**验证**：`third_party/riscv-tests-elf` 的 50 个 ELF **全是 rv32ui/rv32um，没有 C** ✗
⇒ 要另建 `rv32uc` 回归（工具链能编 `-march=rv32imc_zicsr` ✓，`scripts/audit_rvc_width.py` 已有 ✓）。

## 5. 纪律（都是这轮踩出来的，逐条都有血）

1. **综合前 `git status`**：本轮踩过 `cpu_top.v` 被换回旧版 ⇒ **静默产出不含任务 C 的位流**。
   **唯一骗不了人的判据是拍数**（241,633 vs 262,018 差 7.8%）。
2. **"带开关"的位流必须 grep 网表**（约定 46）：`-DCacheOnly` 分支里那行 `WriteAllText`
   曾被误删 ⇒ 脚本**照常打印"DCACHE_EN=1"却根本没改文件** ⇒
   两次"带 D-Cache 的位流"其实是 Cache 全关，**日志/文件名/md5 全看不出来**。
   判据：`grep -aic dcache pds/RV32I_1/place_route/seed_*/cpu_top_board_pnr.netlist` 应 > 0，
   且 **slack 要与该配置的已知值对得上**（Cache 关 **+0.045** / 只 D **+0.151** / I+D **−0.86**）。
3. **同一个 PDS 工程目录不能并发综合**（两个任务抢 `cpu_top.v`/`mem.hex`/`place_route/`
   ⇒ 出过"其实是 I+D 版的位流差点当 D 版归档"）。**要并行就并到不同仓库副本。**
4. **改 RTL 后 `DESIGN_REV` 加一**（现在 `0x2026_1015`，`csr_file.v`），串口首行自证。
   ⚠️ 它证明的是 **RTL 版本**，**证明不了 parameter 开关** —— 两件事都要看。
5. **每个位流都归档**到 `pds/RV32I_1/bitstreams/` + 在 `README.md` 加一行（md5/用途/是否上板）。
   `.sbit` gitignore（9 MB/个），**只有索引进库**。
6. **换 ITER / 换开关 = 换固件 = 必须重综合**（存储器是 BRAM 初始化、没有加载器）。
7. **四条回归**：`run_riscv_tests.ps1`（49/1/0）、`run_own_tests.ps1`（2/0）、AMO（`tb_amo_int.v`）、
   `run_coremark.ps1`（四 CRC + `+MEMWAIT=1/2/3`）。
