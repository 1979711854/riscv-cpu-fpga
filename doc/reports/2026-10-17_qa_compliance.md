## 3. 必须处理的四条

### 3.1 [重点] 「跑分和应用必须是同一个 bit 流」—— 目前不符

答疑第 53 问：

> 问：跑分和应用的展示，是在同一个 bit 流文件中？还是跑分时可以把应用相关电路关闭，
> 两部分分别跑两个 bit 流出来？
> 答：**同一个。**

同时第 25 问答「跑分时可以关闭外设吗」→「可以」。两者如何统一，已有选手追问
（「是否指同一个比特流文件、运行时通过软件关闭应用相关电路；CoreMark/LUT 的 LUT
统计范围是 CPU Core、CPU+Cache 还是完整 SoC」），**官方尚未答复**。

我们的现状：

| 档位 | 位流 | 固件 | 说明 |
|---|---|---|---|
| 跑分 | `c6af65be` | CoreMark | 391.66 / 4.6064 |
| 演示 | `5909a2d0` | RT-Thread 五子棋 | HDMI + 按键 |

两者是**同一份 `rtl/**`、不同 `mem.hex` 与 `DEBUG_LED`**，但物理上是两颗 `.sbit`。
按第 53 问的字面答复，这**不符合**；按第 25 问的解释空间，可以争辩「应用电路仍在同一
设计里，只是运行不同固件」，但这属于赌官方未答的澄清，不建议。

**修法：扩到 128KB，做单一位流 + 运行时选择。**
一颗位流里同时装下 CoreMark 和 RT-Thread 五子棋两个程序，复位后由按键/串口菜单选择
（或 0 级 boot selector 跳转）。跑分时只运行 CoreMark（应用线程不调度），应用时只跑五子棋。
这样既满足「同一个 bit」，也不牺牲跑分。核算见 §4。

#### 3.1.2 已落地（2026-10-17，**板上实测**）

| 项 | 值 |
|---|---|
| 位流 | `pds/RV32I_1/generate_bitstream/cpu_top_board.sbit`，md5 **`b45941d6`**，2026-10-17 18:11 |
| 镜像 | 一份 `mem.hex`，19,710 字 / 39,420 行 = **boot selector 17 + CoreMark 8,552 + RT-Thread 11,141** |
| 选路 | 复位后 `boot.S` 读 GPIO 的 **key[2]（SW6，低有效）**：按住 → `0x1000`（CoreMark），松开 → `0x10000`（RT-Thread） |
| 时序 | CPU 域 **+0.304 ns / 0 失败端点（21,135）**，Fmax 78.3269，**All Constraints Met** |
| 资源 | LUT 7,740 / FF 3,692 / DRM 165.5（40%）—— **与单跑 CoreMark 的 `6074c89c` 逐项相同** |
| 板上 | 默认复位：banner → `[boot] heap = 4840` → render/ai 线程 → `[hb] alive`（连续 3 次）；<br>按住 SW6 + SW3：`Total ticks 846,440,591` / 11.06 s / 四 CRC `e9f5 e714 1fd7 8e3a` / `Correct operation validated` |
| 日志 | `doc/board/uart_20261017_185444.txt` |

⇒ **第 53 问从"设计意图"变成"板上可复现的事实"。** 报告口径：
「同一颗位流、同一颗 CPU，运行时二选一；跑分时 RT-Thread 不启动、HDMI 无应用负载。」
（对应 §3.1.1 对第 25 问"跑分时可关外设"的保守解释：关的是应用，不是另做一颗流。）

> [!] 顺序约束：这个决定必须**先于 ILA 抓波形**。`.fic` 与 `.sbit` 必须来自同一次综合，
> RTL 一改（14→15 位地址），91 根探针的通道映射全部作废。

#### 3.1.1 「跑分时可以关闭外设」怎么理解

官方对第 25 问只答了「可以」，**没有说明是"运行时软件关闭"还是"另综合一颗不含应用外设的位流"**。
已有选手按这个歧义追问（同一份追问里还问了 LUT 统计范围），**官方未答**。

保守解释（也是我们应采用的口径）：

- **同一颗位流**，跑分时让应用相关外设/程序**不工作**，而不是另出一颗精简位流。
- CoreMark 自身必需的 **UART（打印结果）和定时器（`0xFFF4` 周期计数器）不能关**。
  所谓「关闭外设」指的是五子棋/视频这类应用外设，不是把跑分打印也关掉。
- 对我们的 128KB 菜单方案：选 CoreMark ⇒ RT-Thread 不启动、render/AI 线程根本不存在、
  HDMI 无输出。视频逻辑即使仍被时钟驱动，也不抢取指/访存周期，**CoreMark 周期数与今天一致**。
  不需要真的做时钟门控（门控还要改 RTL/约束，收益为零）。
- **不要**为跑分另做一颗「删掉视频逻辑」的位流：
  1. 会落入第 53 问禁止的「两个 bit 流」读法；
  2. LUT 统计范围官方未答（见 §6），不能靠删应用逻辑去抬 `CoreMark/LUTs`；
  3. 第 54 问也明确「资源使用量在同等功能下对比」，功能集应完整呈现。

### 3.2 [重点] 时序报告的呈现风险

CPU 域是过的：**+0.277 ns / 0 失败端点 / Fmax 87.0549 MHz**（rev1027，钉 `gplace_seed 5`）。
但跨域 `CPU→pix_clk` 有 **−1.074 ns / 21 端点**，导致 PDS 的 Design Summary 显示
`Some Constraints Violated`。

我们已经查清这是 **0 级逻辑的同步器 STA 建模假象**（两条路径纯走线，STA 按 pix_clk
周期 39.215 ns 去卡 12+9 位同步器），且 `.fdc` 四种写法全部无效（见
`2026-10-12_session_state.md` §15，其中两种还会让综合中止）。

但评委如果只看汇总数字，会直接判「时序违例」。应对：

- 提交材料明确给出 **CPU 域 path group** 的 WNS / Fmax / 失败端点数；
- 附一页说明这 21 条是 CDC 同步器的建模假象，不是功能路径；
- 不要只丢一份 `multiseed_result.csv`（它的 `Setup(Slow)` 列恰恰是全设计最差 = 这个伪影，
  PDS 选种也会因此挑错布局，见 `2026-10-16_handover_p3_6.md`）。

### 3.3 [X] 高阶任务①的「总线突发」不能声称完成

赛题高阶①包含「存储优化 + 总线突发传输效率」。我们只有单周期片上 BRAM，
有可选 I/D Cache 探索，但**没有 DDR3/AXI 总线突发**。
答疑里「用厂商 DDR3 控制器 IP 的原生突发接口是否满足」这一条**官方未答**。
报告只能写「存储系统做了 Cache 探索」，不能写「完成总线突发优化」。

### 3.4 [X] 演示视频 / 照片缺失

已有 `doc/board/` 的串口日志、ILA 波形、HDMI 实拍证据，但缺一段完整演示录像。
答疑明确「不能只停留在仿真上」、提交物要「演示视频」。这是低成本高收益项。

## 4. CoreMark 与应用程序「一起跑」的性能影响

### 4.1 结论

**「同一个 bit 流」不等于「同时调度」**。按推荐做法（同一镜像、运行时二选一），
CoreMark 分数**不会大幅下降**；真正并发调度才会明显下降。

### 4.2 三种跑法

| 跑法 | CoreMark 影响 | 说明 |
|---|---|---|
| **A. 同一镜像，复位菜单二选一（推荐）** | **≈0** | 跑 CoreMark 时 RT-Thread 根本不启动；与今天裸机跑 CoreMark 完全一致。唯一变量是 128KB 改动可能带来的 Fmax 变化，需实测 |
| B. CoreMark 作为 RT-Thread 线程，其他线程挂起 | 约 **−0.2% ~ −1%** | CoreMark 计时源是自由跑周期计数器 `0xFFF4`（`core_portme.c`），tick 中断每 1 ms 一次（`RT_TICK_PER_SECOND=1000`，85 MHz 下 85,005 周期/次）。11.7 s 约 11,700 次 tick，ISR 开销全部计入 ticks |
| C. CoreMark 与五子棋 render/AI 线程**真并发** | **明显下降，接近按 CPU 份额打折** | 计数器计的是墙钟周期，被别的线程占用的周期全部算进 CoreMark 的 `Total ticks`。两个等高优先级线程对半 → 分数约腰斩；AI 搜索占空比越高，掉得越多。单口 BRAM 的取指/访存/视频争用还会再放大 |

### 4.3 答辩与演示建议

- 演示视频用 **A**：开机菜单 → 选 CoreMark，串口打出 391.66（约 11.7 s）→ 复位 → 选五子棋，
  接 HDMI 下完一局。旁白强调「**同一颗 bit 流、同一颗 CPU**」。
- 如果一定要在游戏画面里出现分数，显示**已跑出的存档分数**，不要让 CoreMark 与游戏并发。
- 不要把 C 的分数当成「加了应用后的 CoreMark 分数」对外报 —— 那不是同一测评条件，
  且与答疑「同等应用下看跑分」的口径不符。

## 5. 128KB 是否必须 —— 体积核算

### 5.1 实测段大小（2026-10-17，`riscv-none-elf-size -A`）

| 程序 | .text.init | .text | .rodata | .data | .bss | mem.hex 镜像 | 含 .bss 常驻 |
|---|---:|---:|---:|---:|---:|---:|---:|
| CoreMark | 3,356 | 28,188 | 2,640 | 24 | 2,020 | **34,208** | 36,228 |
| RT-Thread 五子棋（T6） | 52 | 31,140 | 12,673 | 188 | 10,696 | **≈44,056** | **54,749** |
| 合计 | | | | | | **78,264** | **90,977** |

- 当前 64KB 存储器的程序区是 `0x1000~0x10000`，可用 **61,440 B**。
- **即使两份 `.bss`/栈不同时存在（运行期复用），78,264 B 仍超出 61,440 B 约 16.8 KB。**
- 128KB 下程序区 `0x1000~0x20000` = **126,976 B**：
  - 按 mem.hex 镜像 78,264 B，余 **48,712 B**；
  - 按含 `.bss` 的 90,977 B，余 **35,999 B**。
  都够。

### 5.2 结论

**如果要求「一颗 bit 流里同时装下两个完整程序」，128KB 是必须的；64KB 装不下。**

赛题本身没有规定存储容量，强制项是答疑第 53 问的「同一个 bit 流」。绕开 128KB 的替代路径：

| 替代 | 是否可行 | 代价 |
|---|---|---|
| 只用裸机五子棋 + CoreMark | 体积 25.1 + 34.2 = 59.3 KB，名义上塞得下 | 只剩约 2 KB 栈，AI 递归要用栈 ⇒ 实际不可行；且丢掉 RT-Thread 应用分 |
| 大幅裁剪 RT-Thread / CoreMark | 需砍约 17 KB 代码/rodata | 风险高、要重写移植层，不比扩存储便宜 |
| 外存（SPI Flash / DDR）加载第二个程序 | 板上无现成方案 | DDR 控制器 / Flash 驱动工作量大，且引入启动延迟 |
| 维持两颗位流，赌未答的澄清 | 不合规风险自负 | 0 成本，但可能被判不符合 |

### 5.3 代价与顺序

128KB 不是免费的：

1. RTL：`core.v` 的 `imem_addr` / `imem_addr2` / `ld_addr` 14→15 位，
   `mem_bus.v`、`unified_mem.v`、`sim/mem_model.vh` 同步改。
   **`imem_addr2` 在关键路径上**（P3.5 专门修过），改完必须重跑时序。
2. 内存映射与链接脚本：`addr_map.vh` / `addr_map.h`、`scripts/rtthread/bsp/link.ld`、
   `scripts/demo/link.ld`、`scripts/coremark_port/link.ld`。
3. 全套回归：riscv-tests 49/1/0、own_tests、CoreMark 四 CRC、RT-Thread 四配置。
4. **重扫 `gplace_seed`**：净表一变，钉住的 seed 5 余量（+0.277 ns）作废。
   A1 的教训：LUT +122 就把 +0.277 打成 −0.156。
5. 重出一颗合并位流、板上重验、**然后**才能抓 ILA。

估计 1.5~2 天。**决定必须在 ILA 之前做。**

| D1 | **采用「同一颗位流 + 运行时选择」**，跑分时不启动应用 | 128KB 镜像内同时驻留 CoreMark 与 RT-Thread 五子棋；复位后由按键/串口菜单二选一。跑 CoreMark 时 RT-Thread 不启动、render/AI 线程不存在、HDMI 无输出；UART 与 `0xFFF4` 计数器保持工作。周期数与今天一致 |
