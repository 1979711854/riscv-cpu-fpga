## 2. 现状：平台边界（**先记牢，后面全靠它**）

### 2.1 CPU 能力

```
RV32I + M 扩展 · 5 级流水线（IF/ID/EX/MEM/WB）
前递（EX/MEM、MEM/WB 两级）+ load-use 停顿 + 多拍除法器
统一存储器（指令+数据共用一块双端口 BRAM，A 口取指 / B 口访存）
完整异常/中断（CSR + mret + 六类同步异常 + CLINT）
[!] 只支持 M 模式（mstatus.MPP 硬连线 2'b11）
[!] 没有 A 扩展（无 lr/sc、无 AMO）—— RT-Thread 走的是软原子（关中断临界区）
[!] 总线是【固定 1 拍、单主机、无握手】—— 加不了 DMA、接不了多拍设备
```

### 2.3 [!] BRAM 余量：**1.75 MB 空着**（这是我们的底牌，别浪费）

| | 数值 |
|---|---|
| PG2L200H 的 DRM36K 总量 | **415 块**（≈1.82 MB）|
| 当前 32 KB 主存占用 | **16 块**（3.9%）|
| **剩余** | **399 块 ≈ 1.75 MB** |

**换算成像素**（16 位/像素）：240×240 一帧 = 115 KB，**能放约 15 帧**。

**对游戏场景的用处**：
* **多关卡预载** —— 关卡的 tile 索引表极小（15×15 = 225 字节），放 100 关都行
* **开场画面 / 关卡预览图** —— 一张 115 KB 的整屏位图，放得下十几张
* **如果不做滚动而是整屏切换**，直接换位图比 tile 合成简单

> [!] **大块 BRAM 会占布线资源** —— 当前 slack 只有 **+1.533 ns**，余量不厚。
> **扩容必须实测**，不能想当然。

## 3. 任务 A【P0】显示外设

**当前设计一个显示外设都没有**（只有 GPIO/UART）。这是"游戏机"最大的缺口。

### 3.1 四条路线对比

| 方案 | 要买什么 | RTL 工作量 | 效果 | 风险 | 建议 |
|---|---|---|---|---|---|
| **A1. SPI TFT 小屏** | **30~60 元**（2.4"/2.8" ILI9341 或 ST7789）| **小**：SPI 主控（几十行）+ 初始化 + 刷屏 | 240×320 或 240×240 彩色 | **低** —— SPI 时序宽松 | **[重点] 推荐** |
| A2. 板载 HDMI 输出 | 不用买 | **大**：TMDS 编码 + 像素时钟 | 720p/1080p | **中高** —— 时序收敛难 | 有余力再说 |
| A3. 串口传帧到 PC | 不用买 | **很小**：PC 端 Python 显示 | 低分辨率、帧率受限 | **低** | **先用它把游戏逻辑跑通** |
| A4. 只用现有 LED/按键 | 不用买 | 零 | 只能玩"贪吃蛇"级 | 无 | 保底 |

> **推荐组合：A3（先把游戏跑通）→ A1（上真屏）。**
> A3 不需要任何硬件，一两天就能看到东西在动。

### 3.2 [!] 不需要"图像处理单元"（GPU）—— 这一条先讲清楚

**做马里奥式游戏不需要 GPU。** 三条理由：

**① 历史上的马里奥就没有 GPU。** NES 的"PPU"不是通用 GPU，它只会干两件事：
**把 tile（8×8 图案）按索引表拼成背景** + **把 sprite 叠上去**。**这活 CPU 完全干得了**
—— 更早的机器（Apple II、CGA 时代的 PC 游戏）就是纯软件渲染。

**② 画布不在 FPGA 里。** SPI TFT **屏幕自带显存**（240×320×2 = 150 KB **在屏内**）。
CPU 只要把像素**流**推过去 —— **不需要在 FPGA 里开帧缓冲**。

**③ 算力够，而且富余：**

| | 数 |
|---|---|
| 240×240 @ 60fps | 3.46 M 像素/秒 |
| 我们 49.89 MHz | **每像素约 14 个周期** |
| tile 渲染实际开销 | 查表 + 搬运，**2~3 条指令/像素** |

**绰绰有余。** 再加**脏矩形**（只重画动过的那块），开销再降一个量级。

### 3.3 A1 的具体做法（SPI TFT）

1. **买**：ILI9341（2.4"/2.8"，320×240）或 ST7789（1.3"/2.0"，240×240）。
   选 3.3V 兼容的（FPGA IO 是 3.3V）。
2. **接线**：`SCLK` / `MOSI` / `CS` / `DC`（数据/命令）+ `RST`，共 5~6 根。
   引脚从 **扩展 IO / FMC 扩展口** 挑（找项目负责人要手册）。
3. **RTL**：新增 `rtl/periph/spi_master.v`，挂到 `mem_bus` 上（照抄 `uart_tx.v` 的挂法）。
   **地址映射要在三处同步改**：`rtl/bus/addr_map.vh` + `scripts/demo/addr_map.h` + `doc/spec.md`。
4. **`.fdc`**：给新引脚加约束（照抄现有 LED/KEY 的写法）。
5. **软件**：写 ILI9341 初始化序列 + 画点/矩形/贴图函数。

> [!] **别做"全屏帧缓冲"** —— 32 KB 装不下（240×240×2 = 115 KB）。
> 用 **tile + sprite 实时合成**：按扫描线现算该行属于哪些 tile、有没有角色覆盖，
> 算完直接推给屏。内存只需要 **tile 表 + 角色表**（几 KB）。详见 §5.2。

### 3.4 A2（HDMI）为什么标"工作量大"

- 要 **TMDS 差分编码**，通常用 FPGA 的 **HSST 高速收发器**（本板有 8 路，6.6 Gbps）
- 需要**像素时钟**（720p = 74.25 MHz > 我们 54 MHz 的可达频率）→ 要么降分辨率，要么再提频
- Pango IP Compiler 里有没有现成 HDMI IP **先查**；没有就得手写
- **结论：除非时间非常充裕，不要选。**

## 4. [!] 明确"不做什么" + 答辩话术（**这一节已定案，不要再重新论证**）

### 4.1 不做 2 路组相联 I/D Cache

**一句话：Cache 的唯一作用是隐藏「慢速存储器」的延迟，而我们的存储器本来就是单周期。**

**三级判据（任何一层单独成立就够）：**

| 判据 | 我们 |
|---|---|
| ① 存储器有多快？ | **片上单周期 BRAM** → **第一关就出局** |
| ② 工作集 vs 快速存储器容量？ | **16.4 KB < 32 KB**（全装得下）→ 出局 |
| ③ 访问有局部性吗？ | 逐像素流式处理，**最没有局部性** → 出局 |

**具体算**：Cache **命中 → 仍 1 拍（零收益）**；**缺失 → 多 2 拍（纯亏）**。
还要额外付出 LUT/BRAM 和一致性维护的复杂度。

**类比例子（跟外行讲最好用）**：
> **书桌上的书，不需要再加一个书架来"快速取阅"** —— 书架是给"书在仓库里"用的。

**硬数据**：CPI **1.2294**，离理论极限 1.0 只差 23%，已经很难更好。

> [!] **最强形式是"我实测过"**：花半天做个最小 Cache 原型（哪怕 2 KB 直接映射、只做数据侧），
> 跑 CoreMark → 周期数必然 > 354,119。**把这个实测数字写进报告**，
> 答辩时说"我们实测过所以不做" —— 这比纯论证强得多。

### 4.2 不做多核

**[!] 硬约束先说：我们的 `unified_mem` 只有 2 个端口**（A 口取指 / B 口访存）。

**两个核需要 4 口** → 必须**仲裁** → 每个核的访存从"恒 1 拍"变成"要抢" ✗

> **在别的架构上多核是"加算力"；在我们这里是"把每个核变慢去换核数"。**
> 因为瓶颈不是算力，是**那一块双端口 BRAM**。

**完整代价清单**（如果非做不可）：

| 项 | 工作量 | 说明 |
|---|---|---|
| **A 扩展**（`lr/sc` + 9 条 AMO）| 中 | 需要**保留集**机制（有状态）+ `sc` 成败判定 |
| **核间中断**（CLINT `msip`）| 小-中 | 现在只有 MTIP |
| **`mhartid`** | 小 | 现在硬连线读 0 |
| **总线仲裁** | **大** | 会动承重时序 —— **可能改变 CoreMark 基线** |

**结论**：游戏场景里 CPU 的活是"读按键 → 更新几个变量 → 推像素"，**单核绰绰有余**。
**多核解决的是一个不存在的问题，代价却是唯一可能破坏性能基线的改动。**

### 4.3 不做外存（DDR3 / SD）

**游戏的工作集极小**：

| 项 | 大小 |
|---|---|
| 一屏的 tile 索引表 | 15×15 = **225 字节** |
| tile 图案本身 | 几十个 8×8 tile × 8 字节 = **几百字节** |
| 角色表 | 5 个角色 × 8 字节 = **40 字节** |
| **合计** | **不到 1 KB** |

**而且最大的一块数据（帧缓冲）在屏幕自己的显存里**（150 KB 在屏内）。

> 别人上 DDR3 是为了"装得下帧"；**我们的帧在屏里，工作集不到 1 KB** ✓

### 4.4 不做图像/滤镜系统（无摄像头）

09-27 一度转向"实时滤镜系统"，**因缺摄像头放弃**（静态图片演示说服力弱）。
那份方案的**存储论证已并入本节**（§4.1–4.3），其余不再展开。

### 4.5 不做边缘 AI（YOLO / 轻量 LLM）

32 KB 片内存储是硬墙，最小的 YOLO 变体权重也有几百 KB~MB 级。
**如实写"硬件条件不支持"**，不吹。

> [!] **别把没把握的写成已完成**：MEIP 只有通路无测试；
> 未对齐访存不支持（`ma_data` FAIL 属架构取舍，testnum **668**，不是 1）。
> 评委一验证就穿帮。

## 5. 任务 C【P1】游戏本体

### 5.1 [!] 不能跑 NES 模拟器

- NES 模拟器 + ROM 至少要**几百 KB 内存**，我们只有 **32 KB** —— **装不下**
- **所以：自己写一个精简的平台跳跃游戏。**
  NES 上跑《超级马里奥》是 40 KB ROM + 2 KB RAM 的结果 —— 那是**专用硬件 + 手写汇编 + tile 渲染**。
  我们可以借鉴它的**架构**，但要用 C 重写一个**规模和难度都小得多**的版本。

### 5.2 游戏的技术架构（**32 KB 下唯一可行的做法**）

```
不用帧缓冲，用 tile + sprite 实时合成：

  背景层：一张 tile 地图（8×8 或 16×16 的 tile）
          → 存"每个位置放哪个 tile"的索引表（15×15 = 225 字节！）
          → tile 图案本身存在 .rodata 里（几十个 tile = 几百字节）
  角色层：几个 sprite，每个存 位置(x,y) + 图案号 + 状态（5×8 = 40 字节）

  渲染：按扫描线输出时，现算该行属于哪些 tile、有没有角色覆盖 → 直接推给屏
        （SPI 屏有自己的显存，推过去就完事）
```

**内存占用几 KB，而不是 115 KB。** 参照 NES 的架构，这是经典解法。

### 5.3 建议的游戏规模（**先做小，做完了再加**）

| 阶段 | 内容 |
|---|---|
| **v0（先跑通）** | 一个方块在屏幕上左右移动 + 跳跃受重力。**验证显示链路和定时** |
| **v1（可演示）** | 加滚动地图、平台碰撞、1~2 个敌人、能吃的东西 |
| **v2（像样）** | 多关卡、得分、音效、开场画面（用 §2.3 的 BRAM 余量放整屏位图）|

> **v0 一定要先做** —— 它把"显示 + 输入 + 定时 + 渲染"四件事一次验证掉，后面全是加内容。

### 5.4 [!] 素材版权 —— 这是竞赛提交物，注意

- **不要**用任天堂的原版美术/音乐/角色形象/ROM 数据

## 6. 任务 B【P0】APB 外设总线（与 A 并行）

> 详细方案、接口约定、以及**实测踩到的 4 个坑**见 `doc/reports/2026-09-27_bus_upgrade_plan.md`。
> 这里只讲结论。

### 6.1 为什么需要

**当前总线是「固定 1 拍、单主机、无握手」**（`rtl/bus/mem_bus.v` 头注释写死了这条）：

| 特征 | 后果 |
|---|---|
| 没有 `ready`/`wait` | **任何多拍设备接不进来**（SPI/LCD/SD 全是多拍的）|
| 外设接口是自定义裸线 | **第三方 IP 都得手写胶合** |
| 只有 1 个主机 | 加不了 DMA |

### 6.2 关键结论：先做 `mem_ready`，再谈协议

**APB 一次传输最少 2 拍**（SETUP + ACCESS），**AXI 要五通道握手** —— 两者都要求 CPU 能等。

**所以第一步不是选协议，是给 CPU 加"访存等待"能力。** 这就是 `mem_ready`。

**⚠️ 当前 `mem_ready` 是半成品**：

| 项 | 状态 |
|---|---|
| 机制已实现 | [OK] |
| **恒 1 时逐位透明** | [OK] **已用正式回归验证**（CoreMark 354,119 / riscv-tests 49/1/0）|
| **多拍路径** | **[X] 未跑通** —— 剩两个坑（任务书 §3.5 坑 3 `id_redirect`、坑 4 BHT 训练块未门控）|

**调试工具已备好**：`sim/tools/tb_memdbg.v` —— 逐拍打印
`pc / mem_we / mem_ready / ex_flush / id_redirect / id_ex_branch / branch_taken /
id_ex_pred_taken / funct3 / rs1_val / rs2_val / 四个前递`，
对比 `+MEMWAIT=0` 与 `=2` 的同一段即可定位分叉点。

> [!] **纪律**：这块承重逻辑的耦合面比预想大（实测已撞 4 个坑）。
> **单独一次做，每改一处立刻用 `+MEMWAIT=2` 验一次**，不要一次改多处再一起测。
> 每改完**必须**回归：CoreMark **354,119** + riscv-tests **49/1/0** 逐位不变。

### 6.3 APB 与游戏的关系

**SPI TFT 是新外设** —— 它正是 APB 要服务的第一块。用 APB 挂 SPI，而不是再写一套裸线胶合。

> **但注意**：SPI 屏的写路径可以做成"**写进 FIFO 就 1 拍响应**"，
> 所以**马里奥这条线不依赖总线改造** —— 别让 B 卡住 A。

## 7. 回归纪律（**先背下来再动手**）

**只要改了 RTL，必须跑这两个：**

```powershell
scripts\run_riscv_tests.ps1              # 期望 49 PASS / 1 FAIL / 0 TIMEOUT
scripts\run_coremark.ps1 -Iter 1         # 期望 354,119 拍 / 总周期 1,457,776
```

| 指标 | 当前基线 |
|---|---|
| CoreMark 计时区间 | **354,119** 拍 |
| 测试台总周期 | **1,457,776** |
| 四个 CRC | `e9f5 / e714 / 1fd7 / 8e3a` 逐位一致 |
| riscv-tests | **49 / 1 / 0** |
| 板上实测 | **140.89 CoreMark**（49.8927 MHz，ITER=1663）|
| 资源（生产版）| LUT 3,721 / FF 2,441 / DRM 16 / APM 11 |
| 时序 | 49.8927 MHz，可达 54.0745 MHz，slack **+1.550 ns**，`All Constraints Met` |

> [!] **`crcfinal` 不能比** —— 它是 CoreMark 的跨迭代累加器，必然随 ITER 变。
> 只认 `seedcrc`/`crclist`/`crcmatrix`/`crcstate` 四个。
>
> [!] **改了流水线就必须重算 ITER**，否则 CoreMark 判 invalid。
> 速算式：`ITER = 498,927,000 ÷ 每迭代周期数`（本地板）；取整后留 5~10% 余量。

## 9. 卡住了怎么办（**先看这张表**）

| 现象 | 原因 |
|---|---|
| 板上跑的还是旧程序 | **PDS 不检查 `mem.hex` 时间戳**。用 `build_bitstream.ps1`，它带 sha256 校验 |
| 串口没输出 | **只插了 Jtag，没插 USB-UART** —— 是两块独立接口，要插**两根** USB 线 |
| 烧完是别的程序 | Programmer 会记住上次分配的文件；**每次都要重新 `Operations → Assign New Configuration File`** |
| 综合报 `pll` 是黑盒 | PLL IP 必须以 **IP 源文件**形式加进 `.pds`（`wgt_my_ips_src`）|
| 板上什么都不跑、零报错 | PDS 工程目录里 `mem.hex` 缺失或过期 |
| 加了新外设后地址对不上 | 地址映射要在**三处同步改**：`rtl/bus/addr_map.vh` + `scripts/demo/addr_map.h` + `doc/spec.md` |
| 外设把 X 放上总线 | X 被 CPU 读走会污染分支比较，控制流走错。**外设任何时候都不该输出 X** |
| 改了 `core`/`mem_bus` 的端口后**两个回归台同时挂** | **`sim/tb_coremark.v`、`sim/tb_riscv.v`、`sim/tools/tb_debug_trap.v` 是手工例化 `core`+`mem_bus` 的**（不走 `cpu_top`），新端口在它们那里悬空 → 症状是"跑到 1 亿拍超时、pc=0"（见 CLAUDE.md 约定 37）|
| RT-Thread 起来就崩 | 查 `mtvec` 的 direct 模式假设、`mstatus.MIE` 切换、栈顶是否越过 `0x7FF0` |
