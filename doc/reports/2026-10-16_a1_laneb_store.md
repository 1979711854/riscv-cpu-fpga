## 2. 实现（改动面 = 6 处，全在 `rtl/core/core.v`；`control.v` 一行未改）

| # | 落点 | 改动 | 为什么必须改 |
|---|---|---|---|
| ① | `p_opcode_b_ok` / 配对白名单 | 加 `p_st_b`（`OP_STORE`）+ `p_mem_b = (LANEB_MEM!=0) && (p_ld_b \|\| ((LANEB_ST!=0) && p_st_b))` | lane B 放 store 的准入 |
| ② | **新增 `p_b_rd_ok`** | `!p_b_writes_rd \|\| ((p_rd_b != 0) && (p_rd_a != p_rd_b))` | **store 的 `instr[11:7]` 是 S 型立即数低 5 位、不是 rd**。沿用 `rd_b!=0` 会把 `sw x1,0(x2)`（imm[4:0]=0）整类静默拒掉；沿用 `rd_a != rd_b` 是拿 rd 与立即数比 |
| ③ | "每对最多一条访存" | `!(p_mem_a && p_mem_b)` | 写口只有一套（`mem_bus` 单写口）⇒ 同拍不可能两条 store，也不需要仲裁器 |
| ④ | 写口三条腿 | `mem_we \|= b_st_sel`；`mem_addr` 的 mux 加 `b_st_sel`；`mem_wdata`/`mem_byte_en` 各加 lane B 分支 + **新增 `ex_mem_b_wdata`** | **`ex_mem_wdata` 是 lane A 的 rs2，不能借用**（借用 = 把 lane A 的操作数写进内存） |
| ⑤ | **判据③ `ld_bad_st`** | `id_ex_mem_write \|\| ((LANEB_MEM!=0)&&(LANEB_ST!=0)&&id_ex_b_mem_write)` | lane B 的 store 与 ID 级那条 load 的**提前读口是同一沿读写** ⇒ 漏了 = 静默读旧值 |
| ⑥ | 异常 | 新增 `store_misaligned_b`，并入 `ex_exception_b` / `exc_cause=6` / `exc_tval=alu_result_b` / `trap_from_b` | lane B 的未对齐 store 必须精确陷阱；`b_mem_unaligned` 与 `b_addr_low` 与 load **共用**（S 型与 I 型低 3 位编码一致），A1 不新增取指路径逻辑 |

补充（**不改但必须点名**）：
* `stall` 里**没有**任何 lane B store 的子句 —— store 不产生写回值、数据/地址都在 EX 级取，
  这是"A1 改动面小"的根本原因；
* `ex_mem_b_valid` 已含 `!ex_flush` ⇒ 被冲刷的对里 lane B 的 store 天然不写（不回退这条承重门控）；
* trap 清 ID/EX 与 EX/MEM ⇒ **既陷异常又改了内存**不可能发生（同 2026-09-23 的老坑）。

## 4. 收益（为什么只有 0.18%，不是 1~3%）

`217,088 → 216,695` = **−393 拍 = −0.181%**（效率 4.6064 → 4.6084 CoreMark/MHz）。
按"一对省 1 拍"折算，等于每迭代多配到约 393 对。远小于预期的原因（都可核对）：

1. **`lane A` 是访存时不能配对**（每对至多一条访存）—— CoreMark 的 store 前一条常常也是访存；
2. **同对 RAW 判据**（`rd_a ∉ {rs1_b, rs2_b}`）—— store 需要 base 与 data 两个操作数，
   命中"lane A 刚写这两个寄存器之一"的概率是纯 ALU 指令的两倍；
3. store 在 CoreMark 里的**绝对条数**远少于 load，且其中一部分已被"更值钱的配对"占掉。
> 结论口径：**"lane B 放 store"本身没有错，是 CoreMark 给它留的窗口本来就窄**。
> 这条要写进论文（"设计—收益—代价"闭环），也是 A2（配对率扩展）必须先统计再动的原因。

**三个必须记住的读数**：
1. **E2 逐位复现历史值**（+0.277 ns / 端点 19,114）⇒ **流程本身是确定性的**，
   同网表 + 同 seed ⇒ 同余量（这一条让 A1 的"嫌疑"变得确定，也让 P3.6 的选种结论站得更稳）；
2. **FF 完全没变（3,691）** ⇒ 新增的三个寄存器（`id_ex_b_mem_write` / `ex_mem_b_mem_write` /
   `ex_mem_b_wdata[31:0]`）在关档下**确实被综合裁掉了**（FF 层面折叠成立）；
3. 但 **逻辑 LUT +122（7,195 → 7,317）、端点 +1,107、余量 −0.433 ns** ⇒
   **净表仍然变了**（同一颗器件、同一 seed、同一流程，只有 RTL 不同）。
   ⇒ **`gplace_seed 5` 的余量只对某一版净表成立**：净表一动，同一个 seed 就不是同一件事。
   这是本次最重要的方法论发现（落进 §6 的纪律）。

> 要用"同一天的两次构建"做基准（本报告用 E2 = 7,767 作基准）**，别跨会话比。

## 6. 可复现性发现（E2 对照，本次最重要的方法论）

为区分"我的改动 vs 流程抖动"，用 **rev1027 原样 RTL**（`git stash` 暂存 A1 改动）重跑**同一流程、
同一 `gplace_seed 5`**（日志 `pds/_e2_pristine.log`，位流 `fefc16ae`）：

- **CPU 域：+0.277 ns / Fmax 87.0549 MHz / 0 失败端点 / totalEP 19,114 —— 与历史值逐位相同**
  （时序快照存证：`report_timing/rev1027_seed5_c6af65be.rtr`）；
- LUT 7,767（历史记 7,753，差 14 = 报数抖动）。

⇒ **两个结论**：
1. **流程确定性成立**：同网表 + 同 `gplace_seed` ⇒ 同余量。P3.6 的"钉 seed 5"做法是对的、
   可复现的（这一条本身就是值得写进论文的"过程可复现"证据）；
2. **但"钉 seed"钉的是"某一版净表"**：A1 让净表变了 +122 逻辑 LUT，同一个 seed 5 就给出
   −0.156 ns（85 MHz 下 5 个失败端点）。**不是流程抖动，是"新网表 + 旧种子"**。

**纪律（要落进 `SKILL.md` §8）**：
> **任何 RTL 改动（哪怕仿真逐位等价、哪怕 FF 数完全相同）都要假设钉住的 seed 余量作废；
> 出位流前先单跑一次核对 CPU 域余量，别拿旧余量下结论。**
> 推论：**"关档等价"只在仿真层成立**（CoreMark/CRC/riscv-tests 逐位不变），
> **综合层不成立**（LUT/时序会变）——所以"门控关掉就能回到旧网表"这条直觉要打折扣，
> 需要时得用"原样 RTL 重跑一次"来对照着说。

## 7. 建议（换档与否）

**建议：不换交付档**（跑分档 `c6af65be` / 演示档 `e51ac9e5` 保持 rev1027）。
理由（可直接引用）：

1. **主分收益太小且小于测量噪声量级**：+0.181%（约 +0.7 分）尚未大到能盖过
   板上/仿真口径本身的差异（同一档：板上 217,036.1 vs 仿真 217,088 = 0.024%，
   但换档后面临新的位流、新的四个板级判据）；
2. **指标(3) 明确变差**：CoreMark/千 LUT `50.52 → 49.65`（−1.7%）；
3. **这条最关键 —— 不重扫 seed 就只能降频，而降频是真金白银**：
   A1 的最小代价形态（关档）就已经把余量打到 −0.156 ns / 85 MHz 下 5 个失败端点
   ⇒ 不重扫 seed 的话，板上主频得从 85 降到 83 MHz 才稳；而**化简后的计分公式里
   `Score = Iterations/(Total_Time × Frequency)` ⇒ 分数与主频成正比**，
   降 2.4% 主频 = **直接亏 2.4% 的分**，去换 A1 的 +0.18% —— **净亏 2.2%**；
4. 要拿回那 +0.277 ns 就得重做 seed 全扫（40 跑量级 ≈ 数小时机时）+ 两颗位流重出 +
   两条板级判据重测，去换 **+0.18%**（约 +0.7 分）——性价比明显不足；
5. **排序规则也帮不了忙**：赛题"先比性能、性能相同再比面积"——0.18% 的性能优势
   换来 1.6~1.7% 的面积劣势，两个指标一个微升一个下降，本就是"效率上对、
   整张成绩表上不划算"的典型。

**若将来要换档**，前置条件（缺一不可）：
① seed 重扫（逐 seed 读 CPU 域，`scripts\capture_seed_timing.ps1` 钉新的最优 seed）；
② 两颗位流重出（跑分 + 演示，都用 `build_bitstream.ps1` 唯一入口）+ 两条板级判据重测；
③ 五处口径同步（`CLAUDE.md` 提交档表 / 论文 §0·§0.1 / `doc/board/README.md` /
`pds/RV32I_1/bitstreams/README.md` / `SKILL.md` §1）+ 旧档降为历史参照。

## 11. A4 判定：**不做**（先做 0 成本可行性推导 ⇒ 结论是否，省掉一轮 RTL + PDS）

### 11.1 落点已探明（子代理 + 源码核对，比计划书更准）

| 事实 | 落点 |
|---|---|
| 那条路的 DRAM 是 **`u_pat` = pattern 显存**（不是 palette）：`rtl/video/video_core.v:89-99`（`vram_b32 #(.AW(16)) u_pat`），`pat_q` 来自 `rtl/video/vram_b32.v:50-51` 的同步读（输出寄存） | `video_core.v:61,159` |
| 读译码/读数据 mux：`mem_bus.v:456-458`（`rsel_d==3 ? vid_rdata : …`），`vid_rdata` 是 mem_bus 的输入（`mem_bus.v:84`） | — |
| `mem_ready` **唯一**产生点：`mem_bus.v:373-374`；视频区现在**恒 1**（`mem_bus.v:357-359` 注释） | 一行可改 |
| 写通路**不查 ready**（`mem_bus.v:205` / `239`，视频 BRAM 同址同值幂等） | 写侧无风险 |
| 视频窗口读的**唯一消费者**＝"CPU load 且地址落在视频窗口"；固件只读 `VIDEO_STATUS`（寄存器窗口，`scripts/gomoku/video_port.c:62`），`scripts/rtthread/` 无命中；PPU 走**另一端口**（pix_clk） | ⇒ CoreMark/固件**都不读 pattern 窗口** |
| 现有多拍就绪先例：D-Cache 缺失 `cache_d.v:139-141`、仿真 `+MEMWAIT` `mem_model.vh:85,135-146`（**都只作用于数据口 B**）；core 侧统一消费 `core.v:1243 mem_ready_int` | 机制现成 |
| 测试：`sim/tb_video_core.v` 大读 NT/PAT/PAL，但它的 `mem_rd` **硬编码 1 拍、不查 ready**（`tb_video_core.v:168-178`） | 要改才不误报 |

### 11.2 但推导出**两条硬结论**（这才是判"不做"的依据）

**结论 ①："只把 `mem_ready` 多压一拍" = 零收益（不是"零代价换收益"）。**
那条路是**同沿内**的组合链（起点 = `u_pat` BRAM 的输出寄存时钟沿，终点 = 指令 RAM 的 `ADB0`）。
多压一拍只改变**流水线相位**，**不会**从网表里去掉任何一级组合逻辑 ⇒
违例路径**结构上仍然存在**（被 enabled 寄存器挡住的 D 端路径，STA 照样分析）。
⇒ 计划书里"视频窗口读多压一拍就能挪走 1.76 ns"这一步**不成立**。

**结论 ②：要真去掉，必须把视频读数据**打拍**（寄存器插进那条链），
但这会撞上 core 的**读数据契约**，改动落到 CPU 关键逻辑上、且收益仍有疑问：**

* core 的消费方式是 `load_src = wb_rdata_snap_en ? wb_rdata_snap : mem_rdata`（`core.v:1797`）；
  快照在**停顿的第一个沿**抓 `mem_rdata`（`core.v:1779-1793`）⇒ 隐含契约是
  **"读数据必须在停顿第一拍就已有效"**（这也是 D-Cache 缺失/`+MEMWAIT` 只延长停顿、
  不推迟数据到来的原因，见 `mem_bus.v:368-369`）。
* 若把 `vid_rdata` 打一拍（数据推迟到 T+2），快照在 T+1 抓到的就是**上一个访问的旧值** ⇒
  要么给 core 加"迟到读数据"端口 + 在 `load_src` 前**再加一级 mux**（**正好加在要缩短的那条链上**，
  实测每级 mux ≈ 0.2~0.3 ns，见 `core.v:1766-1770` 的历史教训），要么改快照时序（更险）。
* **收益估算（决定性）**：`+0.277 ns` 那版的 `Logic 4.522 / Route 6.620`（≈ 11.14 ns）
  就是**去掉时钟插入后的纯逻辑/布线**；其中跨模块段只占 `tco 1.644 + net 1.760 = 3.404 ns`。
  即使把这段全切掉，剩下的**尾段（lane B 解包 → 前递 → ALU lt → 分支解析 → 重定向 →
  `imem_addr`/`imem_addr2` → ADB 高扇出 1.201 ns）仍需 ≈ 9.4~11.1 ns 去挤 11.76 ns 周期**
  ⇒ **首尾都在临界点上，赢面不明**，而代价是往 CPU 关键逻辑里插一级 mux + 新增跨模块端口 +
  改契约注释 + 改 `tb_video_core.v` 的 `mem_rd` + 全套回归（含 `+MEMWAIT` 组合）。

**⇒ 判定：A4 不做。** 理由写成一句话：
**"它要动的那条链的命门在 CPU 侧（lane B 解包→前递→ALU→重定向），不在视频侧；
视频侧那 3.4 ns 只是它的引子。切引子不解决命门，而切命门要给所有 load 加拍（43,228 次/迭代）。"**

### 11.3 三处"剩余瓶颈"各自的处置（把这条线一并收口）

| 瓶颈 | 量级 | 处置 |
|---|---|---|
| 跨模块投放线（`u_pat → u_soc`） | 1.760 ns | **不做**（见 11.2：切了不解决命门）|
| `ADB` 高扇出线（扇出 16） | 1.201 ns | 只能靠"取指地址再打一拍"或复制驱动寄存器 ⇒ **前者 +1 拍取指代价（直接亏分）**，后者收益 < 0.3 ns 且要动 `fetch_addr` 腿 ⇒ **不做** |
| 时钟树插入（fanout 3140） | 1.615 ns | **物理项**，不是 RTL 能改的（`.fdc`/region 已有四次否证先科）|

⇒ **Fmax 在 RTL 侧到顶**：`+0.277 ns` 距 `+0.3` 判据差 0.023 ns，**只剩物理手段**。
这条结论本身值得写进论文第 6/8 章（"我们的 Fmax 已经压到 RTL 边界"）。

**关键观察**：这条链的**起点是"视频调色板窗口的读数据"**，也就是说

* **CoreMark 全程不碰视频窗口**（它的全部访存都在 RAM 段）⇒ 若把"视频窗口的读"做成
  **2 拍就绪**（在 `u_pat` 的 DRAM 输出后打一拍，或让 `mem_bus` 对视频窗口多压一拍
  `mem_ready`），**CoreMark 的 217,088 拍不变**（主分不动），而 CPU 域关键路径上
  那 **1.76 ns 跨模块长线**就从路径里挪走；
* 代价只落在**演示固件读视频窗口**的少数访问上（五子棋是"写像素"，读窗口极少）
  ⇒ 对两条板级判据基本无影响；
* 机制现成：`mem_ready_int` 多拍就绪 + `stall/冻结拍` 那套已经为 Cache / `+MEMWAIT` 建好了，
  **不需要新发明**（但要重新过一遍"冻结拍副作用"那几条纪律，见论文第 5 章）。

**⇒ 这才是"效率优先"前提下值得做的 Fmax 项**：它把"指标 2"的收益与"主分"解耦
（不是"降频换余量"那种两难）。**要先做的一步（便宜）**：确认视频窗口读路径的**真实消费者**

—— 若它本身就 > 11.76 ns 周期，那收益要打折，别按 1.76 ns 全额算。
