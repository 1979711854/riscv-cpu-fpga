# 任务 C 实施报告 · load 地址提前到 ID（EARLY_LD）—— 每迭代 −7.79%

> 前置：`2026-10-11_taskC_agu_probe.md`（假 AGU 探针的时序评估）、`CLAUDE.md` 约定 44。
> 本文记录**把评估变成实现**的那一步：做了什么、实测多少、还剩什么、坑在哪。
>
> **一句话：上限 24,568 拍（9.38%）拿到了 20,385 拍（7.78%），兑现率 83%。**
> 262,018 → **241,633 拍/迭代**；预期板上 **≈ 352 分**（324.5 → +8.4%）。**未上板。**

## 1. 做法（为什么这样切）

`load` 的地址若在 EX 级才算，数据要 **WB** 才回来，紧跟其后的消费者（距离 1）只能停一拍
—— 这就是区间内 27,181 拍 / 10.4% 的 load-use 停顿。

把地址算到 **ID** 级、用**专用读口**早一拍取回，数据正好在该 load 的 **MEM** 级到位，
消费者在 EX 级就能前递到它 ⇒ 停拍消失。

```
旧：  ID ── EX(算地址) ── MEM(访存口) ── WB(数据回来)     ← 消费停 1 拍
新：  ID(算地址) ── EX(读口) ── MEM(数据已在) ── WB        ← 消费不停
```

### 1.1 专用读口 = 第三份阵列（**不是**抢 B 口）

`rtl/mem/unified_mem.v` 里再加一份 `mem2`（写口同样广播），与 A2 取指口的做法完全同构：

| 阵列 | 服务 |
|---|---|
| `mem0` | A1 取指 + B 访存（真双口） |
| `mem1` | A2 取指（双发射第二读口） |
| **`mem2`** | **C 口：提前 load 读（只读，`EARLY_LD=1` 时才例化）** |

> [!] **为什么不能复用 B 口的读**：B 口的读地址与写地址是**同一根** `b_addr`。
> store 在 MEM 级占着 B 口的那一拍，load 的提前读就没法共用 —— 而"store 之后紧接
> load"在 CoreMark 里足够常见（实测 1,869 次停顿），要么加仲裁/冻结、要么像连续
> load 那样白付结构性停顿。**多一份阵列（约 28 个 DRM，板上有 329 富余）换来的是
> 零仲裁、零新增停顿**，是这里最省心的切法。

### 1.2 新增的两条前递路（都在 EX 级，不增周期）

| 消费者 | 旧来源 | 新来源 |
|---|---|---|
| 紧跟快通路 load 的指令 | 无（**停一拍**，从 WB 前递） | `ld_early_val`（该 load 的 MEM 级） |
| **基址**来自 EX/MEM 里另一条快通路 load | 无（退回旧通路） | `ld_early_data`（同上，ID 级用它算地址）|

第二条是**链式指针解引用** `lw a5,0(a0) ; … ; lw a1,0(a5)` —— 在 CoreMark 里占
load 的 **22%**，不接进来这批就全留在旧通路上（实测差 6,029 拍 / 2.5%）。

> [!] **第二条【只接字 load】**（`ex_mem_funct3 == 3'b010`）。byte/half 作为基址来源时
> 要先解包，那几级会直接压在这条 ID 链上 —— 综合报告里**它一度顶替乘法器成为 CPU 域
> 最差路径**（`ld_rdata → 解包 → ID 加法器`，slack +0.035 ns），这是直接观测。
> 字 load 的数据**不需要解包**，直接就是寄存器将写入的值，等于白省 3~4 级；
> **周期数一模一样**（CoreMark 里的链式指针解引用全是 `lw`）。
> [!] **但要说清楚：这一刀"到底换回多少 ns"没量准。** 它改了网表 ⇒ 布局也变，
> 单次综合没法把"逻辑更浅"和"布局变好"分开（实测它之后的那次反而 −0.156，
> 再叠上 §1.2b 的快照合并才回到 +0.045）。**它是一个"逻辑确实更浅、且不要钱"的改动，
> 不是"实测省了 0.2 ns"的改动** —— 别把因果说过头。

> [!] **前递的必须是【解包后】的值。** 2026-10-11 实踩：只前递原始字时
> `lw` 全过、**`lb`/`lbu`/`lh` 全 FAIL**（`lhu` 因为测试数据高半字恰好为 0 而蒙混过关），
> CoreMark 的 matrix/state CRC 也全错（它用的是 `u16`）。
> WB 段那条解包逻辑服务的是**写回**，前递必须**另来一份**（`ld_fwd_byte` / `ld_fwd_half` /
> `ld_early_val`，与 WB 段同构）。

### 1.2b 快通路 load 的写回：复用 A.0 的抢救快照寄存器

快通路 load 的数据在它**自己 MEM 级**就到位了，所以必须在 **MEM→WB 那个沿**抓下来。
第一版为它单开了一个 `mem_wb_ld_raw` + 一级 mux，结果那一级正好落在那条
**时序敏感链**上（`BRAM 出 → load_data → wb_data → 前递 → 分支 → 重定向 → 取指地址`）。

**改成直接把数据抓进既有的 `wb_rdata_snap`**（A.0 那个冻结快照寄存器），于是 WB 段的
`load_src` 表达式与基线**逐字相同**、快通路**一级都没给它加**：

```verilog
else if (mem_ready_int && ex_mem_ld_fast)   // 快通路 load 的 MEM→WB 沿
        wb_rdata_snap <= ld_early_data;
else if (mem_ready_int)                     // 正常推进（且不是快通路 load）
        wb_rdata_snap_en <= 1'b0;
else if (!wb_rdata_snap_en)                 // 冻结第一个沿
        wb_rdata_snap <= ex_mem_ld_fast ? ld_early_data : mem_rdata;
```

正确性要点：`wb_rdata_snap_en` 只在"流水线冻结"或"EX/MEM 里是快通路 load"时保持为 1，
其余情况在**每一条非快通路指令进 EX/MEM 的那一拍**就被清掉 —— 所以旧通路 load 到 WB
时 en 必为 0、走实时 `mem_rdata`，与基线逐位一致 ✓（`+MEMWAIT=1/2/3` 全部复测通过）。

### 1.3 保守判据：判错只退回旧通路

只有**四条都满足**的 load 才走快通路，其余原样走旧通路（旧通路一行未改）：

| # | 判据 | 为什么 |
|---|---|---|
| ① | 基址在 ID 级拿得到 | 不含"被 **EX 级**那条指令刚写出"（结果还在 ALU 里；见 §5 可选项）、也不含"被 EX/MEM 里**旧通路 load / AMO**"写（数据还没回来） |
| ② | **地址落在 RAM 段** | 专用读口只镜像 RAM（外设 / 视频 / 兼容区没有） |
| ③ | **紧前一条不是 store** | 它与提前读口是"同拍写/读"，读到的是**旧值**（非阻塞语义） |
| ④ | 前/后没有 **AMO** | AMO 的写与它的冻结放开在**同一沿**，同理 |

①③④ 在 ID 级就看得出（地址/寄存器号都是 ID 级信号），不需要任何新停顿、也不需要冻结机制。

## 3. 实测结果

### 3.1 周期（仿真，双发射，ITER=1，判据 `+PROF` 的 `region cycles`）

| 版本 | 拍/迭代 | Δ | 用了快通路的 load | 剩余停顿 |
|---|---|---|---|---|
| 基线（`EARLY_LD=0`） | **262,018** | — | — | 27,181 |
| 第一步（只做 §1.2 第一条前递） | 247,662 | −14,356（−5.48%）| 38,954（68%）| 12,825 |
| **第二步（加 §1.2 第二条前递）** | **241,633** | **−20,385（−7.79%）** | **48,850（85%）** | **6,796** |

> [!] §1.2 的"只接字 load"与 §1.2b 的"写回走快照寄存器"这两刀**都不花周期数**
> （限制前后都是 241,633，逐位相同），它们纯粹是在**还时序**。

**兑现率 = 20,385 ÷ 24,568 = 83%。**

> [!] 第一版只兑现了 58%（14,356/24,568），差额**不是**猜的：`+LDANAL` 里加了一条
> "模型判可走 / RTL 标慢"的对拍计数，量到 **12,749 条** load 全部由同一个原因挡住 ——
> **基址来自 EX/MEM 里另一条 load**。把它接进 ID 前递网后，对拍数掉到 **49**，
> 兑现率随之升到 83%。**没有这一步对拍，只会看到"没达到预期"而不知道差在哪。**

### 3.2 剩余停顿的去向（就是下一步的可选项）

| 成因 | 拍数 | 占比 | 要做什么才能消 |
|---|---|---|---|
| **基址在 EX** | **4,744** | 1.81% | 加 **EX→ID 前递**（把 `alu_result` 接进 ID 加器；即"两级加法器一条链"）|
| 紧前是 store | 1,869 | 0.71% | store→load **字节合并旁路**，或一次性冻结 |
| 旧通路 load / AMO | 183 | 0.07% | 基本不值得做 |

| 项 | 预期 | **实测** |

| `Total ticks` | 994,561,428 | **994,362,145**（差 0.02%）|
| 时长 | 11.700 s | **11.6976 s** ✓ >10s |

### 3.4 板上预期（算法）

```
ITER = 85,005,100 × 11.7s ÷ 241,633 = 4,116      （与旧版 3796 同等的 17% 余量）
时长 = 4,116 × 241,633 ÷ 85,005,100 = 11.699 s   ✓ > 10s
得分 = 4,116 ÷ 11.699 = 351.9                    （324.5 → +8.4%）
```

> [!] **口径**：`ITER` 必须按新周期数重算（速算式 `频率 × 10s ÷ 每迭代周期数`），
> 否则 CoreMark 判 invalid。`Total ticks` 与 `region cycles` 必须相等（见约定 42）。

### 4.1 抢救快照（`ld_snap`）

与既有的 `wb_rdata_snap` 同构：访存冻结（`+MEMWAIT`、I-Cache 缺失、AMO 占 MEM）会让
实时 `ld_rdata` 在下一拍就跟到**别人的地址**上去，所以**停顿的第一个沿先抓一次**，
`mem_ready_int` 放开那拍清掉标志。没有它，快通路 load 在冻结跨过它的 MEM→WB 沿时会写回错值。

## 5. [重点] 时序：**这是本版唯一的保留项**

`pds_shell -project RV32I_1.pds -run pnr`，每次都是 8-seed 流程取最优。**同一份 RTL
连跑几次，结果差 0.3 ns 以上**（约定 25 的老问题）—— 所以下表把每次单独列出来：

| # | 版本 | CPU 域 slack | 失败端点 | 关键路径落在哪 |
|---|---|---|---|---|
| — | 基线 `EARLY_LD=0`（历史四份报告）| **+0.544 ~ +0.879** | 0 | 乘法器 |
| 1 | 只做 §1.2 第一条前递 | **+0.208** | 0 ✓ | **乘法器**（本轮逻辑不在上面）|
| 2 | + 第二条前递（未加字限制）| +0.035 | 0 ✓ | **新 ID 链**（`ld_rdata→解包→ID 加法器`）|
| 3 | + **字 load 限制** | **−0.156** | >0 ✗ | `前递→分支→重定向→取指地址`（Route 占 **69%**，单根网线 1.23 ns）|
| 4 | + 写回走 `wb_rdata_snap`（**当前版本**）| **+0.045** | **0** ✓ | 同上那条链 |

**读法（2026-10-11 晚补正）：**
* [!] 第 4 行的 **+0.045 在三次独立 P&R 里逐位复现**（含最终出位流那次）——
  所以**本机的 slack 是"每个 RTL 版本一个值"，不是随机数**。上表每一行对应**一个
  不同的 RTL 版本**，那 0.3 ns 的散布是**版本差异 + 布局随之改变**，不是重复测量噪声。
  （约定 25 记过"同一 RTL 两次差 5.7%"的反例，所以引用余量时**仍要说清是哪一次、哪份 RTL**。）
* 第 3 次那条最差路径落在 `前递 → 分支 → 重定向 → 取指地址` 上，且 Route 占 69%
  （单根网线 1.23 ns）—— 那是**布局变了之后新冒出来的**一条链。
* **本轮新逻辑确实"碰得到"关键路径**：它在两条链上各加 1~2 级 —— ①ID 级 AGU 链
  （§1.2 的字限制就是为了把它摘下去）②`BRAM 出 → load_data → wb_data → 前递 → 分支
  → 重定向 → 取指地址`（§1.2b 的快照合并就是为了还它一级）。
* **结论**：功能与周期是硬的（−7.79% 稳定复现），**时序是软的** ——
  当前版本的 slack 在 **0 附近**（+0.045 / 0 失败端点）。**上板前必须先看当次
  P&R 报告的 CPU 域那两行**；为负就重跑一次（P&R 有随机性），再不行就 `EARLY_LD=0` 回退。
* 顺带确认：`u_pll → u_video` 那条 −1.06 ~ −1.13 ns / 21 端点的跨域违例**是历史就有的**
  （翻遍 `report_timing/*.rtr`，每一份都是同样的 21 个端点），**不是本轮引入**。

> [!] **最终出位流那一版（`2ddaf32f`）**：CPU 域 **+0.045 ns / 失败端点 0（16,484 端点）**
> —— 约束**满足**，余量 0.4%。`u_pll→u_video`（−1.081 / 21 端点）与 `u_video→u_pll`
> （−0.325 / 1 端点）两条跨域违例**在历史每一份报告里都在**，与本轮无关。

> [!] **给答辩/报告的口径**：不要写"时序余量充足"。写
> **"消除 load-use 停顿换来 −7.8% 周期；代价是 CPU 域余量从 ~5% 降到 ~0.4%，
> 我们认为这个交换是划算的，因为频率上限本来就是靠布局决定的（约定 25）"**。

## 7. 回答"任务 C 能不能做成"

**能，而且比评估时担心的顺利。** 评估里点名的三件风险各自的实测结论：

| 评估里的担心 | 实测 |
|---|---|
