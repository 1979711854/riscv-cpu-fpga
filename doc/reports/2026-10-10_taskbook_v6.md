## 2. 归因：差距到底在哪（**下面每个数都是我实测出来的**）

### 2.1 排除三个常见嫌疑

| 嫌疑 | 实测 | 结论 |
|---|---|---|
| **时钟** | 85.0 vs 83.5 / 90.0 MHz | **同档，不是原因** |
| **分支预测** | 他们 A **5.478%**；我们 **3.5%**（1,543 次误预测 / 迭代）| **我们更好，不是原因** |
| **Cache** | 他们 D-Cache 缺失 **5,135 次 / 5.66 亿次访问 = 0.000%** | **Cache 对他们的分数没有贡献** —— 想靠加 Cache 追分，方向就错了 |

**[重点] 这三条要写进答辩材料**：它说明"我们没做 Cache"不是欠账，而是**这个 benchmark 根本不吃 Cache**（他们做了，缺失率也是 0）。

### 2.2 编译选项能白拿 ~10%（**阶段 0，零风险**）

同一个 benchmark、同一颗我们的 CPU，只换编译选项：

| 版本 | 选项 | 拍/迭代 | 得分 @85 MHz |
|---|---|---|---|
| 当前 | `-O2` | **313,886** | 270.82 |
| 他们的 A 选项 | `-O2` + `-funroll-loops -funroll-all-loops -fpeel-loops` | **288,040** | 295.1 |
| 他们的 B 选项 | `-O3` + 上面 + `-falign-functions=4 -falign-loops=4` | **282,777** | **300.6** |

`crclist = 0xe714` 与基线一致 → **仍是有效运行**。

**合法性**：`third_party/coremark/README.md` 的 Run Rules 里
`Allowed #2: Changing toolchain and build/load/run options` —— **明确许可**，只要如实报告。
> [!] 唯一前提：**先确认赛题本身没规定编译选项**。没规定就用。

### 2.3 [重点] 配对率**不是**主因 —— 它已经接近上限了

用**单发射的干净指令流**做离线复放（`sim/tb_*` 的 `+PAIRTRACE` → `scripts/pair_analyze.py`），
并与双发射实测**交叉验证**：

| | 离线模型 | 实测（反推）|
|---|---|---|
| 指令数 n | 288,056（与文档逐位相同 ✓）| 288,056 |
| 成对指令占比 | **43.8%**（k = 63,042，p = 0.2802）| **41.6%**（228,183 个写回周期 → 59,873 对）|
| 模型误差 | —— | **5.0%，可信** |

**上界也高不了多少**：把规则放宽到"预测**不跳转**的分支也能拿来配对"，p 也只到 **0.3435**（46.6%）。
=> **放宽配对规则的全部收益约 3.5% ~ 7%**（模型口径）。

单独发射的原因拆分（当前规则）：

| 原因 | 占 g 的比例 | 含义 |
|---|---|---|
| **b_not_alu** | **34.8%** | **B 不是纯 ALU**（load/store/branch 等不能当第二条）|
| **break_a** | **31.2%** | **A 是分支/跳转/系统指令**（该组只能 1 宽）|
| waw | 3.6% | 同对写同一寄存器 |
| b_dep_a | 2.3% | B 依赖 A |

> [!] **所以"扩 lane B 到 load/store"这件事，收益上限就在 3~7%** —— 别为它做大改。
> （A→B 旁路那条更小：预测只值 +1.3 分。）

**怎么跑这个分析**（复现用）：
```powershell
# [!] 必须用【单发射】跑 +PAIRTRACE —— 那个探针是 Stage 0（单发射时代）写的，
#     每个写回周期只流出一条记录（v_wb 是单沿），双发射下它看不见 lane B，
#     数出来的 n 是【写回周期数】而不是指令数，配对率会算歪。
scripts\run_coremark.ps1 -Iter 1 -Single
cd sim
vvp tb_coremark_single.vvp +ITER=1 +PAIRTRACE +IMEM=programs/imem.hex +DMEM=programs/dmem.hex
python ..\scripts\pair_analyze.py programs/pairtrace.txt
# 判据：pairtrace.txt 行数必须是 288,056（= 每迭代指令数）。对不上就是口径错了。
```

### 2.4 那剩下的 40% 在哪 —— 两个候选（都还没量死，阶段 1/2 就是去量它们）

先把气泡账单摆出来（双发射，每迭代）：

```
313,886  总周期
228,183  发射/写回拍（其中 59,873 拍成对发射，覆盖 288,056 条指令）
 85,703  气泡 = 27.3%
   其中：load-use stall  30,964
         mul 多拍         9,396
         ex_flush         4,017
         ---------------------------------
         **其余          ≈41,300（13.2%）**  ← 主要嫌疑
```

**候选 (a)：我们的分支预测没有真正做到"从预测目标取指"。**
`core.v` 里 BHT 是在 **`if_id_pc`（ID 级）** 和 **`if_addr_d`（取指数据到达级）** 被查询的 ——
两者都**晚于取指地址发出那一拍**。真正的重定向还是走 ID 级的 `id_redirect`，
实测 **35,195 次/迭代**，也就是**每条被预测 taken 的分支仍然要付 1 拍取指重定向气泡**。
而那 ≈41,300 拍的"其余气泡"几乎正好是它。

> 对照：他们用 BTB **直接从预测目标取指**，理论上 taken 分支 **0 拍**。
> **这是目前最具体、最有界、估计 ~5~10% 的优化点。**

**候选 (b)：RVC。** 他们是 `-march=rv32imc`，我们没有。压缩指令让代码缩小 ~25~30%，
取指带宽和局部性都更好 —— 而我们的瓶颈恰好是**前端供给**。**收益未知，可能最大。**

> [!] **`IPC` 这个数先别急着比**：他们自报 1.350（定时段 1.61），我们从
> 288,056 / 313,886 推算 ≈ 0.92。**但他们的 `Total instructions` 是自建 harness 的口径**，
> 而且他们开了 `-funroll-all-loops`（指令数会变）。**要比 IPC，先跟她/他要那段统计代码**，
> 或者我们自己把 `+PROF` 的指令计数改成"逐条计数"而不是"逐写回周期计数"再比。

## 3. 阶段与排序

**排序原则**：
1. **零风险的先做**（编译选项）。
2. **按"改动半径"从小到大**：前端 → 存储器 → 路径。
3. **路径优化永远最后** —— 前面每一步都会把关键路径改掉，提前优化等于白做。
4. **每阶段都必须能独立验证、独立回退。**

| 序 | 阶段 | 预期收益 | 依赖 | 判据 |
|---|---|---|---|---|
| **0** | **冻结 + 换编译选项** | **+11%**（实测）| 无 | CoreMark ≥ 300；位流归档 |
| **1** | **前端：让 BTB 真正在取指级重定向** | ~5~10%（估）| 无 | 周期数降，49/1/0 与四个 CRC 不变 |
| **2** | **前端：RVC（压缩指令）** | 未知（估最大）| 新验证手段 | 新增 `rv32imc` 测试全过 |
| **3** | **存储器：`mem_ready` 收尾** | 0（是前置）| 无 | `+MEMWAIT=2` 全回归通过 |
| **4** | **存储器：DDR3 + Cache** | **0（是容量，不是速度）** | 3 | 大工作负载能跑 |
| **5** | **路径优化** | 与 1-4 耦合 | 1-4 | PDS 报的 Fmax |
| 之后 | 应用场景（v5 的 C/D/E/F + H）| —— | 5 | v5 §1 |

## 4. 各阶段细节与验收

### 阶段 0 · 冻结 + 编译选项（**做完就能上板，一天**）

1. **先冻结**：`scripts\build_bitstream.ps1 gomoku` 综一个带版本号的 gomoku 位流
   （当前只综了 CoreMark），上板验一遍，归档到 `pds/RV32I_1/bitstreams/`。
   **手里必须永远有一个"能演示的完好版本"** —— 后面任何阶段搞砸了都能退回来。
2. **换编译选项**：`scripts/run_coremark.ps1` 的 `-O2` 改成
   `-O3 -funroll-loops -funroll-all-loops -fpeel-loops -falign-functions=4 -falign-loops=4`，
   同时更新 `scripts/coremark_port/core_portme.h` 的 `COMPILER_FLAGS` 字符串
   （**那是打印给人看的，报告里会引用，别让它和命令行对不上**）。
3. **重算 ITER**：`ITER = 85,005,100 × 10 ÷ 每迭代周期数`。新周期数按实测填，
   取整后留 17% 余量（照现在的惯例）。
4. **验收**：`Total ticks` 与新的每迭代周期数自洽；四个 CRC 仍为
   `e9f5 / e714 / 1fd7 / 8e3a`；板上跑一遍。

### 阶段 1 · 让 BTB 真正在取指级重定向

**要改什么**：`rtl/core/core.v` 的取指地址 mux。现在的链路是
`if_id_pc` 查 BHT → 到 ID 才 `id_redirect` → 下一拍才改 `fetch_addr`。
要做的是**在"发取指地址"那一拍就用 BHT 的结果选目标**，让被预测 taken 的分支
**不再产生取指气泡**。

**难点（先说清，别一头扎进去）**：
- BHT 的索引/tag 现在用 `if_id_pc` / `if_addr_d`（都是**已经取过**的地址）。
  要提前到取指级，就得用 **`fetch_addr` 自己**去查 —— 那会命中/不命中在**同一拍**，
  是个组合环，**必须检查关键路径**（现在 slack 只剩 +0.525 ns，4.5% 余量）。
- 预测目标（分支的 target）现在是在 ID 算的。要提前，得**在取指级也算一遍** ——
  要么预存到 BTB 里（真 BTB 的做法：tag + target），要么用 PC 直接算立即可用的那部分。
  **推荐走"给 BHT 加 target 字段"这条路**，虽然要多一个数组。

**验收**：
- CoreMark 每迭代周期数**下降**（预期 5~10%），
- riscv-tests 49/1/0、四个 CRC、自写测试 2/0 **全部不变**，
- `+PROF` 的 `region flush` / `ID redirect` 计数应明显下降 —— **这是本阶段的直接证据**。

### 阶段 2 · RVC（压缩指令）

**为什么值得**：我们的瓶颈是**前端供给**，而压缩指令直接改善取指密度（一个 32 位字里两条指令）。

**难点（真正的坑）**：
- **16 位指令可能跨 32 位字边界** —— 一条 16 位指令落在字尾、下一条落在下一个字。
  在**双发射 + A1/A2 两个取指口**下，这会彻底打乱现成的"取指两个字、各自译码"的结构。
  **必须先想清楚这一层，再动代码。**
- `pc + 2` vs `pc + 4` 会渗透到：分支/跳转目标、`mepc`、`mtval`、ICACHE 对齐、
  以及 `imem_addr` 的 `fetch_addr[15:2]` 切片。
- 译码（`rtl/core/control.v`）要加一级预译码。

**验证手段要提前准备**：riscv-tests 的 `rv32ui` **不含 C**。
需要：① 用 `-march=rv32imc` 重编现有的 50 个基线 ELF（如果源码在），
或 ② 找/写 `rv32uc` 的测试。**没有测试就别做这个阶段。**

**验收**：新增的 `rv32imc` 测试全过 + 现有两条基线不变 + CoreMark 每迭代周期数变化有解释。

### 阶段 3 · `mem_ready` / `mem_req` 收尾（**DDR3 的前置，必须先做**）

现在的 `core.v` 假定访存**恒 1 拍**。DDR3 一旦接上，访存就是**可变延迟**，
所有依赖"应答当拍到"的逻辑都会错。

`doc/reports/2026-09-27_bus_upgrade_plan.md` §3.5 记了三个实测坑，
**前两个已修，第三个（`id_redirect` 漏 `mem_ready`）当时仍未通过验证**：

```
坑 3 · id_redirect 漏了 mem_ready → 分支预测状态不一致
现象：+MEMWAIT=2 下 BSS 清零循环冲过上限 0x6128 一直转
```

> [!] 那次之后，**A 扩展 + 双发射把这段逻辑整个重写过**（现在是
> `id_redirect = … && mem_ready_int`，多了 `mc_stall`）。**所以坑 3 的状态要用当前 RTL 重新验一遍**，
> 不能沿用"未解决"的结论。

**验收（这一步的判据很硬，也是最有价值的）**：
`+MEMWAIT=1` / `+MEMWAIT=2` / `+MEMWAIT=3` 下，
**四条基线全部通过**（riscv-tests 双/单发射 49/1/0、自写测试 2/0、CoreMark 四个 CRC 不变）。
`sim/mem_model.vh` 已经有 `+MEMWAIT=n` 这个开关，**不用写新工具**。

### 阶段 4 · DDR3 + Cache

**先说清定位**：**这是为了"容量"和"架构完整性（高阶任务①）"，不是为了涨分。**
§2.1 实测已经证明 **Cache 对他们的分数零贡献**（缺失率 0.000%）。

**做法（唯一能让 CoreMark 不掉分的架构）**：
```
CPU ──1 拍──> 片内 64 KB TCM（栈 / 热数据 / CoreMark）
     ├─ I 侧 ─> L1 I-Cache ─┐
     └─ D 侧 ─> L1 D-Cache ─┴─> AXI 主桥 ─> HMIC（硬核存储控制器）──> DDR3 1 GB
```
把 CoreMark 的 `link.ld` 指到 TCM 段 → **分数不变**。

**硬件是齐的**：板上 1 GB DDR3（2×4Gbit、32-bit、1066 Mbps）+ **专供它的 125 MHz 差分晶振（N3/N2）**；
PG2L200H 有 **HMIC 硬核控制器**，对外是 AXI，不用自己写 PHY。

**工作量（仓库自己的判断是"另一个项目"）**：HMIC IP 配置 + 初始化/校准序列 +
AXI 主桥 + 地址映射重划 + Cache（tag/way/替换/写回/一致性 + uncached 窗口划分）+
1066 Mbps 时序收敛 + 全部回归重做。

**如果只是想 claim 高阶① 的收益而不想承担这个工作量**：
`doc/reports/2026-09-25_progress_report.md` §3.1 有已经成文的答辩话术
（结论是"评估后判定为负收益，主动不做"，量化依据是工作集 16.4 KB 远小于片内 64 KB）。

### 阶段 5 · 路径优化（**必须最后**）

阶段 1/2/3/4 每一个都会改变关键路径。**现在优化的是马上要变的东西。**

**现在的位置**：85.0051 MHz 请求 → 实测 **88.98 MHz**，CPU 域 slack **+0.525 ns**（余量 4.5%）。
**开工前先看 PDS 的 `report_timing/cpu_top_board.rtr`**，别拿旧报告的 Estimated 当上限 ——
同一份 RTL 不同 seed 能差 5%。

## 5. 纪律（**这就是"避免改完再加功能产生更多 BUG"的答案**）

1. **每完成一个阶段就上板验证 + 归档位流。** 手里永远有一个可回退的"已知良好"版本。
2. **每阶段开工前先写判据。** 判据要能证伪（例："`+MEMWAIT=2` 全回归通过"），不能是"看起来对了"。
3. **一次只动一个子系统**：前端 / 存储器 / 路径，三选一。RVC 和 DDR3 不能同时开工。
4. **[重点] 特征做成可编译开关** —— 照 `DUAL_ISSUE` 参数的范例：
   现在的 `core.v` 默认 0、`cpu_top.v` 传 1，**一行就能切回已知良好配置做对照**。
   **RVC 和 Cache 都必须这么做。** 这一条最值钱：出问题时能立刻二分。
5. **探针判据（今天的教训）**：
   - `+PROF` 的 **`region cycles` 必须等于 `Total ticks`**（ITER=1 时 313,886）。**看到 1 就是坑。**
   - `+PAIRTRACE` 的 **行数必须是 288,056**（单发射口径）。对不上就是口径错了。
   - **改了字符串/打印要小心 `0xFFF4`**：`sim/tb_coremark.v` 用"第 1/2 次读 0xFFF4"划计时区间，
     任何在 `start_time()` 之前碰 `0xFFF4` 的打印都会**静默打坏所有分解数据**
     （`CLAUDE.md` 约定 42 有完整说明）。
6. **改 RTL 后、综合前要改 `rtl/core/csr_file.v` 的 `DESIGN_REV`**（约定 42）——
   固件把它打在串口第一行，日志靠它自证是哪一版网表。
7. **iverilog 的「端口宽度不一致」警告是硬错误**（约定 40）。
8. **提交按里程碑拆、信息写清改动；不自动 push。**

## 6. 应用场景（**明确排在后面**）

用户 2026-10-10 拍板：**先优化 CPU，再谈应用**。
v5 的 C/D/E/F 与 H 剩余（RT-Thread 拆线程做 G3）**全部排到阶段 5 之后**，
细节见 `2026-10-10_taskbook_v5.md` §3.3–3.6 与 `2026-10-10_handoff_teammate.md` §1。

> [!] **不要并行。** 应用侧每次改动都要重综位流 + 重上板，
> 而 CPU 阶段会**反复**改 RTL —— 两边同时动，"是 CPU 改坏的还是应用改坏的"就分不清了。
> 这也是用户这次指定优先级的原因。

**唯一例外**：如果阶段 0 之后有一段等待（比如等 DDR3 板子/器件），
可以拿来做 v5 的 **A/B 必修项之外的**、**不碰 `rtl/` 的**小活。
